# Wave-1 stores pre-registered by W1-INV

One line per store. W1-INV does not write these stores. `pending: F42` means the collection or prefix is not in the tree yet. A matter deletion finds a row only when `matterId` equals that matter (`functions/src/retention/saga.ts` `rowsQuery`).

- `firestore:intakes` — owner: wave-1 intake writer; why: the prospective matter record before it is promoted; deletion key: field `matterId` (null until promoted, so a matter deletion does not reach that row; W2-DEL, after #264, adds firm/intake-keyed reach); profile `matter_record`; anonymise clears `matterId` only; pending `F42`.
- `firestore:intake_messages` — owner: wave-1 intake writer; why: messages on an intake; deletion key: field `matterId`; profile `matter_content`; pending `F42`.
- `firestore:evidence_items` — owner: already in the inventory (not a W1-INV append); why: evidence of a matter; deletion key: field `matterId`; profile `matter_content`; no `pending` flag because the store is already in the tree.
- `firestore:custody_events` — owner: already in the inventory (not a W1-INV append); why: append-only custody events of a matter (append-only is the writer's rule; the inventory has no separate flag); deletion key: field `matterId`; profile `matter_content`; no `pending` flag because the store is already in the tree.
- `firestore:draft_autosave_points` — owner: W1-L51 (`functions/src/d4/autosave.ts`); why: autosaved draft points, including the `{draftId}~head` cursor in the same collection; deletion key: field `matterId` (a matter deletion queries `firmId` and `matterId`, so a row whose `matterId` is null is not reached); profile `matter_content`; not pending (the writer has landed). Every row carries `firmId`. A pre-matter row (`matterId` null) is found by `firmId` plus the owner key `createdBy` (the draft owner's uid). See `functions/src/d4/autosave.README.md`.
- `firestore:upload_sessions` — owner: W1-L91 (`services/d1-6/bulkUpload.ts`); why: an upload job, including a loose-vault session whose `matterId` is null; deletion key: field `matterId` (a null `matterId` is not reached by a matter deletion); profile `job_record`; every row carries `firmId`; no `pending` flag because the writer is in the tree. The matter-deletion saga does not purge `job_record` rows.
- `objects:upload-staging` — owner: W1-L91; why: staged chunk bytes before promotion into the document vault; deletion key: objects via `firestore:upload_sessions`, path field `storagePath` (the session prefix `<firmId>/upload-staging/<sessionId>`); profile `vault_object` with no `lockConfig` (the F33 lock file is the promoted vault). No `pending` flag. The saga tombstones only `objects:documents`, so this prefix has no matter-deletion reach. Chunks expire 24 hours after the session starts (`BULK_UPLOAD_STAGING_TTL_MS`), when the session is touched or when `sweepExpiredBulkUploads` runs. No scheduler is wired.
- `firestore:whatsapp_outbound_keys` — owner: wave-1 WhatsApp writer (`services/d2-1/outboundKeys.ts`); why: the outbound key hash and `firmId` only, no message content; deletion key: none (matter deletion does not apply); TTL clock: `ageField` `expiresAt` timestamp (Firestore TTL, the `operational_ttl` deleter). The writer has landed, so `pending` is removed.
