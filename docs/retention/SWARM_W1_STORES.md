# Wave-1 stores pre-registered by W1-INV

One line per store. W1-INV does not write these stores. `pending: F42` means the collection or prefix is not in the tree yet. A matter deletion finds a row only when `matterId` equals that matter (`functions/src/retention/saga.ts` `rowsQuery`).

- `firestore:intakes` — owner: wave-1 intake writer; why: the prospective matter record before it is promoted; deletion key: field `matterId` (null until promoted, so a matter deletion does not reach that row; W2-DEL, after #264, adds firm/intake-keyed reach); profile `matter_record`; anonymise clears `matterId` only; pending `F42`.
- `firestore:intake_messages` — owner: wave-1 intake writer; why: messages on an intake; deletion key: field `matterId`; profile `matter_content`; pending `F42`.
- `firestore:evidence_items` — owner: W1-Q08B writer landed; why: evidence of a matter; deletion key: field `matterId`; profile `matter_content`; every row carries `firmId`; no `pending` flag (the store was already in the tree, and the writer does not add one).
- `firestore:custody_events` — owner: W1-Q08B writer landed; why: append-only custody events of a matter (append-only is the writer's rule; the inventory has no separate flag); deletion key: field `matterId`; profile `matter_content`; every row carries `firmId`; no `pending` flag (the store was already in the tree, and the writer does not add one).
- `firestore:draft_autosave_points` — owner: W1-L51 (`functions/src/d4/autosave.ts`); why: autosaved draft points, including the `{draftId}~head` cursor in the same collection; deletion key: field `matterId` (a matter deletion queries `firmId` and `matterId`, so a row whose `matterId` is null is not reached); profile `matter_content`; not pending (the writer has landed). Every row carries `firmId`. A pre-matter row (`matterId` null) is found by `firmId` plus the owner key `createdBy` (the draft owner's uid). See `functions/src/d4/autosave.README.md`.
- `firestore:upload_sessions` — owner: W1-L91 (`services/d1-6/bulkUpload.ts` writes the collection when persistence mode is firestore); why: an upload job, including a loose-vault session whose `matterId` is null; deletion key: field `matterId` (a null `matterId` is not reached by a matter deletion); profile `job_record`; every row carries `firmId`. When the deletion plan's treatment for `objects:upload-staging` is lock or purge and the bytes are actually removed, the saga deletes the matter's rows in batches of at most 450. While staging shares the locked vault bucket, the rows stay. The shipped policy still retains this class. A stored row that does not match the session shape is not loaded.
- `objects:upload-staging` — owner: W1-L91; why: staged chunk bytes; deletion key: objects via `firestore:upload_sessions`, path field `storagePath`. Keys are `upload-staging/<firmId>/<matterId>/...`. No `pending` flag. A one-day lifecycle rule for that prefix is `infra/backup/upload-staging-lifecycle.json` (not applied live). A delete counts only on HTTP 204 or 404; any other status, including 403, is rethrown. The saga lists the prefix again and acknowledges `purged` only when that list is empty. While the chunks share the locked vault bucket, the acknowledgement is `retained` with `locked: true`, not `purged`. The shipped policy retains `vault_object`, so that path does not run until the plan says so. `bulkUploadStagingSweep` lists the prefix by object age and is idle unless `SIKANDER_FLAG_D1_BULK_UPLOAD` is `true`. A segment named `documents` does not hide a staging key from that list.
- `firestore:whatsapp_outbound_keys` — owner: wave-1 WhatsApp writer (`services/d2-1/outboundKeys.ts`); why: the outbound key hash and `firmId` only, no message content; deletion key: none (matter deletion does not apply); TTL clock: `ageField` `expiresAt` timestamp (Firestore TTL, the `operational_ttl` deleter). The writer has landed, so `pending` is removed.
