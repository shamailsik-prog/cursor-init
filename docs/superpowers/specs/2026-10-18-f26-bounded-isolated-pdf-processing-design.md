# F26: every harvested PDF is bounded, kept and parsed in a sandbox (design)

**Finding.** Audit F26 (HIGH, P0), `docs/audit/2026-10-13-forensic-audit.md`: "Production PDF paths bypass the bounded downloader and parser isolation." Judgment tasks read `response.content` and run PDF extraction synchronously inside the async task; a PDF signature is not a resource or malware check. Failure scenario: a malicious or oversized valid-signature PDF consumes worker memory or parser CPU before any size policy can protect it, and one slow parse ties up its task slot. Recommended correction: the shared bounded download path for every connector; decompressed, page and time limits; immutable raw files; parsing in an unprivileged sandboxed subprocess with memory and CPU quotas, and a malware policy. The v2 re-audit (`docs/audit/2026-10-14-forensic-audit-v2.md`, F26 row) has it OPEN: "lahorehighcourt.py / pdf_extractor.py unchanged".

**Rule for closure** (`docs/audit/REMEDIATION.md`): a merged PR with an end-to-end test of the real flow that fails on main and passes after it, then an independent re-audit.

**Base.** origin/main 84025e8 (F25 #67, F28 #72, F31 #71 and F23 #74 merged). The branch had no commits of its own when F31 and F23 landed, so it was fast-forwarded to each new main; nothing was rebased.

## 1. What main does today

F25 (#67) already routes every request through the fetch boundary (`scraper/net/fetch_policy.py`), so the download half of the finding is narrower than when it was written. F28 (#72) already counts `not_pdf` and `empty_pdf_text` as failed documents.

| Path | Download | Size policy | Parse | Raw bytes | Active content |
|---|---|---|---|---|---|

Measured with main's extractor in process (evidence log; Python 3.12, pdfplumber 0.11.10, pdfminer.six 20260107, shared 4-core machine at load 10-20): a 26 KB PDF holding one million path operators takes 54.6 s to "extract" (it yields no text); a 0.5 MB PDF whose content stream inflates to 512 MiB raises the worker's peak RSS to 1,073 MiB; a PDF whose catalog opens a JavaScript action is extracted and staged.

## 2. Rulings

Each ruling records the decision and the reason (owner's standing instruction).

**R1. One path from a fetched PDF to text: `scraper/tasks/pdf_intake.py`.** All seven PDF harvesters (six court modules and National Assembly) call `pdf_intake.intake(client, url[, fetch=...])` for every PDF, inside their existing `async with fetch_policy.fetcher_for(...)` block. Nothing else in the production tree imports a PDF parser library (pdfplumber, pdfminer, pypdfium2, pytesseract, PIL) or the extractor: `tests/test_f26_pdf_sandbox.py` fails the build if any module other than `parsers/pdf_extractor.py` (the parser) and `parsers/pdf_sandbox.py` (its process) does. `pdf_extractor.download_pdf` and `download_pdf_sync` are removed: no caller, they need a streaming client API the boundary does not offer, and F25's spec left them for F26 to retire. `bootstrap_harvest.py` is unchanged: it downloads through F25's boundary (bounded, 100 MiB) and never parses. *Reason:* the finding is that connectors each did their own thing; one function makes every refusal, bound and record identical for every source, and a guard keeps a second path from growing back.

**R2. The PDF size policy is enforced by the boundary, before the body is held.** The cap is `settings.PDF_MAX_SIZE_MB` MiB (the existing operator setting, default 100, range 1-500), never above F25's `MAX_BYTES`. `intake` narrows the connector's `PolicyFetcher.max_bytes` to the cap (only ever downwards, `min`), so the boundary refuses a declared `Content-Length` over the cap before reading the body, and a streamed body as soon as it passes the cap; that refusal (F25's `too_large`) becomes `pdf_too_large`. The client is recognised by that public attribute, not by its class: F25's guard refuses any reference to `PolicyFetcher` outside the boundary module (found while going GREEN). `intake` re-checks the length it was given, for a client that has no such cap (the test harnesses). *Reason:* the finding's "before the size policy can protect it". F25 forbids building a `PolicyFetcher` outside its registry, its factory takes no cap, and `scraper/net/*` is another lane, so narrowing the public `max_bytes` attribute of the client the connector already holds is the way to apply a per-stage cap. The default stays 100: it is the operator's documented setting, and the sandbox (R6) is what bounds parser memory, not the download cap.

**R3. Cheap checks run in the worker, before anything is stored or parsed.** In order: HTTP 200 (else `http_<status>`, F28's key and F28's retry rule, unchanged); the declared `Content-Type` is not a non-PDF family (`text/html`, any `xml`, `json` or `javascript` type, `image/*`, `audio/*`, `video/*`, `font/*`, `multipart/*`), else `not_pdf`; the body starts with `%PDF-` (F28's `looks_like_pdf`), else `not_pdf`. An absent type, `application/pdf`, `application/octet-stream`, `text/plain` or any other type passes to the signature check. *Reason:* the brief asks for content-type and magic checks before parsing. A denylist, not an allowlist, because government servers label PDFs `application/octet-stream`, `application/x-download` and worse; the header is server-declared metadata, not a safety property, and the signature plus the sandbox are the controls. The check catches the common failure: an HTML error or login page, or an image, served at a `.pdf` URL. A body that claims to be HTML and starts with `%PDF-` is a polyglot and is refused.

**R4. Malware policy: a PDF that carries JavaScript, a launch action, an embedded file or a script container is refused (`pdf_active_content`), before any text is extracted.** In the sandbox, before extraction, a structural scan opens the document with pdfminer and walks every object it resolves through the cross-reference table or stream, including objects packed in compressed object streams, plus every trailer: every dictionary key, every name value and every stream dictionary is checked against `/JS`, `/JavaScript`, `/Launch`, `/EmbeddedFile`, `/EmbeddedFiles`, `/EF`, `/FileAttachment`, `/RichMedia` and `/XFA`. Names are compared after pdfminer decodes `#xx` escapes, so `/J#61vaScript` is `/JavaScript`. `/EF` and `/FileAttachment` are in the list because an attachment needs neither `/EmbeddedFile` (the stream's `/Type` is optional) nor the `/EmbeddedFiles` name tree; `/XFA` and `/RichMedia` because they carry scripts without any `/JS` name. A document pdfminer cannot open is left to extraction (which then fails as `empty_pdf_text`). There is **no byte scan of the raw file in the worker**, which the predecessor draft had: a three-byte pattern such as `/JS` followed by a delimiter occurs by chance in compressed or image data about once in 3x10^8 positions, so a 10 MB scanned judgment would be refused about 3% of the time, and the same text inside a content-stream string would refuse a judgment that merely quotes it. A full antivirus scan is a follow-up (F26-FU1): no engine is in the image, and ClamAV would add a daemon and a signature-update service. *Reason:* court judgments never need scripts, launch actions or attachments, so refusing them costs nothing; the extractor does not execute them, but a malware policy is about what the service accepts, and viewer exploit chains start from exactly these features. Object streams are the standard way to hide them from byte scanners, so the scan is structural.

**R5. Raw bytes are kept once, by sha256, before parsing.** `scraper/parsers/raw_store.py` writes the bytes to `<PDF_STORAGE_PATH>/raw-pdf/sha256/<aa>/<bb>/<sha256>.pdf` (`PDF_STORAGE_PATH` is the existing "local vault for PDFs" setting, the compose `./live` volume). Every write holds an exclusive `flock` on `raw-pdf/.lock`, so workers in different containers sharing the volume are serialised. A new object is written to a temporary file (owner read-only, R14), fsynced and hard-linked to its name, so a stored file is never overwritten or truncated and a crash leaves no partial object. An existing object is verified by size and sha256 before reuse; a mismatch is refused (`raw_store_failed`) and logged. The store is bounded: a ledger (`raw-pdf/.usage`) holds the stored bytes, and a write that would take the store past `MAX_STORE_BYTES` (20 GiB) or leave less than `MIN_FREE_BYTES` (1 GiB) free on its filesystem is refused (`raw_store_full`); how the ledger stays safe when a writer dies is R15. Any other failure to write is `raw_store_failed`. The court staging row records the store key (relative to `PDF_STORAGE_PATH`, so it survives a different mount point) in `raw_pdf_path` (an existing column; F19's publication already maps it to provenance `raw_storage_key` and derives `extraction_method` `pdf` / `ocr` from it and `ocr_applied`), and records `pdf_page_count`, `ocr_applied`, and `parsing_metadata.raw_sha256`. Documents refused by R2-R3 are not stored; documents that reach parsing are stored first, including ones the sandbox then refuses (they are evidence for re-examination; the store is never served). *Reason:* FINAL_2 mandatory rule 2 ("write raw html/pdf reference ... BEFORE attempting any parsing") and the finding's "retain immutable raw files": a re-parse reads the store, never the court. Fail closed: a document that cannot be retained is not parsed. No schema change: the columns exist. National Assembly writes `statutes_master`, which has no raw-reference column, so NA keeps the file but its rows do not point at it (F26-FU2).

**R6. Parsing runs in a separate process with hard limits: `scraper/parsers/pdf_sandbox.py`.** The worker starts a child with billiard's `spawn` context (a fresh interpreter, never a fork of the worker), hands it the stored file's path, sha256 and size, and waits in a thread (`asyncio.to_thread`), so the event loop keeps running. The child, before it reads any PDF byte:
1. becomes a session leader (`setsid`), so the worker can kill it and any `tesseract` it started as one process group, and arms `alarm()` a little past the wall limit, so even an orphan ends;
2. replaces its environment with a fixed minimal one (`PATH`, `LANG`, `LC_ALL`, `OMP_THREAD_LIMIT=1`, `HOME` and `TMPDIR` = its own scratch directory, and `TESSDATA_PREFIX` only if the worker has one): no credential reaches the parser or `tesseract`;
3. sets `RLIMIT_AS` and `RLIMIT_DATA` (memory), `RLIMIT_CPU` (CPU seconds; SIGXCPU ends it), `RLIMIT_FSIZE` (largest file it may write; SIGXFSZ ignored so a write fails instead), `RLIMIT_NOFILE` and `RLIMIT_CORE = 0`;
4. opens its input (`O_NOFOLLOW`), checks size and sha256 against what the worker stored, imports the parser stack and warms it on a built-in one-page PDF (so nothing the parser loads lazily needs the privileges dropped next);
5. tries to leave the network (`unshare(CLONE_NEWNET)` as root, else an unprivileged user and network namespace) and, when it runs as root (the corpus image has no `USER`), drops to uid/gid 65534 with no supplementary groups, after which its `/proc/self/environ` is unreadable and it cannot write the application tree; what it achieved is reported (`net`, `uid`), never assumed;
6. sets PIL's `MAX_IMAGE_PIXELS` with decompression-bomb warnings raised as errors.

It inherits no socket and no database connection: spawn passes only its own pipes (`close_fds`). It answers with one JSON document on a pipe; the worker reads at most `max_result_bytes` and never unpickles anything the child sends. A watchdog timer kills the process group at the wall limit whatever the worker thread is doing, and the group is killed again on every exit path before the child is reaped. *Reason:* the finding's "parse in an unprivileged sandboxed subprocess with memory/CPU quotas". The process boundary is what makes the limits enforceable: `setrlimit` on the worker would cap the whole Celery process, and a C-level loop in pdfium or zlib cannot be interrupted in process.

**R7. Why billiard's spawn and not `subprocess` (a ruling for the re-auditor).** F25's guard (`tests/test_f25_fetch_guard.py`, another lane, not edited here) refuses `subprocess`, `ctypes`, `os.exec*`, `os.posix_spawn`, `asyncio.create_subprocess_*` and `anyio.run_process` anywhere in corpus code, because a program such as `curl` opens an HTTP path the boundary cannot see. A spawn-context process does not run a program of the caller's choosing: it re-runs this Python interpreter on billiard's fixed bootstrap and executes one picklable callable, `scraper.parsers.pdf_sandbox._child`, which is itself scanned by F25's guard. So the sandbox opens no path around the boundary. Stdlib `multiprocessing` cannot be used: Celery's prefork workers are daemonic billiard processes, billiard mirrors that into `multiprocessing.current_process()`, and stdlib `Process.start()` then refuses ("daemonic processes are not allowed to have children"; proven in `test_f26_pdf_sandbox.py`). billiard's `Process.start()` has no such check, and billiard is already installed as Celery's process library; it is now declared in `requirements.txt` (F31's import contract requires every direct import to be declared), as is `pdfminer.six`, pdfplumber's own parser, which the active-content scan imports directly. F26's own guard test pins process creation to that one module, that one context and that one target, so billiard cannot become a way to run arbitrary code later. Residuals, stated plainly: spawn cannot pass a custom environment, so the child's initial environment block, scrubbed from Python and unreadable through `/proc` after the uid drop, still sits in its memory, where a native-code exploit in the parser could read it; and billiard starts one small semaphore-tracker helper per worker process the first time it spawns. The clean fix for the first is an exec with an empty environment, which needs an allowlist entry in F25's guard (that lane) or a dedicated parse container (F26-FU3).

**R8. Limits (defaults, reviewed in code like F25's bounds; `pdf_sandbox.LIMITS`).**

| Limit | Value | Over it |
|---|---|---|
| wall time per document (watchdog; child `alarm` at +15 s) | 300 s | `pdf_parse_timeout` |
| CPU time of the child (`RLIMIT_CPU`) | 270 s | `pdf_parse_timeout` (SIGXCPU) |
| address space and data (`RLIMIT_AS`, `RLIMIT_DATA`) | 1 GiB | `pdf_memory_limit` (the child's `MemoryError`) |
| largest file the child or `tesseract` writes (`RLIMIT_FSIZE`) | 64 MiB | the write fails; the page's OCR fails |
| open files (`RLIMIT_NOFILE`) | 64 | the open fails |
| pages | 1,000 | `pdf_page_limit` |
| extracted text, from the text layer or from OCR | 4,000,000 characters | `pdf_text_limit` |
| result on the pipe | 24 MiB | `pdf_text_limit` |
| pages sent to OCR | the first 25 | the rest are not OCRed; the result says `ocr_truncated` |
| pixels of a page rendered for OCR, and of any image PIL decodes | 50,000,000 (an A4 page at 300 dpi is 8.7 million) | the page is not rendered (`ocr_skipped`); PIL's bomb error fails that page |
| `tesseract` per call | 30 s | that page's OCR fails |

Any other death of the child is `pdf_parse_crashed` (a signal: pdfium, for one, aborts with SIGABRT when an allocation fails inside it) or `pdf_parse_failed` (no usable answer). Measured: a normal text parse peaks at 66 MiB of virtual memory, an OCR render at 138 MiB, so 1 GiB is about seven times the largest normal need. The wall limit is sized for OCR: `tesseract` takes several seconds per page on an idle core and far longer on a loaded one, and 25 OCR pages must fit. The OCR cap trims work, not the document: a scanned judgment of more than 25 pages is OCRed on its first 25 and staged with `ocr_truncated` in `parsing_metadata`. That is not a new kind of partial row: every court harvester already stages `text[:50000]`, about 15-20 pages, so OCR beyond 25 pages never reached a staging row anyway. The page and text caps refuse, because a document past them is not a judgment. *Reason:* the brief's page, per-page OCR, total text and image-decompression caps, and the finding's time and memory quotas; a run of hostile documents now costs at most the wall limit each, inside Celery's 3,600 s task limit, instead of an unbounded hold on the slot.

**R9. The extractor's algorithm does not change.** `pdf_extractor.extract_pdf(data, limits)` is the old `extract_pdf_text` with the caps of R8 checked inside its loops, each page's cached layout released after it is read (`Page.close()`), and `MemoryError` and limit errors no longer swallowed by its broad handlers, including when pdfplumber wraps them (`PdfminerException(e)`, `MalformedPDFException(e)`): every broad handler first looks through the exception's cause, context and arguments and re-raises either one (found while going GREEN: the first run of the 1.5 GiB bomb test was `pdf_parse_crashed`, signal 6, because the wrapped `MemoryError` was swallowed and the OCR fallback then aborted inside pdfium). It also reports what it did (pages, whether the returned text came from OCR, pages OCRed, skipped, truncated). `extract_pdf_text(data)` keeps its signature and returns the same text. With no cap reached, the sandbox returns exactly what main's extractor returned for the same bytes: a golden test compares the staged text with text produced by main's in-process extractor (`tests/fixtures/f26/`, generated from main's unmodified `pdf_extractor.py`). *Reason:* the brief's "a normal PDF still parses to the same text as before".

**R10. Every refusal is a failed document in F28's tally.** `outcomes.DocumentRejected(code)` (new, in F28's vocabulary module): `error_key` is the code, so the run record's `errors` counts `pdf_too_large`, `pdf_active_content`, ... like `not_pdf`; it is never retried, except an `http_<status>` code, which keeps F28's transient-status rule. A run whose every document was refused fails (`SourceRunFailed`, F28 R2); a run with some staged and some refused is partial. Codes: `not_pdf`, `empty_pdf_text` (F28's), `pdf_too_large`, `pdf_active_content`, `raw_store_full`, `raw_store_failed`, `pdf_parse_timeout`, `pdf_memory_limit`, `pdf_page_limit`, `pdf_text_limit`, `pdf_parse_crashed`, `pdf_parse_failed`. *Reason:* the brief: "a typed failure that F28's tally counts as a failed document, never progress, with a safe error class". The codes carry no document content.

**R11. The worker survives a hostile document.** A refusal ends that document; the next one in the same run is processed. The worker process never holds more than the capped body (R2) and never runs parser code. *Reason:* the finding's "worker crashes, stalled queues".

**R12. Test seams.** The F20 harness (subject: trust, not parsing) used to stub `pdf_extractor.extract_pdf_text` and `nationalassembly.extract_pdf_text`; it now stubs `pdf_sandbox.parse`, the function `intake` looks up at call time, exactly as F25's harnesses replace `fetch_policy.fetcher_for`. F28's two marker fixtures (a readable judgment, a whitespace-only text layer) move to the same seam; its unreadable fixture still goes through the real parser, now in the real sandbox. No production switch bypasses the sandbox; tests that need small limits replace `pdf_sandbox.LIMITS`. The pinned test set gains pdfplumber and its parser stack (`pdfplumber`, `pdfminer.six`, `pypdfium2`, `pillow`) in `requirements-test.txt`, so the golden, sandbox and e2e tests run the real parser in CI; F31's alias table drops its `PIL` and `pdfplumber` entries, which it keeps only for modules the pinned set cannot map. `tests/conftest.py` points `PDF_STORAGE_PATH` at a per-session temporary directory (one additive fixture), so no test writes `/app/live`.

**R13. Scope.** No change to `scraper/net/*` or `tests/test_f25_*` (F25), F24's routers and `public_corpus.py`, F23's `routers/quarantine.py`, `quarantine_ledger.py` and migration, `models.py`, `config.py`, `main.py`, `init.sql`, migrations or the Dockerfile. No schema change. Edits to `requirements.txt` (`billiard`, `pdfminer.six`), `requirements-test.txt` (the parser stack), `tests/import_contract.py` (two aliases out) and `tests/conftest.py` (one fixture) are additive or subtractive only where R12 says why. The F20 harness and F28's marker fixtures move to the new seam (R12); no expected value in them changes. *Reason:* the brief's lanes.

**R14. The raw store is owner-only; every container that mounts it runs as one uid** (PR #76 review round: CodeQL `py/overly-permissive-file`, severity 7.8, three results in `raw_store.py`). Objects are 0o400; the lock and the ledger 0o600; every directory the store creates 0o700. Modes are set explicitly (`fchmod` / `chmod` after creation), so a permissive umask cannot widen them. Nothing needs group or world access: (a) the PDF sandbox opens, reads and verifies its input in step 4 of R6, before step 5 drops it to uid 65534, and after the drop it reads only the bytes it holds in memory and its own scratch directory (chowned to 65534 before the drop); (b) in `corpus_service/docker-compose.yml` every service that mounts `./live` (`api`, `worker-a`, `worker-b`, `worker-embed`) is built from `corpus_service/Dockerfile`, which declares no `USER`, and no service sets `user:`, so every reader and writer of the store runs as uid 0. Ruling: the store requires its readers and writers to share one uid. A deployment that runs them as different uids must give them the same uid, or change the store to group access with a shared gid in a reviewed change; it must not loosen the modes in place. The test environment proves the read-before-drop order: running as root, the sandbox reads a 0o400 root-owned object and then reports uid 65534, which could not have read it. *Reason:* a raw judgment PDF is untrusted input and evidence; no other local user needs it, and the modes then match what the code needs and no more.

**R15. The usage ledger fails safe** (PR #76 review round: Codex P2, thread 4306132181). In the first version an object was linked before the ledger was updated, so a worker killed in between, or a ledger write that failed, left an object the ledger did not count; a later put of the same bytes took the existing-object branch without repairing it, and the store could pass `MAX_STORE_BYTES` (only `MIN_FREE_BYTES` still protected the disk). Ruling, of the two options the review offered: record usage before linking, and correct an overcount by recounting. Under the lock, a new object is written and fsynced to a temporary file, the ledger is rewritten (temporary file, fsync, atomic replace, directory fsync) to count it, and only then is the object linked; a link that fails puts the ledger back. An interruption between the ledger write and the link therefore overcounts, never undercounts. Whenever the ledger says a write would pass the cap, and whenever it is missing or unreadable, the store recounts its objects from the tree, rewrites the ledger and removes temporary files, which only a killed writer can have left (every writer holds the lock while it has one), and only then decides. *Reason:* of the two directions an interrupted write can leave the ledger, only an overcount keeps the cap; recounting only when the ledger says the store is near its cap keeps the common write O(1) (the alternative, validating the ledger against the tree before every write, walks the whole store each time).

## 4. End-to-end tests (`tests/test_f26_pdf_intake_e2e.py`)

The flow is the production one: the `scrape-lahorehighcourt` beat entry runs the real Celery task (`Task.apply`), dispatcher, LahoreHighCourt harvester, `pdf_intake`, raw store, sandbox and F28 run record against a fresh Postgres 16 + pgvector database migrated by `python -m scraper.migrate`. The network edge is a local HTTPS server (a throwaway CA) reached through the real `PolicyFetcher` with the boundary's own test hooks (`_test_ssl_context`, `_test_loopback_origins`); only discovery is replaced, to return the server's PDF URLs, as the F20 and F28 harnesses do. Expected values come from this spec, not from the code under test.

- (a)/(b) oversized (declared and streamed), decompression bomb, slow parse, each followed by a normal judgment in the same run: refused with its code within the limits, counted as a failed document, the run partial, the normal judgment staged (the worker survives), no parser code run in the worker process and no bomb-sized allocation in it.
- (c) the golden fixtures are staged with exactly the text main's extractor produced.
- (d) the same bytes at two URLs over two runs are stored once, read-only, under their sha256, and every staging row points at that key.
- (e) a `/JavaScript` PDF (plain and inside an object stream) is refused; a run of only such PDFs fails and is not retried.

## 5. Residual risks

- Native-code exploit inside the sandbox (the finding asserts none): bounded by the limits, the uid drop (when root) and the network namespace (when the kernel allows it); the child's initial environment block stays in its memory (R7). In Docker's default seccomp profile `unshare` is refused, so production reports `net: none` unless the operator grants it, and such an exploit could then read the worker's environment and reach the network. The brief's floor ("inheriting none of the parent's DB or credential handles") holds regardless; F26-FU3 closes both gaps.
- No `PR_SET_PDEATHSIG` or `PR_SET_NO_NEW_PRIVS` (both need `ctypes`, which F25's guard bans): if Celery hard-kills a worker mid-parse, the orphaned child ends at its alarm (wall + 15 s) or CPU limit.
- The structural scan sees what pdfminer resolves (every cross-reference section, object streams, its own repair scan of a broken table). A viewer with a different repair heuristic could see objects pdfminer does not.
- Refused documents that reached parsing stay in the raw store (R5); the store has no pruning or retention policy beyond its size bound.
- No antivirus engine (F26-FU1).

## 6. Follow-ups

- **F26-FU1.** Antivirus scan of retained PDFs (ClamAV sidecar or equivalent), with its own update policy.
- **F26-FU2.** A raw-reference column (or provenance row) for National Assembly's `statutes_master` writes.
- **F26-FU3.** Exec the sandbox with an empty environment (needs an allowlist entry in F25's guard) or move parsing to a dedicated container with no secrets and `network_mode: none`; grant or refuse `unshare` explicitly in compose.
- **F26-FU4.** A retention and pruning policy for the raw store, and a re-parse command that reads it.

## 7. Follow-up: the independent re-audit (F26-FU)

The independent re-audit of PR #76 (merged as 53f4450, head 5121394) failed F26 at 7/10 on one MEDIUM, tracked as FA-corpus-009 in issue #30. The sandbox child inherits the worker's stdout and stderr. A 2,777-byte PDF whose form XObject makes pdfminer log one warning per invocation wrote 7,241 MiB into the worker's stderr in 300 s, which is Docker's unrotated json-file log on the host disk; `RLIMIT_FSIZE` does not bound a pipe. The re-audit also listed LOWs L1-L6 and four INFO items. This section rules on each. Branch `claude/remediate-f26-fu`, from origin/main 53f4450; every RED in the plan's ledger is a run of the new tests on 53f4450's code.

**R16. The child never writes to the worker's stdout or stderr (FA-corpus-009).** The first thing `_child` does, before `setsid` and before it reads a byte of the PDF, is open `/dev/null`, `dup2` it onto fds 0, 1 and 2, and call `logging.disable(logging.CRITICAL)`. Everything the child and its `tesseract` write to those descriptors (pdfminer's warnings through logging's last-resort handler, Python warnings, a native library's messages, billiard's own traceback printing) goes nowhere, and no log record is even built. If `/dev/null` cannot be opened, the child answers `pdf_parse_failed` (detail `stdio`) without reading the PDF: it never parses while attached to the worker's log. *Why `/dev/null` and not a scratch file bounded by `RLIMIT_FSIZE`:* a file costs up to 64 MiB of disk per parse, times every concurrent parse, and nobody reads it; its content would be derived from the document, which is untrusted. *Diagnostics, ruled:* the child returns exactly what it returned before: one code, a short content-free detail (an exception class, a signal number, an active-content name) and the isolation record. No log text crosses the pipe: pdfminer's warnings quote document bytes (the flood PDF's are 100 KB strings), and `ParseRefused.detail` is content-free by contract (R10). The worker still logs one line per parse with the code. The isolation record now reads back where fds 0-2 point and whether logging is disabled (R24), so a test sees the redirect itself, not only the absence of output.

**R17. A stale temporary object never blocks a write (L1).** The raw store names a new object's temporary file `.<sha256>.<16 random hex digits>.tmp` (`secrets.token_hex(8)`) instead of `.<sha256>.<pid>.tmp`, and keeps `O_EXCL`. A writer killed after it created its temporary file can no longer make every later put of the same document by a process with the same pid fail with `FileExistsError` (`raw_store_failed`) until a recount. R18 reclaims the stale file.

**R18. When the store recounts (L2, L3; replaces R15's trigger).** R15's order (count before link, so an interruption overcounts) stands. What changes is when the tree is walked. R15 walked it, under the global lock, on every put that the ledger said would pass the cap: at a full store of 100,000 objects that is 3.8-5.2 s per refused put, serialising every worker (L3). A refusal at the free-space floor never recounted, so temporary files left by killed writers stayed invisible there (L2). The store now recounts, under the lock and before any bound is checked, in exactly three cases:
1. the ledger is missing or unreadable (as before);
2. a **dirty marker** (`raw-pdf/.dirty`) exists. A writer sets it, and fsyncs the store directory, before it creates its temporary file, and clears it only after the object is linked and the temporary file is gone. A marker that survives means a write was interrupted: the ledger may overcount and temporary files may remain. A failed write that the store handled also leaves it set, so the next put recounts once (the safe direction);
3. a write would pass **either** bound (the cap or the free-space floor) and the last recount is older than `RECOUNT_INTERVAL_SECONDS` (600 s), as recorded by the modification time of `raw-pdf/.recounted`, which every recount touches (a missing stamp, or one in the future, counts as due). This keeps R15's self-repair for what the marker cannot see (an operator who removed objects by hand, a marker lost in a power failure) and bounds its cost to one walk per ten minutes, whatever the refusal rate.

Otherwise the store refuses from the ledger, without walking the tree. A recount removes every temporary file, rewrites the ledger, touches the stamp and only then clears the marker. *Ruled against:* recounting at every refusal (L3), and recounting only on the marker (an operator's manual removal would then leave the store refusing indefinitely). An operator who removes objects and wants the space back at once deletes `raw-pdf/.usage`; the next put recounts.

**R19. `/health` and `/api/vault` never walk the raw store (L5; amends R13, which left `main.py` alone).** Since F26 the raw store lives under `PDF_STORAGE_PATH` (`/app/live`). That is the directory `/health` walks with `rglob` to count `total_pdfs`, so every unauthenticated, unrated `/health` call stat-ed every raw object (1.8-2.4 s at 100,000 objects), and `total_pdfs` silently began to count raw-store objects. `/api/vault`'s newest-100 listing filled with them too. Both now enumerate the vault through one helper that prunes any directory named `raw-pdf` (`raw_store.STORE_DIR`) and does not follow directory links. `total_pdfs` therefore counts what it counted before F26 (bootstrap PDFs over 15,000 bytes), and `/api/vault` lists what it listed before. The response shapes are unchanged, so no consumer is affected; the dashboard's `total_pdfs` tile (`templates/dashboard.html`) shows the pre-F26 number again. *Whether `/health` should walk the tree at all, ruled:* not decided here. The remaining walk, of the bootstrap vault, predates F26 and is owned by two open findings: F44 (MEDIUM: "expose cached freshness/queue telemetry rather than recursive file enumeration") and FA-corpus-001 (MEDIUM: an unauthenticated, unrated full-table `COUNT(*)`). Removing the walk would change what `total_pdfs` means to the dashboard, which is F44's redesign (liveness versus readiness, cached telemetry), not a sandbox fix. F26-FU only takes back the cost F26 added.

**R20. Active features the malware policy now refuses, and the one it accepts (L4).** Added to `ACTIVE_CONTENT_NAMES`:
- `/OnInstantiate` and `/3DD`. A 3D annotation's script runs from its 3D stream's `/OnInstantiate`, with no `/JS` name. `/3DD`, the 3D stream every 3D annotation must carry, refuses 3D artwork as a whole: no judgment carries it, and the U3D and PRC parsers are a known exploit surface.
- `/GoToR` and `/GoToE`: go-to actions whose target is another file (`/F` can be a UNC path, which makes a viewer leak the user's NTLM hash) or an embedded one.
- `/SubmitForm` and `/ImportData`: form actions that send the form's data to a URL or load data from a file (the same leak class). A judgment is not a form.

**Accepted: `/URI`.** Judgments link to statutes, law reports and court sites, so refusing link actions would refuse ordinary documents; a test pins that a judgment with a URI link is accepted. A URI action runs only when a reader clicks it, the raw store is never served, and nothing in the service resolves it. Residual: a `javascript:`, `file:` or UNC URI is accepted too, because the scan is name-based and does not read string values. Other action types not listed (`/Sound`, `/Movie`, `/Rendition` without a `/JS` key, `/Hide`, `/Named`, `/SetOCGState`) stay accepted: they run no script and send nothing. Content-level detection belongs to F26-FU1 (an antivirus engine).

**R21. A response with more than one Content-Type value is not a PDF (INFO).** RFC 9110 makes Content-Type a singleton field. The intake reads every Content-Type field (`get_list` on the boundary's `httpx.Headers`; every matching key on a harness mapping) and refuses with `not_pdf` (detail `multiple Content-Type values`) when there is more than one field, or one field whose media type, before any `;` parameter, is a comma-separated list. Identical duplicates are refused too: a duplicated singleton field marks a malformed or rewritten response, and the header is server-declared metadata, while the signature check and the sandbox remain the real controls. A comma inside a parameter (`application/pdf; name="a,b.pdf"`) is not a list.

**R22. billiard is pinned in the test set (INFO).** `requirements-test.txt` pins `billiard==4.3.1`, the version `celery[redis]==5.6.3` resolves to today, so the sandbox tests run the process library they were proven with. The runtime `requirements.txt` keeps billiard unpinned beside Celery, like the rest of the runtime set, until F46 pins it. F31's import contract is unaffected: billiard stays declared there.

**R23. A killed pool process's scratch directory is swept (INFO).** The worker names each parse's scratch directory `f26-pdf-<worker pid>-<random>` in the system temporary directory. Before it creates one, `parse` removes every `f26-pdf-*` directory there whose worker is no longer a live process, or whose last change is more than `SCRATCH_STALE_SECONDS` old (7,200 s: twice Celery's 3,600 s hard task limit, so no live parse can own it). Directory links are never followed and removal is best effort (`shutil.rmtree` does not follow links). A pool process killed mid-parse (Celery's hard limit, the OOM killer) can no longer leave its 65534-owned directory behind indefinitely: the next parse in that container removes it, even while the orphaned child still runs (the child ends at its alarm or CPU limit, and its answer goes nowhere). Directories named by F26's first version, which carry no pid, are swept by age.

**R24. What the tests can now see (L6).** The re-audit's 16 surviving mutants included 12 real gaps. Each now has a test that fails under it. Some needed the code to expose what actually holds rather than what it set:
- the two reply bounds report different details. The child's own cap answers `answer over max_result_bytes`; the worker's read bound refuses with `answer over max_result_bytes (worker bound)`. Each layer is therefore observable alone (M14, M15).
- the isolation record reads back, inside the child and after isolation: its network namespace (`/proc/self/ns/net`) and the interfaces it sees (`/proc/self/net/dev`); whether it leads its own session and process group; where fds 0-2 point; whether logging is disabled; and PIL's pixel bound and bomb-warning filter. A test compares the namespace with the worker's own where a probe shows that this kernel lets a process enter a new network namespace, and is skipped with the probe's error where it does not (M37, M44).
- `_kill_group` is tested on a real session leader with a grandchild (M38); the OCR loop on a page whose size cannot be read (M48); and one fixture per active-content name, each carrying no other listed name (M19-M24).

The equivalent survivors stay recorded as equivalent: M11 (`RLIMIT_CORE` is already 0 here), M16 and M17 (a JavaScript action carries both `/S /JavaScript` and `/JS`) and M32 (the chain walk re-raises a direct `MemoryError` too).

**R25. F26-FU3 proposed, not built.** The child's initial environment block still holds the worker's secrets (FA-corpus-010). The smallest safe design is a dedicated parse service: a `pdf-parser` container from the same image, with no secrets in its environment, no network (`network_mode: none`), a read-only mount of the raw store and a scratch tmpfs, reached through a Unix socket on a shared volume. The worker would send a sha256 and receive the JSON answer the sandbox already produces. An exec with an empty environment is smaller in code but needs an allowlist entry in F25's guard, which is another lane. Either is a design change that needs its own review, so it is recorded as the first follow-up and not built here.

### Residual risks after F26-FU

- FA-corpus-010 (F26-FU3): the environment block in the child's memory and, under Docker's default seccomp, no network namespace (R7, R25).
- `/health` still walks the bootstrap vault and counts `case_law_master`, unauthenticated and unrated (F44, FA-corpus-001; R19).
- URI actions, including `javascript:`, `file:` and UNC targets, and the media actions listed in R20 are accepted.
- Between an operator's manual removal of raw objects and the next recount (at most `RECOUNT_INTERVAL_SECONDS` after a bound is hit), the store can refuse writes that would now fit (R18).
- A scratch directory whose worker pid has been reused by another live process waits for the age bound (R23).
