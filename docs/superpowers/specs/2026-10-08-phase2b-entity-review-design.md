# Phase 2b-A: L17.2 Entity Review Queue and confirmMerge (design)

Status: approved under the owner's standing autonomy instruction (CLAUDE.md, 2026-10-07): every design decision below is a recorded ruling, not a question.
Governing text: `docs/architecture/SIKANDER_AI_Architecture_Set_v19.txt` ("Lnnnn" = line). Phase 2a spec: `docs/superpowers/specs/2026-10-07-phase2a-matter-spine-conflict-design.md` (rulings P2-1..P2-22); this spec continues the numbering at P2-23 so the ledger stays unique.

## 1. What this builds and why

L17.2 (L6921-6964) and L18 §7 (L8398-8414) require entity resolution with "candidate and confirmed states, a human threshold, a full merge history and a reversible un-merge path". Phase 2a built the read side: `registerClient` writes one `entity_links` row per shared deterministic key (`{firmId}_{a}_{b}_{key}`, `state: "candidate"`, `disputed: false`, classification = max of the two entities), and the conflict engine reads a link as confirmed iff `state === "confirmed"`, or it is an undisputed candidate at least 30 days old (L18 §7.1), and only with `L17_2_ENABLED` on (P2-18). Nothing can yet confirm, dispute or reject a link, so every key duplicate either waits 30 days or stays an unresolved identity that sends same-role hits to review (forensic test 3).

Phase 2 part 2b is split again (P2-23):

| Part | Scope | Why separate |
| --- | --- | --- |
| **2b-A (this spec)** | The human review queue for candidate links; `confirmMerge` (link-confirm with an immutable `merge_events` row); dispute and reject; `getEntity`, `listAliases`; events `entity.candidate` and `entity.confirmed`; the engine honouring rejected links; open item O-27 (opposing-party hit label) | Emulator-testable; needs no job engine; removes the review noise 2a leaves behind. |
| 2b-B | `unmergeEntity` and the un-merge saga (L18 §7.5: one P2 job per referencing collection, dead-letter, "unmerge in progress"); `entity.unmerged`; eager staleness of checks that relied on a reverted link (P2-21); probabilistic `resolveEntity` scoring (L18 §7.2-7.3: weighted name / father's name / address / DOB / secondary contact, 0.70-0.95 band) and its evaluation set; materialising the 30-day auto-confirm (O-28); `explainConflictBasis` as its own function | Needs the P2 job engine (Phase 3) and the firm's 400-pair evaluation set (L8408). |

Work lands in Cloud Functions under `/api/d1/entity/{function}` (E-23). Entities are firm-scoped (L6963, P5).

Success: an associate opens the review queue, sees the oldest unresolved duplicate pairs within their clearance with the date each would auto-confirm, and either confirms the pair (an immutable `merge_events` row with who, when, evidence, score and a pre-merge snapshot; `entity.confirmed`) or disputes it (the 30-day auto-confirm stops); a partner settles disputes by confirming or rejecting; the next conflict check reads the new identity (P2-29: a confirmed or rejected pair no longer raises same-role review; a role-crossing key hit on a confirmed pair is FLAG); a matter cannot be opened on a check whose review resolution the new identity contradicts; every step is audited, cross-firm access is denied, and a G-4 phase-close script proves it.

## 4. Data flow: confirming a duplicate

1. `registerClient` (2a) finds an existing entity with the same CNIC and writes `entity_links` rows per key in state candidate, plus (new) `events/{firmId}_{a}_{b}_candidate` (`entity.candidate`).
2. An associate calls `listReviewQueue` → the pair, with `autoConfirmAt`.
3. `confirmMerge { linkId, note }` → transaction: permission → flag → `readPair` (404 gate) → every row of the pair must have `state "candidate"` (409 `link_not_candidate`); a disputed pair needs a partner (403 `role_not_permitted`) → note ≥ 20 → write `merge_events/{auto}` (P2-24), update every row (`state: "confirmed"`, `confirmation`, raised `classification`), `events/{mergeEventId}_confirmed`, one audit row.
4. The next `runConflictCheck` for client A (named by `clientId`) reads the link as confirmed (P2-29): the same-role hit on client B is informational NONE (forensic test 3 no longer raises review), and a role-crossing key hit on a party row carrying entity B is FLAG with `confirmed_identity`.
5. A pending check whose role-crossing review hit on that pair was resolved `different_person` is refused at `openMatter` with 409 `check_stale` (re-screen, P2-30).

Dispute: `disputeLink` sets `disputed: true` and `dispute`; the pair moves to the `disputed` view and never auto-confirms. A partner then confirms (as 3, `priorState: "disputed"`) or `rejectLink`s (`state: "rejected"`, `rejection`).

## 5. Firestore rules

- `merge_events`: `allow read: if sameFirm() && role() in ['partner', 'associate'] && cleared(resource.data.classification); allow create, update, delete: if false;`
- `entity_aliases`: `allow read: if sameFirm() && isStaff() && cleared(resource.data.classification); allow create, update, delete: if false;`
- `entity_links`, `entities`, `events`: unchanged.
Existing rules-test seed rows for `entity_aliases` and `merge_events` gain `classification: "internal"`; their assertions are unchanged.

## 6. Errors

Existing envelope `{ error: { code } }`. Codes used: `not_found` (404: missing, other-firm or above-clearance link or entity), `feature_disabled` (404: L17.2 off), `link_not_candidate` (409: confirmed or rejected), `already_disputed` (409), `note_too_short` (400), `invalid_query` (400: bad `linkId`/`entityId`/`view`, non-string note), `invalid_limit` / `invalid_cursor` (400), `role_not_permitted` (403: role table, or associate on a disputed pair), `client_denied` (403). Every deny is audited once (CallAudit).

## 8. Pre-existing finding (verified 2026-10-08, ruling P2-41)

Commit 3424355 changed `tailor` so a link counts only between the subject's own entity and the candidate's entity, but three 2a cases in `functions/test/d1.conflict.emu.test.ts` still expect FLAG for an unnamed opposing subject over a confirmed link. Run on the current tree under the emulators, they fail: "opposing party = existing client with a live matter, same CNIC, link confirmed 31 days ago → FLAG …", "a disputed 31-day-old candidate link is not auto-confirmed; a human-confirmed 1-day-old link is", "only the link on the matched key counts: a confirmed phone link does not confirm a CNIC match".

**P2-41 (ruling):** the 3424355 semantics stand: a link between two registry entities is not evidence about an unnamed party (L17.2 #15; P2-5 makes a bare key match a candidate). Plan Task 1 rewrites the three cases so they still prove what they were written to prove (31-day auto-confirm, dispute stops it, human confirmation counts at once, only the matched key's link counts) through a path that reads links: the subject is client A named by `clientId`, and the candidate is an opposing `matter_parties` row carrying entity B (the shape the 2a "adverse_history" case already seeds). (At design time an uncommitted correction of those cases along the same reading was already in the working tree; the plan keeps it if it lands and adds the linked-path cases.) Each rewritten case also asserts that the same unnamed opposing subject stays POSSIBLE_CANDIDATE_REVIEW, so no expectation is relaxed to make a test pass; the severity each asserts for the linked path is unchanged (FLAG). Cost if wrong: if the owner prefers the pre-3424355 reading, `tailor` and these cases change together.
