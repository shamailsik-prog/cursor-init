## 1. Root cause, traced from the code (main @ f3bbcc9)

`scraper/routers/quarantine.py:21-45`, `POST /quarantine/{id}/promote`, behind `require_admin_api_key`:

| Line | Code on main | Problem |
| --- | --- | --- |

| :31-33 | plain `SELECT` of the staging row; `if st:` | No lock. When the staging row is absent (or the queue row has none, e.g. a statute record) nothing is written and the route still answers `{"message": "promoted"}` (:45). |

Context that shapes the fix:
- Since F19 (#49) automatic promotion (`scraper/tasks/promotion.py`) publishes into the Annex A contract and no longer writes `case_law_master`; it writes a `quarantine_queue` row for every record it holds back (`review_source`, `low_confidence`, `blocked_source`, `unknown_source`, `citation_missing`, the Annex A reasons, `promotion_error:*`, `batch_invalid:*`).

## 2. Rulings

**Ruling 1: one transaction with an expected-state check under row locks.** Promote and reject run in one database transaction. The queue row is read `SELECT ... FOR UPDATE`; the only state either route accepts is pending (`reviewed IS FALSE AND coalesce(resolution, 'pending') = 'pending'`). For promote, the staging row is then read `FOR UPDATE` and must exist and not be promoted already, and the resolved source row is read `FOR SHARE` (a concurrent trust change waits for the decision, or the decision sees it). Two requests for one record serialise on the queue-row lock; the second sees the first one's committed state. Lock order is queue row, staging row, source row, citation advisory lock; promotion takes staging row then advisory lock and never locks a queue row, so the orders cannot cycle.

**Ruling 2: status codes.** 404 when the queue id does not exist; 422 for a malformed id, body or `Idempotency-Key`; 409 when the record is not pending (already resolved, resolved concurrently, or resolved before this fix without evidence); 409 when the record's state refuses promotion (`staging_record_missing`, `staging_already_promoted`, `source_not_promotable`, `citation_already_published`). A refusal writes nothing and leaves the record pending, so the reviewer can still reject it. Only pending is decidable: a row in the CHECK's other states (`needs_edit`, `escalated`, which nothing writes today) is also 409 `already_resolved`, failing closed rather than overriding an open escalation. Every 409 body is `{"detail": {"error": <code>, ...}}`; an `already_resolved` body names the existing decision (id, decision, reviewer, time) when there is one. A database integrity error raised by a race the checks did not foresee (the backstops in ruling 4) is rolled back and returned as 409, never 500.

**Ruling 3: a replay is identified by an `Idempotency-Key`, not by the decision type.** The design intent asks for both "a replay of the same decision is a no-op that returns the same result" and "a double promote ... 409 on the loser". Two promote requests are not necessarily one decision (two reviewers can click the same row), so the route cannot infer a replay from the decision type. A client that may retry sends an `Idempotency-Key` header (1-128 characters of `A-Z a-z 0-9 . _ : -`); it is stored on the decision. A later request on a resolved record with the same key and the same decision returns 200 with the stored result (`"replayed": true`) and writes nothing. Any other request on a resolved record is 409. Without a key, a retry is 409 and the 409 body tells the client what was decided.

**Ruling 4: stable publication identity.** The publication key is `quarantine/<quarantine id>`; the `case_law_master` row id is `uuid5(NAMESPACE_URL, "corpus-service:case_law_master:" + publication key)`, so anyone can recompute it from the queue id. The same key, id and outbox row id are recorded on the decision, on `scraper_staging.promoted_to_id` and in the response. Two database backstops make a second publication impossible even if the state check were bypassed: the master primary key (the id is deterministic) and `UNIQUE (quarantine_id)` on the decision table.

**Ruling 5: reviewer and decision evidence in an append-only table.** New table `quarantine_decisions`, one row per resolving decision: `quarantine_id` (unique), `staging_id`, `decision` (`promoted` | `rejected`), `reviewer` (required, 1-255 characters), `reviewer_auth` (`shared_admin_key`), `reason` (required, 1-2000 characters), `prior_state` and `new_state` (JSON snapshots of the queue row's `reviewed`, `resolution`, `reviewed_by`, `reviewed_at`, `reason` and the staging row's `promoted`, `promoted_to_id`, `quarantined`, `quarantine_reason`), the source evidence read at decision time (`source_id`, `source_trust_level`, `source_resolved_by`), the publication (`publication_key`, `published_table`, `published_id`, `embedding_outbox_id`; all set for `promoted`, all null for `rejected`, enforced by a CHECK), `request_key` and `decided_at`. One timestamp (`clock_timestamp()`, read once after the queue-row lock is held) is used for `decided_at`, the queue row's `reviewed_at`, the staging and master `promoted_at`. The queue row's own columns are filled too: `reviewed`, `reviewed_by`, `reviewed_at`, `resolution` (`approved` | `rejected`, the existing CHECK vocabulary) and `resolution_notes` (the reason). There is deliberately no foreign key from a decision to the queue row: `quarantine_queue.staging_id` cascades on a staging delete, and the evidence must outlive its subject. Append-only is enforced in the database: a trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` (SQLSTATE 23001), whoever runs them, so the runtime role's DML grant (default privileges, `provision-roles.sh:320-325`) cannot rewrite history.

**Ruling 6: the reviewer is asserted, and the record says so.** The audit lists "Named identity" (F47) as a dependency. The only credential is the shared admin key, which names nobody. The route therefore requires the reviewer's name in the body and stores `reviewer_auth = 'shared_admin_key'` beside it, so the evidence states exactly what it proves: the decision was made by a holder of the admin key who gave that name. F47 replaces the asserted name with an authenticated principal; the column is where it lands.

**Ruling 7: trusted-source checks use F20's vocabulary, failing closed.** `scraper/trust.py` gains `human_review_decision(trust_raw)`: `trusted` and `review` may be promoted by a human; `blocked` is refused `blocked_source`; anything else (None, a deleted or renamed source, a legacy or misspelt value) is refused `unknown_source`. Confidence is not consulted: a human review is the step FINAL_2 :896-897 sends both a low-confidence trusted record and a review-source record to. The source is resolved from the staging row by promotion's own rule (`scraper.tasks.promotion._resolve_source`: FK, stamped id, stamped name, `source_site`, never falling through), and its trust is read now, not copied from the queue row, so a source blocked after quarantine is refused. Reject has no trust check (rejecting can only remove a candidate); its decision still records the trust evidence when the staging row exists.

*Steelman against ruling 7 (strict reading).* "Trusted-source checks" could mean only `trusted` may publish. *Answer.* Then the route could never promote a review source, yet FINAL_2 (:76, :93, :897) sends every review-source record to this queue "until a human verifies", and F24's published boundary keeps `review` for exactly this path. The check refuses what F20 refuses everywhere (blocked, unknown) and re-reads trust at decision time, which is what the finding found missing ("verifying current source trust").

**Ruling 8: destination stays `case_law_master`, with the verified source.** Manual promotion writes the same table as on main, with main's field mapping, plus `promoted_at`, the deterministic id, a trimmed citation (blank becomes NULL), and `source_site` set to the resolved source's name (the source whose trust was just verified, which is the source F24's published predicate then checks), not the queue row's label (a court harvester's `SindhHighCourtPublic` rows carry the label `SindhHighCourt`). A citation already present in `case_law_master` (exact text, the table's own unique key) is refused `citation_already_published` under a per-citation advisory lock keyed by `scraper.tasks.promotion.citation_lock_key` (namespace 0x0F23), so two reviewers promoting two records with one citation serialise and the second gets 409, not a deferred unique violation at commit.

*Steelman against ruling 8.* Since F19 the authoritative corpus is Annex A; a human approval should become an audited Annex A publication. *Answer.* That is the right destination and is follow-up 1. It is not a fix of this finding: F19's publication applies `publication_decision`, which quarantines every review-source item, so publishing a human approval needs a reviewed-trust override in the publication contract (`annex_a.py`, `003_corpus_publication.sql`), and most queued records fail Annex A's own requirements (bench, canonical citation, provenance) by construction. The audit rates F23 "architectural redesign: No". F24's public routes and the existing embedding consumer both read `case_law_master`, so this destination keeps retrieval visibility and the embedding hand-off consistent with the code that exists.

**Ruling 9: the embedding outbox is `embedding_queue`, written in the same transaction.** A promote inserts one `embedding_queue` row (`table_name = 'case_law_master'`, `record_id` = the published id, `status = 'pending'`) in the decision's transaction; `UNIQUE (table_name, record_id)` makes it exactly once (`ON CONFLICT DO NOTHING` then the existing row's id). The consumer is `tasks/embeddings.py`, unchanged: it already embeds pending `case_law_master` rows. Its missing lease and recovery state are F27, its job outcome F28; this PR only writes the row and records its id on the decision.

**Ruling 10: reject is added.** `POST /quarantine/{id}/reject` (FINAL_2 :1155) takes the same body and key, resolves the record `rejected` with a decision row, and leaves the staging row as it is (quarantined, not promoted). Without it the only resolving decision is a promotion, a mistaken record can never be closed with evidence, and "a promote racing a reject" cannot be tested. It is the second half of the transition the finding asks for, not a new feature.

**Ruling 11: schema change by migration 002, and the table never exists without its triggers.** The table comes from the ORM model (`Base.metadata.create_all`, as for every application table). What the ORM cannot express, the append-only trigger function and its two triggers, lives in one new module, `scraper/quarantine_ledger.py`, and is created in the table's own schema (resolved from `'quarantine_decisions'::regclass`, like F20's probe) by two paths: an `after_create` listener on the table, so `create_all` makes the triggers in the same transaction as the table whoever runs it, and `corpus_service/migrations/002_quarantine_decisions.py`, which re-asserts them on every migrate. The migration is idempotent: a database whose function body and enabled triggers are already current is left untouched; a dropped, disabled or altered one is recreated. *Why both.* The first version had the migration alone. A table created by `create_all` as one role and migrated by another then has no triggers, and the migration role cannot add them to a table it does not own: the F20 tests build a "today's tables" legacy schema as the superuser and hand only the nine pre-F23 tables to the migration role, so migrate failed there (verified in the plan ledger), and in production a table created by a development startup would sit without its triggers until a migrate. With the listener, the table and its triggers are created together, and the migration only repairs. `scraper/migrate.py` runs migration 002 inside the existing upgrade transaction, from an explicit list (`NUMBERED_MIGRATIONS`), loaded by file path because the names start with a digit; a missing file or a module without `upgrade(conn)` stops the migration. `001_initial.py` is a placeholder and is not touched or listed. The list does not require contiguous numbers: if F28's `003_*` merges first, `002` is still listed and runs in list order; whichever PR merges second resolves a one-line conflict in that tuple. The runtime role gets DML on the new table from the migration role's default privileges in production; `tests/conftest.py` adds the table to its mirror of that grant (`ORM_TABLES`). The RED run needs no conftest change (main's schema has no such table and main's route never touches one).

**Ruling 12: bounded inputs.** `reviewer` and `reason` are trimmed; empty, over-long, or containing control, format or surrogate characters (Unicode Cc, Cf, Cs; tab, newline and carriage return are allowed in the reason) is 422 before any database work. Unknown body fields are 422 (`extra = forbid`). The path id is a UUID (422 otherwise, never a 500).

*Devil's advocate against the whole design.* (a) The reviewer name is self-asserted, so "who" is only as good as the key holder's honesty (ruling 6; residual 1). (b) Append-only binds the runtime role, not the table owner or a superuser, who can disable the trigger (residual 2). (c) A client that retries without a key gets 409 for its own successful first attempt; the 409 body names the decision so it can reconcile, but the status is not 200 (ruling 3). (d) Exact-text citation matching lets two spellings of one authority both reach `case_law_master`; that is the table's existing key and Annex A's canonical keys are the long-term answer (residual 3). (e) Court harvesters write quarantined staging rows without queue rows, so their records never reach this route; that is F21's missing workflow, not this transition (residual 4).

*Bias check.* Untested premises, and how they are tested: that the lock serialises requests rather than the test happening to run them in sequence (the race test holds the queue-row lock from another connection until both requests are waiting on it, so they are released together); that the runtime role can do everything the route needs and nothing it should not (the app runs as a DML-only role in every e2e test, and the trigger is exercised as that role); that the published row is really visible (the test reads it back through F24's public `GET /cases/{id}`).

## 5. Residual risks and follow-ups

1. **Asserted reviewer.** The shared admin key names nobody (F47). The decision records `reviewer_auth = 'shared_admin_key'`; F47 must bind decisions to an authenticated principal and scope promotion separately from trigger and export.
2. **Append-only binds the application, not the owner.** The migration role owns the table and could disable the trigger; a superuser can do anything. Off-host audit shipping is outside this finding.
3. **Exact-text citation key.** `case_law_master` deduplicates on exact text; two spellings of one authority can both be published there. The advisory lock is canonical, so they at least serialise.
4. **Court harvesters write no queue rows.** Their quarantined staging rows never reach this route (F21).
5. **Destination is the legacy table.** Follow-up: when F24's follow-up 1 moves public reads to Annex A, manual promotion should become an audited Annex A publication with a reviewed-trust override.
6. **The outbox consumer has no lease** (F27) and its job outcome is F28's; the row is written exactly once, but processing it exactly once is theirs.
7. **`GET /quarantine` `limit` is still an unbounded integer** (F24 residual 6; admin-only, not part of F23's finding).
8. **Rows resolved on main carry no evidence.** A row promoted before this fix is `reviewed = true` with no decision; it now answers 409 `already_resolved` with `decision: null`. No evidence is invented for it.

## 6. Review round (Copilot)

PR #74 at 869d041. Threads: Copilot 4305754687 (HIGH), Cursor Bugbot 4305785492 and 4305785497 (on the RED commit 747ae02), Cursor Bugbot 4305801306 (HIGH, on the Cursor Agent's 2549328).

**Finding (4305754687).** `quarantine_ledger.is_current` compared each trigger's name, function, enabled flag and `tgtype` only. A row trigger recreated `BEFORE UPDATE OR DELETE ... FOR EACH ROW WHEN (false)`, or `BEFORE UPDATE OF reason OR DELETE`, keeps all four (tgtype 27 in both cases, checked on PostgreSQL 16), so migration 002 reported "append-only trigger already current" and left a trigger that never fires, or fires for one column only: the runtime role could then rewrite or delete decisions. 4305785492 and 4305785497 restate the same gaps against the RED tests (`'A'` expected but not created; WHEN and column list not compared). 4305801306 is the Cursor Agent's own defect (below).

**Ruling R1: compare every attribute that decides behaviour, and rebuild from nothing on any difference.** The function must match its body, language (`plpgsql`), return type (`trigger`), zero arguments, kind (a plain function), not SECURITY DEFINER, no `SET` options, not strict, not set-returning, volatile. Each trigger must match the function's oid, `tgtype` (BEFORE; ROW with DELETE and UPDATE, or statement-level TRUNCATE), `tgenabled = 'A'`, `tgqual IS NULL` (no WHEN clause), `cardinality(tgattr::int2[]) = 0` (no `UPDATE OF` list), no arguments, not a constraint trigger, not deferrable or initially deferred, no transition tables, not cloned from a parent. On any difference the migration drops both triggers, drops the function `CASCADE`, creates the function and both triggers and enables them ALWAYS. It does not try to patch a drifted definition, so nothing of it survives.

*Steelman: compare `pg_get_triggerdef` and `pg_get_functiondef` text instead.* It is shorter and catches anything the renderer prints. *Answer.* Those texts are rendered from exactly the columns above, but the function name is qualified or not depending on the session's `search_path` (on PostgreSQL 16 `pg_get_triggerdef` prints `public.quarantine_decisions` but an unqualified `quarantine_decisions_append_only()`), so an exact-text check would depend on the migrate session's settings. The column comparison has no such dependency. The rendered text is still checked, independently, by the e2e test: after every repair it asserts the exact `pg_get_triggerdef` of both triggers.

**Ruling R2: the triggers are ENABLE ALWAYS (`'A'`), and only `'A'` is current.** An ordinarily enabled trigger (`'O'`) does not fire in a session whose `session_replication_role` is `replica`. A superuser can set that, and so can any role granted `SET` on the parameter (PostgreSQL 15 and later); the e2e test showed a replica-mode session updating, deleting and truncating decisions on 869d041. `'A'` fires in every mode, so the append-only rule holds in a logical-replication apply or a restore session as well. The cost: a replication subscriber of this table would refuse a replicated UPDATE or DELETE. That is correct for an append-only table, whose publisher never produces one.

**Ruling R3: the Cursor Agent's commits.** Bugbot Autofix pushed 2549328 on top of the RED commit. It had the right direction (ENABLE ALWAYS, require `'A'`, compare the WHEN clause and the column list), but it compared `tgattr = '{}'::int2vector`. `'{}'` is not valid `int2vector` input (PostgreSQL 16: `invalid input syntax for type smallint: "{}"`), so migration 002 raised on every migrate. That broke `corpus_service pytest` and `policy-e2e` in CI (step 8, the compose `store_security_e2e.sh`, which passed on 869d041), and locally its tree gave 6 failed, 31 passed, 7 errors, every one "migrate failed" (Bugbot thread 4305801306). It was reverted with a new commit (36a7559). The agent then pushed bd93eec, which re-applies its change with `''::int2vector`; that version passes its own tests (44 passed locally). It stays in the history, and e8c1d45 builds on it. That commit keeps its ENABLE ALWAYS statements, the `'A'` requirement, the WHEN and column-list checks (written with `cardinality`) and every unit case it added. It replaces its body-only function check and its `CREATE OR REPLACE` repair with R1.

*Devil's advocate.* (a) Another trigger with another name is not checked. A BEFORE trigger that sorts earlier and returns NULL stops ours from firing, but it also cancels the row operation, so nothing changes; only an owner can add one. (b) A rule or a policy on the table could redirect writes, but creating either needs ownership, the same boundary as residual 2. (c) The table owner can still disable or drop the triggers between two migrates; migrate repairs them, and residual 2 stands.

**Tests.** e2e `test_i_migrate_repairs_every_drift_and_the_triggers_fire_in_every_replication_role`, parametrized over five cases. After a first migrate the admin applies a drift: the row trigger recreated with `WHEN (false)`, with `UPDATE OF reason`, or `FOR EACH STATEMENT`; the function replaced with a no-op body; or, in the fifth case, nothing. For the three real holes the test first proves the runtime role can rewrite a decision. It also requires exactly the expected `pg_get_triggerdef` and `'A'` for both triggers, and the expected function attributes. `test_h` now expects `'A'`. The unit test checks `is_current` against 29 single-attribute drifts and the rebuild DDL.

## 7. Re-audit round 2 (M1, L1–L8)

Base: `origin/main` @ 84025e8 (PR #74 merged). The independent re-audit of PR #74 at 3fd7833 failed it at 7/10 on one MEDIUM that PR #74 introduced (M1) and listed eight LOWs (L1–L8). This round closes them on branch `claude/remediate-f23-fu`. Rulings 13–26 are new; where one supersedes part of an earlier ruling it says so. Out of scope and recorded as residuals: L9 (citation normalisation, pre-existing table semantics), L10 (staging edited in the database), L11 (decision rows forged with the runtime credential) and the INFO owner-boundary cases.

### 7.1 M1, traced from the code (84025e8)

`promote` and `reject` declared `decision: ReviewDecisionIn` as a body parameter. FastAPI 0.142.2 reads and parses a declared body before it solves any dependency: `fastapi/routing.py:441-463` (`if body_field: body_bytes = await request.body()`, then `request.json()`) runs before `solve_dependencies` (:499), which is where `require_admin_api_key` raises 401. Neither uvicorn nor the app caps a request body, and the repository ships no proxy. So an unauthenticated request was buffered whole (the auditor: +450 MB RSS for one 150 MB body, +703 MB for four 64 MB bodies) and a request that declared a large `Content-Length` and stopped sending held the connection past 90 s. Main's route had no body parameter, so FastAPI never read the body and the 401 came in 0.11 s. Ruling 12's bounds applied only after the whole body had been read.

### 7.2 Rulings

**Ruling 13: the admin key is checked before any of the body is read, by the same dependency.** The two review routes no longer declare a FastAPI body parameter. They take the `Request` and read the body themselves, inside the endpoint, which FastAPI calls only after every dependency has run. The admin check is still `Depends(require_admin_api_key)`, unchanged and listed first, so the constant-time comparison is the one function every admin route uses (nothing is copied). A route without a body field is exactly how main's route escaped the problem (`routing.py:441`: the body is read only `if body_field`). *Steelman: an ASGI middleware for `POST /quarantine/*` (the auditor's option A).* It refuses before routing, but it must either copy the key comparison or import the dependency and call it outside FastAPI, it needs a change to `scraper/main.py` (shared with open work), and it matches paths by pattern while the routes match them by the router. Option B (this ruling) keeps the guard in the route that owns the body. The endpoint's OpenAPI entry keeps the request-body schema through `openapi_extra`.

**Ruling 14: the body cap is 32 KiB (32,768 bytes), derived from ruling 12.** The longest valid fields are 255 + 2,000 = 2,255 characters. Valid JSON can spend up to 12 bytes on one character (a non-BMP character written as a `\uXXXX\uXXXX` surrogate-pair escape), so a maximal valid body carries at most 27,060 bytes of field text plus about 30 bytes of structure. *Against the auditor's 8 KiB:* a 2,000-character reason in Urdu sent by a client that escapes non-ASCII (Python's `json.dumps` default, 6 bytes per character) is 12,000 bytes, a valid request that 8 KiB would refuse; the owner's own practice writes such reasons. The cap costs 24 KiB more per request in the worst case. A `Content-Length` above the cap is answered 413 before anything is read. A body without a usable length (chunked) is read in the chunks the server delivers and answered 413 as soon as the running total passes the cap, so at most the cap plus one receive chunk is ever held. 413 detail: `{"error": "body_too_large", "max_bytes": 32768}`.

**Ruling 15: an authenticated body must arrive within 10 s, or 408.** The body read is bounded by `anyio.fail_after(10)` (the primitive `routers/export.py` already uses), measured from the start of the read, which is after authentication. Only an admin-key holder ever reaches the read, so the deadline bounds a faulty or very slow admin client, not an anonymous one. 10 s carries a maximal 32 KiB body at 26 kbit/s; an ordinary body is under 1 KiB. No database connection is held while reading: the session from `get_db` connects on its first statement, which comes after the read. 408 detail: `{"error": "body_timeout", "seconds": 10}`. *Not chosen: a server-level timeout.* uvicorn 0.54.0 has no request-body timeout (its keep-alive timeout is cancelled by every byte that arrives), and the compose command passes none.

**Ruling 16: a response sent before the body has been completely received closes the connection.** On the two review routes every such response (401 from the key check, 408, 413, a 422 for a bad id, `Idempotency-Key` or `Content-Type`) carries `Connection: close`, and uvicorn then closes the connection after sending it. Measured on uvicorn 0.54.0 with both its HTTP implementations (h11 and httptools 0.7.1): without `close`, uvicorn keeps the connection after an early response and discards the rest of the body, and since each arriving byte cancels its keep-alive timer, a client sending one byte a second held the connection for as long as it kept sending (still open after 6 s); with `close`, the connection was closed at once and the client read the 401 first. RFC 9110 §15.5.9 says a 408 SHOULD carry `close`, and §15.5.14 lets a 413 close the connection. *Devil's advocate.* A client that is still pushing a large body when the server closes may see a connection reset instead of the response (measured: a 64 MB unauthenticated body sent with httpx raised `ReadError`, where without `close` it read 401). Only a body over the cap, or a client sending without the key, can be in that position; a legitimate small body has arrived before the answer (200 of 200 small unauthenticated requests read their 401).

**Ruling 17: no other route on the app reads a body before authenticating.** Every route of `scraper.main.app` was enumerated (`fastapi.routing.iter_route_contexts`): of the admin routes, only the two review routes ever had a body field. `POST /api/start`, `POST /api/stop` and `POST /admin/sources/{name}/trigger` declare no body, so FastAPI never reads theirs, and F24's anonymous routes are all `GET` without a body. They are left as they are; a structural test fails if any route that depends on `require_admin_api_key` gains a body field, and the uvicorn test sends each admin `POST` an unauthenticated request declaring 1 GB and requires 401 within 1 s. What they share with every route of the app (a client can trickle a declared body after the response, on uvicorn's keep-alive) is a server-level property, recorded as residual 10.

**Ruling 18: the review routes render their own 422s, without the input (L4, L5).** Every validation error on the two routes, from the body (parsed with `ReviewDecisionIn.model_validate_json`) or from FastAPI's path and header validation, is answered `{"detail": [{"type", "loc", "msg"}, ...]}`: no `input`, no `ctx`; every string is made encodable (`backslashreplace` turns a lone surrogate into its escape text) and cut to 64 characters (`type`, each `loc` part) or 200 (`msg`); at most 10 errors are listed, then one entry with the count of the rest. A body that is not `application/json` (or `application/*+json`) is 422 before it is read, as FastAPI's strict content type made it before. FastAPI's own renderer echoed the whole input (a 10 MB field gave a 10,000,152-byte 422) and failed to encode a lone surrogate (500). The handler is a route class on these two routes only; F24's routes and `GET /quarantine` keep FastAPI's renderer. Amends ruling 12 (the 422 body shape).

**Ruling 19: contention errors are 409 or 503 after rollback, never 500 (L3).** After the transaction is rolled back:

| SQLSTATE | Name | Status | Detail |
| --- | --- | --- | --- |
| 40001 | serialization_failure | 409 | `{"error": "transaction_aborted", "sqlstate": "40001", "retryable": true}` |
| 40P01 | deadlock_detected | 409 | `{"error": "transaction_aborted", "sqlstate": "40P01", "retryable": true}` |
| 55P03 | lock_not_available | 503, `Retry-After: 1` | `{"error": "database_busy", "sqlstate": "55P03", "retryable": true}` |
| 57014 | query_canceled | 503, `Retry-After: 1` | `{"error": "database_busy", "sqlstate": "57014", "retryable": true}` |

Why the split: 40001 and 40P01 mean this transaction lost to a concurrent one and was aborted, a conflict with concurrent state that the client may resend at once; 55P03 and 57014 mean the server stopped waiting (a `lock_timeout`, a `statement_timeout` or a cancel), a temporary unavailability that the client should retry after the delay. This matches the public `google.rpc.Code` HTTP mapping (ABORTED to 409, UNAVAILABLE to 503), cited as persuasive convention only. Nothing was written in any of the four (the rollback), so a resend is safe, and with an `Idempotency-Key` a resend after an unknown outcome is safe too. The body carries the SQLSTATE and never the SQL or the driver's message; the log line carries the SQLSTATE only. Any other database error stays a 500 with no detail. *Steelman: all four 503.* One rule is simpler; but 409 tells the client the record was contended by a concurrent writer, so it should resend now and read the new state, while 503 tells it to back off.

**Ruling 20: an `Idempotency-Key` replays only the request it was sent with (L6).** Every decision now stores `request_fingerprint`: the SHA-256 (64 lowercase hex characters) of the canonical JSON of the validated `decision`, `reason` and `reviewer` (keys sorted, no whitespace, non-ASCII escaped). On a resolved record, a request with the stored key and the stored decision is replayed only when its fingerprint matches; a different reviewer or reason is 422 `{"error": "idempotency_key_reused"}` and writes nothing, as the IETF HTTPAPI working group's Internet-Draft "The Idempotency-Key HTTP Header Field" (draft-ietf-httpapi-idempotency-key-header) recommends for a key reused with a different payload; it is a draft, cited as convention. The same key with the other decision stays 409 `already_resolved`: that request is another operation on a resolved record, not a retry of this one (ruling 3 unchanged there). A row written before the column existed has a NULL fingerprint and is compared by recomputing the fingerprint from its stored `decision`, `reviewer` and `reason`, which is exact, because the fingerprint is defined over exactly those stored values. Supersedes ruling 3's "same key and same decision returns the stored result": the body must match too.

**Ruling 21: the column comes from a new migration 003, not from 002's repair path.** `migrations/003_quarantine_decision_fingerprint.py` adds `request_fingerprint varchar(64)` and `CHECK (request_fingerprint IS NULL OR request_fingerprint ~ '^[0-9a-f]{64}$')` (`ck_quarantine_decisions_request_fingerprint`) when either is missing, and logs "already current" otherwise; the model declares both, so `create_all` makes them on a new database. Why a new migration: 002 means "the table is append-only" and its log lines and tests say so; one numbered migration per schema change is what `scraper/migrate.py` documents ("Append later migrations in order"); and since migrate runs every listed migration on every run, there is no applied-state difference between the two choices. No other open branch adds a 003 (checked against `claude/remediate-f28-fu` and `claude/remediate-f26`). Existing rows are not backfilled: the table refuses `UPDATE` (ruling 5), and rewriting evidence to add a derived value is the opposite of append-only; ruling 20's recomputation covers them.

**Ruling 22: a reviewer name or reason must contain a visible letter or digit (L7).** After NFC normalisation, each of `reviewer` and `reason` must contain at least one character whose Unicode general category is L or N and which is not a Default_Ignorable_Code_Point. The only default-ignorable letters or digits are the Hangul fillers U+115F, U+1160, U+3164 and U+FFA0 (enumerated from Perl's Unicode 15.0.0 tables, the version Python 3.12's `unicodedata` carries); they render as nothing, so they do not count. Line and paragraph separators (categories Zl, Zp: U+2028, U+2029) are refused anywhere in either field, alongside Cc, Cf and Cs. So whitespace-only names, U+3164, U+2800 (braille blank, category So), a name of combining marks only and a name containing U+2028 are 422. The values are stored as given (trimmed), not normalised. Amends ruling 12. *Steelman: apply it to the reviewer only.* A reason with no letter or digit (".", U+2800, an emoji) records no reason a later reader can review, and the same rule costs nothing to apply.

**Ruling 23: the 11 surviving mutants are pinned by tests (L1).** One test per survivor, each written so the mutant changes its outcome: Q02 (a row main marked reviewed), Q03 (`needs_edit`, `escalated`), Q05 (two queue rows on one staging row), Q07b (two records with one citation, both seen waiting on the advisory lock, the second refused with exactly `citation_already_published`), Q08 and Q09 (ruling 24), R01 (another key on a promoted record is 409, not a replay), R02 (a padded citation is refused), R07 (the decision records the trust read at decision time). For N08 and N09, `test_i`'s drifts that recreate the row trigger now finish with `ENABLE ALWAYS`, so the `WHEN` clause or the `UPDATE OF` list is the only difference migrate can see; a new `origin_enabled` drift keeps the `'O'` case covered. Every survivor is re-run with the auditor's `mutate3.py`.

**Ruling 24: the source `FOR SHARE` lock is observable, and tested (L2).** PR #74's residual 8 and this plan's ledger said it was "not observable by a deterministic test". That was wrong. A transaction holding an uncommitted `UPDATE scraper_sources SET trust_level = 'blocked'` makes the promote wait; the wait is visible in `pg_stat_activity` (the runtime role's backend, `wait_event_type = 'Lock'`, its current query a `SELECT` on `scraper_sources`) and in `pg_locks` (that backend holds the tuple lock of a `FOR SHARE`, mode `RowShareLock`, on `scraper_sources`); after the blocking commit the promote is 409 `source_not_promotable` / `blocked_source`. The lock mode is read from `pg_locks` because `pg_stat_activity.query` is cut at `track_activity_query_size` (1,024 bytes by default), before the ORM's long column list reaches `FOR SHARE`; the first version of the test looked for that text and failed on correct code. Residual 8 is withdrawn.

**Ruling 25: hygiene (L8).** The literal U+202E and U+200B characters in `test_f23_quarantine_review_rules.py` are written as `\u202e` and `\u200b` escapes. The editing tools used for this round turned the escapes of its own new code and tests into the characters themselves (Hangul fillers, U+2800, U+2028, U+2029, combining marks, and these two in this spec); they were written back as escapes, and `test_f23_files_write_invisible_characters_as_escapes` now refuses any format, control, separator, combining, private-use or unassigned character, or blank-rendering letter or symbol, written literally in the eight F23 code and test files (RED on 84025e8's rules file: U+202E at line 198, U+200B at line 199).

**Ruling 26: the uvicorn proof runs in CI under both of uvicorn's HTTP implementations.** `requirements-test.txt` gains `uvicorn==0.54.0` (the version `tests/e2e/Dockerfile` pins) and `httptools==0.7.1`, so the guard is proven end to end under h11 and under httptools, which production's `uvicorn[standard]` selects. The test starts `python -m uvicorn scraper.main:app` as the compose `api` service does, bound to the runtime role.
