## 0. Understanding

**What the brief says.** There is no cloud project access from this session. Close everything code and CI can enforce; mark everything live NOT DEMONSTRATED. Five things: (1) a versioned manifest as the single source of truth for region, database location, per-function settings, queues and their OIDC identities, schedulers and their identities, IAM, TTL and indexes, alert policies and the Next host's time limit; (2) a CI gate that makes code and manifest agree and fails on a planted mismatch; (3) fail closed on the unsafe proxy/ingress combination and constrain the default `api` ingress; (4) a deploy preflight, a release runbook and a clean-staging promotion procedure; (5) health that reports the deploy-contract checks it can verify at runtime.

**Assumptions (mine, each recorded as a ruling below).** Terraform cannot be validated here (no provider download); the owner's stack is Firebase Functions v2 plus Firestore in `asia-south1`, the Next app on Vercel, the corpus runtime in compose; production reaches `api` through an external Application Load Balancer because that is the topology `functions/README.md` already documents for `TRUSTED_PROXY_HOPS`.

## 2. Approaches considered

**A. Terraform only (hand-written HCL), with the gate parsing it.** The usual answer. Rejected: there is no HCL parser in the Python standard library, `terraform validate` needs `terraform init` (provider download, forbidden here and credential-free CI should not need it), and Terraform cannot express what `firebase deploy` already owns (function options, task queues, schedulers, rules, indexes, TTL).

**B. A typed manifest checked by a gate, and no IaC tool.** Offline, no dependency. Rejected as the whole answer: the finding says "as code", and IAM, the database, the load balancer and alert policies are not created by `firebase deploy`. A manifest nobody can apply is documentation.

**C. (chosen) The manifest is the source of truth; the existing Firebase files carry what `firebase deploy` owns; Terraform is a generated projection for the GCP resources it does not own.**
- `infra/deploy-manifest.json` (JSON, readable by Python, Node and the tests) states the whole contract.
- `functions` code states the same function settings explicitly (no platform default left to chance); the gate makes the two agree, per field, on the built bundle, which is what the deploy tool reads.
- `firestore.indexes.json` carries the TTL policies (`fieldOverrides[].ttl`), `firebase.json` carries the database location and runtime, and both are checked against the manifest and validated with `firebase-tools`' own validator.
- `infra/terraform/*.tf` is rendered from the manifest by `infra/render_terraform.py`, committed, and byte-compared by the gate (drift is a failure). It holds only what `firebase deploy` cannot manage: service accounts, project IAM, the database, the load balancer, alert policies and the notification channel.

*Steelman for A:* the Terraform workflow is native for operators and drift against the cloud is Terraform's job. *Answer:* the rendered files are ordinary Terraform operators plan and apply; the manifest adds the property A lacks, that CI can prove code and infrastructure agree with no credentials. *Devil's advocate against C:* a generator between the manifest and the HCL is one more thing to maintain, and a mistake in the renderer is a mistake in every environment. *Answer:* the output is committed and reviewed as a diff, the renderer is small and table-driven, a structural validator and the planted-mismatch tests cover it, and `terraform validate` is the first step of the staging procedure (NOT DEMONSTRATED here). *Bias check:* I chose C partly because it is the only option I can test end to end in this session; that is a real constraint on the owner's staging, not a preference, and the runbook says so.

**D. Make the code read the manifest** (function options imported from the JSON). Rejected: it removes the possibility of disagreement by construction, but it hides every function's settings in a second file, couples the bundle to an `infra/` path, and a manifest edit would change runtime behaviour without a code review of the function. Two explicit statements plus a gate that proves them equal is the stronger control (it catches the third party that edits only one).

## 3. Rulings

**R1. Format.** C above. Reasons in section 2.

**R2. The gate has two tiers.** *Static* (Python standard library; G-0 check [20]; runs before `node_modules` exists): manifest shape, export parity with `index.ts`, queue and scheduler parity with the code, TTL and index parity, alert registry, environment profiles, `firebase.json`, rules, Next `maxDuration`, IAM lint, Terraform drift, runbook order. *Bundle* (the same script with `--bundle`, in the `gates` and `functions` CI jobs after the build): `functions/scripts/dump-endpoints.cjs` loads `functions/lib/index.js` in a fresh Node process, the way the deploy tool discovers endpoints (the `deploy.test` precedent: `setGlobalOptions` in `index.ts` runs after the imported function objects exist, so source-level tests cannot see what is deployed), and every field of every endpoint is compared with the manifest, for a named environment profile. *Reason:* the static tier is cheap and always on; only the bundle shows what the deploy tool will read.

**R3. One dedicated runtime identity, `sikander-functions`.** Every function sets `serviceAccount: "sikander-functions@"` (the CLI expands the trailing `@` to `@{project}.iam.gserviceaccount.com`, `proto.formatServiceAccount`), and `jobWorker` sets `invoker: ["sikander-functions@"]`. The CLI then grants that account the Cloud Run invoker role on the worker and the Cloud Tasks enqueuer role on its queue, and, for schedule functions, the invoker role (`fabricator.js`). The account's project roles are the least set the code needs: `roles/datastore.user` (Firestore), `roles/firebaseauth.admin` (the Admin SDK Auth calls in `p5`), `roles/logging.logWriter`, `roles/eventarc.eventReceiver` (the Firestore triggers), plus `roles/iam.serviceAccountUser` on itself (Cloud Tasks creates the OIDC token as the account that enqueues). Primitive roles (`owner`, `editor`, `viewer`) are refused by the gate. *Changes a pinned test:* `p2.boot.test.ts` pinned "no invoker on `jobWorker`" so that nobody sets `public`; it now pins the invoker to exactly the runtime account and still refuses `public`. *Why one account, not one per function:* the Admin SDK enqueues with the calling function's identity, so `api`, the sweeper, the worker and the trigger all enqueue to the same queue; one account keeps the queue's invoker list a single member. *Devil's advocate:* a single account is a larger blast radius than five. *Answer:* the roles it holds are exactly what every function needs (they all read and write Firestore), none holds anything beyond Firestore, Auth admin, task enqueue and logging, and splitting `api` (Auth admin) from the rest is a follow-up that needs the live deploy to prove the per-function roles. *Risk accepted and named:* a missing role fails at runtime, not at deploy. Mitigation: the staging procedure runs the smoke flows before promotion; NOT DEMONSTRATED.

**R4. Every function sets its limits explicitly.** Memory `256MiB` and concurrency `1` are today's effective platform values, pinned so they cannot drift; `minInstances: 0`; `maxInstances` is the new cap; timeouts are stated for every function (60 s where the platform default applied). The cap per function is a judgement, recorded with its reason in the manifest (`why.maxInstances`): `api` 20 (120 s requests at concurrency 1; a law-firm tenant count, not consumer traffic; the per-user limit is 60 a minute), `jobWorker` 10 (equal to the queue's `maxConcurrentDispatches`), the per-minute reconcilers and sweeper 1 (an overlap is wasted cost; a busy single instance answers the scheduler 429 and the next minute runs), the daily ticks 1, the Firestore triggers 10, `health` 2. *Devil's advocate:* 20 may be too low on a bad day. *Answer:* it is a cost ceiling, raised by one reviewed line in two places (the code option and the manifest); past the cap Cloud Run holds a request briefly and then refuses it with 429, which the Next forward and the consoles already treat as a failed call; an unbounded `api` is the finding's "uncontrolled cost". The numbers are not derived from production load (none is available here); that is a residual.

**R5. Ingress.**
- `api`: no silent default in a deployed bundle. A deployed bundle (production `NODE_ENV`, baked by `build.mjs`, and not the Functions emulator) refuses to start unless `SIKANDER_INGRESS_SETTINGS` is set. The manifest's `production` and `staging` profiles set `ALLOW_INTERNAL_AND_GCLB` with `TRUSTED_PROXY_HOPS=1`; the gate refuses `ALLOW_ALL` in either profile. `ALLOW_ALL` remains the default only where nothing is deployed (unit tests, the emulator, local runs), where the setting has no effect.
- `health`: `ALLOW_ALL`. It answers verdict words only (no tenant data, no values), does no IP-dependent work, and an uptime check or smoke test must reach it without the balancer. Capped at 2 instances.
- Every trigger-only function (`onJobCreated`, `onEventCreated`, `jobWorker`, both ticks, three registry triggers, both reconcilers, `jobSweeper`): `ALLOW_INTERNAL_ONLY`. Their callers are Eventarc, Cloud Tasks and Cloud Scheduler, which Cloud Run's documentation lists as internal sources when they are in the same project and use the default `run.app` URL (Google Cloud, "Restrict network endpoint ingress for Cloud Run", read 2026-10-22). They are also IAM-private (invoker is the runtime account), so no other caller could reach them; ingress is the second lock. NOT DEMONSTRATED live.
*Consumer impact:* see section 7.

**R6. Fail closed at load.** `deployConfig.ts` evaluates the environment once, when it loads, with a pure function `deployContractViolations(env, { deployed })`, and throws `DeployContractError` after logging one ERROR line, `deploy.contract_violation`, that names the codes (never values). The codes:
- `ingress_not_set`: deployed and `SIKANDER_INGRESS_SETTINGS` unset.
- `ingress_invalid`: not one of the three Cloud Functions values (this was already a throw).
- `proxy_hops_invalid`: `TRUSTED_PROXY_HOPS` set but not a non-negative integer (it silently meant 0).
- `proxy_trust_with_open_ingress`: hops > 0 and ingress `ALLOW_ALL` (the forgeable hop; was a warning).
- `gclb_ingress_without_trusted_hop`: ingress `ALLOW_INTERNAL_AND_GCLB` and hops 0 (the shared-bucket denial of service).
Because `index.ts` imports the router, which imports `deployConfig`, an unsafe environment makes the bundle fail to load: the deploy tool's discovery fails with the error text, and a revision that somehow starts never serves. *Why load-time and not per request:* it fails the deploy before anything runs, it needs no per-request cost, and the IP-dependent decision (the per-IP limit) is reachable only through `api`, which cannot start. `trustedProxyHops()` keeps returning 0 for a malformed value (its existing contract and tests); the violation is reported by the evaluator.

**R7. TTL as code.** `firestore.indexes.json` `fieldOverrides` gets `ttl: true` entries for `idempotency_keys`, `idempotency_effects`, `rate_limits`, `conflict_index_breaks` (the four documented) and `counters` (the daily-limit counters; a gap on main). They deploy with `firebase deploy --only firestore:indexes`; the `gcloud` commands leave the README. Each entry lists the three default single-field indexes, so the override does not exempt the field from indexing (Firestore's default stays; whether to exempt for write cost is a measured follow-up). `counters` is safe to put under TTL because only `dailyLimit.ts` writes an `expiresAt` into it. Explicitly *not* TTL: `mfa_disable_approvals.expiresAt` (a validity bound on an approval that is part of the MFA audit trail; retention is F42) and the job lease timestamps (nested fields). The gate scans the two server-side trees that write `expiresAt` (`functions/src`, `platform/http`) and fails on a file that is in neither the TTL writer list nor the exemption list, so a new TTL field cannot ship unclassified.

**R8. Alerts as code.** The manifest registers each alert line with its event, level, surface, emitting files and the runbook that names it. The gate checks the event string is in each emitting file and the runbook, that every dotted `*.error("...")` event in `functions/src` is registered or exempted with a reason (a new ERROR line without a decision fails), and that the runbook order holds. Terraform renders one `google_monitoring_alert_policy` with a `condition_matched_log` per Cloud Functions alert, notifying one email channel (`var.oncall_email`, no default). The Next runtime's (F18) and the corpus runtime's (F27, F28) alert lines are registered with `delivery: external`; their logs do not reach Cloud Logging from this repo's deployment, so a policy cannot be rendered for them and the manifest says who must route them (Vercel log drain; the corpus host). Alert delivery to a human is NOT DEMONSTRATED (F43).

**R9. Health.** `GET /health` keeps `{ status, region }` and adds `contract`, a map of verdict words (`ok`, `violated`, `unknown`) and nothing else: `region` (the metadata server's instance region against `asia-south1`), `database_location` (`FIREBASE_CONFIG.locationId` against `asia-south1`), `ingress` and `proxy_trust` (the R6 evaluation), `required_env` (explicit ingress setting in a deployed bundle) and `runtime_identity` (the metadata server's service account against `sikander-functions`; this also verifies the identity the queue and scheduler use, which is the same account by R3). Any `violated` answers 503 `unhealthy`; `unknown` (not on GCP, metadata unreachable, no `locationId`) does not fail the probe. The metadata probe has a 500 ms timeout and its result is cached for 5 minutes per instance, so the endpoint stays cheap. No values are returned. This is the deploy-contract part of F44 only; dependency checks (Firestore reachable) are not added.

**R10. The Next host.** The manifest records the host (`vercel`) and, per route file, the required `maxDuration`. The gate reads the literal `export const maxDuration = N` and compares: `app/api/p1/committee-brain/route.ts` 130 (F18: above `FORWARD_TIMEOUT_MS / 1000` = 125, and within the smallest plan's 300 s), `app/api/d1/documents/route.ts` 60. A route that exports `maxDuration` and is not listed fails. The Next base URL for Functions (`SIKANDER_FUNCTIONS_API_BASE_URL`) must be the balancer's https URL, never a `run.app` or `cloudfunctions.net` URL, once `api` ingress is restricted; the preflight checks a supplied Next env file for that.

**R11. Preflight, runbook, staging.** `scripts/deploy-preflight.sh` builds the bundle, runs the gate with `--bundle --profile <p> --env-file <functions/.env.PROJECT_ID>` and prints the commit and manifest digest. `docs/deploy/RELEASE_RUNBOOK.md` calls it before `terraform apply` and before `firebase deploy`, and defines the clean-staging promotion. A CI dry run runs the same script with the environment file the gate itself prints from the manifest (`--print-env`), so the path an operator takes is exercised on every PR.

**R12. Staging is a rehearsal of production.** The `staging` and `production` profiles must carry identical contract settings (the gate compares them); a difference needs a manifest change, so it is a reviewed one.

**R13. Out of scope, named.** The load-balancer front end's own security policy (Cloud Armor), VPC egress, backups (F33), retention (F42), dependency-aware health and alert delivery (F43/F44), budgets, secrets delivery for the AI gateway key (F18's note says Secret Manager; nothing in `functions/src` binds a secret, so the runtime account holds no `secretAccessor` role and the manifest records that), and per-function runtime accounts.

**The manifest** (`infra/deploy-manifest.json`, `manifestVersion` 1): `project` (region, database), `runtime`, `identities` (accounts, project roles with a reason each, who may act as whom), `functions` (13 entries: kind, region, memory, timeout, min, max, concurrency, identity, ingress, trigger details, and `why` for ingress and the instance cap), `queues`, `firestore` (TTL list with writers, exemptions, server-only collections), `alerts` (policies and exemptions), `environments` (`local`, `staging`, `production`: the env keys of the contract), `next`, `runbook`, `apis`.

**Data flow.** Manifest -> (renderer) -> `infra/terraform/*.tf`; manifest <-> `functions/src` options (gate, bundle tier); manifest <-> `firebase.json` and `firestore.indexes.json` (gate); manifest <-> alert lines, TTL writers and route files (gate); manifest `environments.<p>.env` -> `--print-env` -> `functions/.env.<project>` -> bundle dump (preflight).

**Errors.** The gate prints one `FAIL [check-id] message` line per problem and exits 1; the id is stable so a test or a reviewer can name it. The start-up refusal logs `deploy.contract_violation` once at ERROR (codes only) and throws `DeployContractError` whose message lists the codes.

## 6. NOT DEMONSTRATED (live)

- Any IAM binding, role sufficiency, the service account's creation, Cloud Tasks OIDC with the dedicated account, scheduler invocation with it.
- Any deploy: `firebase deploy`, `terraform init/validate/plan/apply`, the TTL policies becoming active, the database location of an existing project, the load balancer, the `X-Forwarded-For` shape behind it (the README's `<client>, <lb-ip>` is documented, not measured), Cloud Run ingress exemptions for Eventarc, Scheduler and Tasks beyond Google's documentation.
- A clean staging deploy and promotion; alert delivery to a person; the instance caps against real load.

## 7. Consumer impact

- **Operators must, before the next deploy:** (1) `terraform apply` stage 1 (`infra/terraform`: APIs, accounts, IAM, database import, alert policies) with `-var project_id=... -var oncall_email=...`; (2) write `functions/.env.<projectId>` from `python3 ci_gates/check_deploy_contract.py --print-env <profile>`; (3) `bash scripts/deploy-preflight.sh --profile <profile> --env-file functions/.env.<projectId>`; (4) `firebase deploy`; (5) `terraform apply` stage 2 (the balancer, after the `api` service exists); (6) set `SIKANDER_FUNCTIONS_API_BASE_URL` (Vercel) to the balancer's URL.
- **Blocks current callers:** `api` leaves `ALLOW_ALL`. Once deployed with `ALLOW_INTERNAL_AND_GCLB`, the `run.app` / `cloudfunctions.net` URL answers 403 to everyone, including the Next server and the consoles, until they use the balancer's URL. Deploying without the setting now fails instead of defaulting open. Staging first.
- **Behaviour:** an unsafe proxy/ingress combination no longer starts (was a warning). A malformed `TRUSTED_PROXY_HOPS` now fails the deploy (was 0).
- **Cost:** instance caps (R4) bound concurrency; past the cap Cloud Run holds a request briefly, then answers 429.
- **Identity:** all functions run as `sikander-functions@PROJECT_ID.iam.gserviceaccount.com`; it must exist before the deploy or the deploy fails.

## 8. Residuals

Section 6, plus: the instance caps and memory are not derived from load; one runtime account for all functions; Terraform is generated and structurally validated only; the alert filters assume the structured-log shape (`jsonPayload.message`) the README already documents; delivery for Next and corpus alert lines is external; TTL on `counters` assumes no other writer adds `expiresAt` there (the gate scans `functions/src` and `platform/http` only; Next domain code uses epoch-number fields that cannot be TTL fields); index coverage of new queries is still caught only by emulator tests that do not enforce composite indexes; `firebase.json` `functions.runtime` pins `nodejs22`, matching `engines.node` and `.nvmrc`.
