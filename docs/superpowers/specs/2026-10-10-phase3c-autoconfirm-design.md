# Phase 3c: materialising the 30-day entity auto-confirm (O-28)

Date: 2026-10-10. Status: rulings made under the owner's standing autonomy instruction (7 October 2026); pending the partner's signature with Erratum Set No. 2.

## Why

L18 §7.1 auto-confirms an undisputed deterministic-key candidate link after 30 days. Phase 2b-A computes that at read time and writes nothing (P2-28), so an auto-confirmed pair has no `merge_events` row: L17.2 #16 ("every merge has who, when, evidence, score and an un-merge path") does not hold for it, and the un-merge saga (E-43(f)) cannot reverse it. O-28 asks for a P2 job that writes the record at day 30. Phase 3b built un-merge first, as the 3a spec required (P3-1 table: "un-merge must exist first or auto-links become irreversible", L6928-6929). This slice builds the job.

## Observe: what exists

- `effectiveLinkState(row, nowMs, l17_2Enabled)` (`functions/src/d1/entity/linkState.ts`): an undisputed candidate created at least 30 days ago reads `auto_confirmed`; the conflict engine treats `confirmed` and `auto_confirmed` alike (`isConfirmedState`). A pair's state is its most unresolved row (`read.ts` precedence: unmerging, disputed, candidate, rejected, auto_confirmed, confirmed).
- `confirmMergeOp` (`functions/src/d1/entity/ops.ts`) writes the human confirmation: one `merge_events` row (`kind: "link_confirmed"`, evidence, score 0.99, `priorState`, snapshot, `reverted: false`), every link row `state: "confirmed"` with `confirmation`, and event `entity.confirmed`; it requires every row of the pair to be a candidate.
- `unmergeEntity` accepts a pair whose rows are confirmed by one unreverted `link_confirmed` event; the reversal reopens the pair as a disputed candidate, which never auto-confirms (P3-27).
- The scheduled-job primitive (`functions/src/p2/scheduled.ts`, P3-16): one run per firm per period, key `jobType:period` in PKT, `createdBy: "system"`, firm-level, classification `internal`; `SCHEDULED_JOBS` is empty; a backfill CLI exists (max 366 periods).
- Index `entity_links (firmId, state, disputed, createdAt, __name__)` exists.
- `entity_links` is in `REGISTRY_SCOPE`: every write must bump the firm's registry version in its own transaction (P3-20; the test recorder enforces it).

## Rulings

| Id | Ruling | Basis | Cost if wrong |
| --- | --- | --- | --- |
| P3-42 | **Scope.** One job type `d1.entity.autoconfirm` (not a saga), registered in the P2 registry, and the first entry of `SCHEDULED_JOBS`: period `day`, cron `20 2 * * *` (02:20 PKT, off-peak, off the hour), exported as the scheduled function `entityAutoConfirmSchedule`. | O-28; L18 §7.1; P3-16 (the primitive was built for this). | A firm's identities are materialised up to a day after day 30; the read side already treats them as confirmed in between, so no conflict result changes. |
| P3-43 | **Which pairs.** A run for firm F at time T materialises a pair when L17_2 is enabled for F and every `entity_links` row of the pair is `state: "candidate"`, `disputed: false`, has no un-merge in progress and was created at or before T − 30 days, i.e. the pair's read-time state is `auto_confirmed` by the existing rule (reuse `effectiveLinkState`; do not restate it). Candidate rows are found with the existing index (`state == "candidate"`, `disputed == false`, `createdAt <= T − 30 d`, ordered by `createdAt`, then id) and grouped by pair; each pair is then loaded whole, so a pair with any other row (a newer candidate, a disputed row, a confirmed row) is skipped. With L17_2 off for F the run does nothing and records `skipped: "feature_disabled"` in its output. | Same rule as the read side and as `confirmMerge`'s `notCandidate`, so the record never says more than the engine already believes. | A pair whose rows straddle the window (one row older than 30 days, one newer) waits until the newest row reaches 30 days; correct, since until then it reads `candidate`. Mixed pairs with an already-confirmed row are skipped: O-50. |
| P3-44 | **The record.** Per pair, one Firestore transaction that re-reads every row of the pair and the firm's flag, decides again (any change → skip, no write), bumps the registry version, and writes what `confirmMerge` writes, with these differences: `merge_events` `priorState: "auto_confirmed"`, `actorId: "system"`, `actorRole: "system"`, `autoConfirmed: true`, `autoConfirmAt` (the latest row's `createdAt` + 30 d), `confirmedAt` the run's clock, `evidence: { note: "Auto-confirmed: undisputed for 30 days (L18 §7.1)", keyValues }`; each row `state: "confirmed"` and `confirmation { by: "system", role: "system", at, note, mergeEventId, auto: true }`; event `entity.confirmed` with `auto: true` in its payload. The shared parts (snapshot, key values, event shape) come from one helper used by both `confirmMerge` and the job, so the two cannot drift. | L17.2 #16 (who, when, evidence, score, un-merge path); E-41(b) shape; un-merge needs `kind: "link_confirmed"` and nothing else. `priorState: "auto_confirmed"` (not O-28's "candidate") matches what `confirmMerge` records for the same pair state. | None to conflict results: `auto_confirmed` and `confirmed` read alike. The legal effect is intended: after the record is written a mistaken identity is reversed by a partner's un-merge, not by a late dispute (P2-28's late-dispute path closes once the record exists). |
| P3-45 | **Exactly once.** The merge event's id is deterministic: `"auto_" +` the first 32 hex characters of SHA-256(`firmId` NUL `pairId` NUL sorted link ids joined by commas), created with `tx.create`, so a retried or duplicated run cannot write a second record; an existing event means the pair is done. Pairs are processed in chunks of 50 inside `runFenced` steps (as the 3b checks job), at most 50 steps, so at most 2,500 pairs per run; when more remain the output says `more: true` and the next day's run continues. | P3-6 (Firestore effects commit exactly once), P3-29 pattern. | A firm with more than 2,500 pairs reaching day 30 on one day drains over several days; each pair still reads confirmed meanwhile. |
| P3-46 | **Audit.** One `audit_log` row per materialised pair, staged in the pair's transaction: `actorId: "system"`, `action: "entity.confirm"`, `decision: "allow"`, `reason: "auto_confirm"`, target the merge event, `onBehalfOf: null`. Skipped pairs write nothing. | E-42(i): worker-side changes are audited with actor `system`; an auto-confirmation is a firm-wide identity decision and must be findable in the trail. | One audit row per pair. |
| P3-47 | **Read side.** `getEntity` and the merge history show the system actor as recorded; no other read changes (the pending review view already excludes pairs older than 30 days, P2-31). | Nothing reads differently. | None. |
| P3-48 | **Gate and CI.** `ci_gates/gate_g4_phase3c.sh` (`npm run gate:g4:phase3c`): route coverage unchanged (21 d1, 4 jobs), boot checks, named tests (materialises a 30-day pair once with its event, audit and registry bump; skips disputed, too-young, mixed and flag-off pairs; a duplicate run writes nothing; an auto-confirmed pair can be un-merged end to end and does not auto-confirm again), functions lint, G-2; and a CI step after Phase 3b. The deploy test's region check covers the new scheduled function, and G-2's `NOT_TENANT_ENDPOINTS` lists it ("scheduler, no caller"). | Same gate discipline as 2a to 3b. | None. |
