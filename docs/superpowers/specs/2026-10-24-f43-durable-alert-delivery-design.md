## 0. Understanding

**What the brief asks.** Logs are not a delivery mechanism of record. Every critical condition writes an idempotent Firestore alert document, in the same transaction as its state change or through a fenced step, carrying severity, owner role, firm, subject reference, first and last seen, count, a state (`open`, `acknowledged`, `resolved`) and an escalation deadline, and no restricted text. The owning role acknowledges or resolves through an authenticated, P5-authorised endpoint, with an audit trail. A scheduled escalator raises severity and re-targets the next owner when a deadline passes unacknowledged, idempotently and fenced. External delivery goes through one notifier interface: an in-repo outbox and notification document plus a structured log line that the F32 manifest's log-based policy matches. Alert policies are code. Every route is exercised by fault injection under the emulator.

**Constraint.** There is no cloud access. A page reaching a real phone or inbox is NOT DEMONSTRATED. Everything code, the emulator and CI can prove is closed in the repo.

**Assumptions (mine, each recorded as a ruling).** The named operator is the on-call address the F32 Terraform already declares (`var.oncall_email`, `google_monitoring_notification_channel.oncall`). The firm administrator is the firm's founding partner, whom `onboardFirm` records in `platform_onboarding/{uid}`. The existing `notifications` collection (per-user, readable and markable by its user in `firestore.rules`) is the in-repo notification surface; nothing writes it today.

## 2. Approaches considered

**A. Keep log lines, add more log-based policies.** Cheapest. Rejected: a log line is lost with logging, carries no state, cannot be acknowledged and cannot escalate; the finding is exactly that logs are the delivery mechanism.

**B. Raise alerts by subscribing to the existing events through the P2 engine** (fan-out a `job.deadLettered` or `ai.budget.threshold_crossed` event into an alert job). Uses the engine's exactly-once `runFenced`. Rejected as the primary path: the core failure scenario is a broken Cloud Tasks dispatch, and an alert job dispatched through that same queue would never run. The alerting path must not depend on the thing it watches. It would also touch `p2/fanout.ts` subscribers (F36's lane).

**C. (chosen) A durable alert document written where the state change is written, plus a scheduled checker for conditions that have no single transaction, plus a scheduled escalator, behind one notifier interface.**
- Where a transaction already records the condition (dead letter, budget crossing, a blocked call), the alert is read and written in that same transaction: it exists if and only if the state change committed.
- Where the condition is a duration or a repetition (a job not dispatched, a queue or saga that has waited too long, spend that stays unresolved), the condition's durable state already lives on the rows (`redispatches`, `nextAttemptAt`, `unmerge.startedAt`, `leaseUntil`), and a scheduled pass derives the alert from it idempotently. If that write fails, the next pass derives it again from the same rows.
- An escalator (every minute) delivers pending notifications through the notifier and escalates open alerts whose deadline has passed, each in a fenced transaction.

*Steelman for B:* exactly-once delivery is already solved in P2, so reusing it is less new code. *Answer:* the dead-letter alert is already exactly-once under C, because it shares the dead-letter transaction, and only C keeps alerting alive when the queue is the fault. *Devil's advocate against C:* two derivation mechanisms (in-transaction and scheduled) are more surface than one, and a derived alert can lag its condition by one schedule period. *Answer:* each condition has exactly one owner of its derivation (table in section 4); the lag is one sweep (1 minute) or one check (5 minutes) against thresholds of 15 to 60 minutes. *Bias check:* C is also the design I can prove end to end under the emulator; that matches the brief's scope ruling rather than a preference.

## 3. Rulings

**R1. The alert document is the delivery mechanism of record.** Collection `ops_alerts`, document id `"a" + sha256(condition NUL firmId NUL subjectKey)[0:40]` (the `jobIdFor` pattern). One document per condition and subject. Fields: `schemaVersion`, `condition`, `firmId`, `subjectKey` (`kind:id`, e.g. `job:j3a…`, `jobType:platform.diagnostic`, `budget:2026-10:90`), `ref` (the latest concrete document path, e.g. `jobs/j3a…`, or null), `detail` (codes, ids and integers only), `baseSeverity`, `severity`, `state`, `level`, `ownerRole`, `episode`, `count` (this episode), `totalCount`, `firstSeenAt` (episode start), `lastSeenAt`, `escalateAt` (the acknowledgment deadline, or null), `escalations` (this episode's steps), `actions` (acknowledge and resolve records, last 20), `acknowledgedAt`/`acknowledgedBy`, `resolvedAt`/`resolvedBy`, `createdAt`, `updatedAt`. *Reason:* the brief's field list, with the episode and history fields that make reopening and the audit trail exact.

**R2. No restricted text.** `detail` accepts only integers and strings matching `^[A-Za-z0-9_.:-]{1,128}$`; anything else throws before any write (a programming error, never data). Subjects and refs are document ids and paths. Job payloads, matter titles, client names, notes, prompts and error messages never enter an alert, an outbox row or a notification. *Reason:* the brief's "store references only"; an alert is read by operators who are not members of the matter.

**R3. Raise semantics (dedupe).** A raise reads the alert in the caller's transaction, then writes it:
- absent: created `open`, `level` 0, `ownerRole` `operator`, `severity` the condition's, `episode` 1, `count` 1, deadline `now + ackWindow(severity)`, and one level-0 notification staged in the outbox;
- `open` or `acknowledged`: `count + 1`, `totalCount + 1`, `lastSeenAt`, latest `ref` and `detail`; severity only rises; no notification (this is the dedupe: one page per episode and level);
- `resolved`: reopened as a new episode (`episode + 1`, `count` 1, `firstSeenAt` now, level 0, fresh deadline, acknowledgment and resolution cleared) with a new level-0 notification.
*Reason:* "created once (deduped)" and "resolve closes the alert" both hold, and a condition that recurs after a human closed it is never silent.

**R4. Severity, deadlines and the owner ladder.** Severities `warning` < `high` < `critical`. Acknowledgment windows: critical 15 minutes, high 30 minutes, warning 4 hours. The ladder is `operator` (level 0) → `partner` (level 1) → `firm_admin` (level 2). *Why this order:* every condition in section 4 is first an operational fault (a queue, a store, the reconciler, a provider budget) that only the platform operator can repair, so the operator is paged first; if the operator does not acknowledge, the firm whose work is stalled is told next, through its partners, who can retry or cancel jobs, raise a budget or call the operator; if no partner acknowledges, the firm administrator, the person accountable for the firm's account, is told as critical. *Firm administrator:* the founding partner recorded by `onboardFirm` in `platform_onboarding/{uid}` (FN-1), if that user is still an active partner of the firm; otherwise every active partner, marked `fallback: "partners"` on the notification. There is no separate admin role in this codebase (firm administration is partner-only in the shared decision table), so this is the only durable record of who administers a firm.

**R5. Escalation is fenced and exactly once per step.** The escalator queries `state == "open" and escalateAt <= now` (oldest first) and, per alert, runs a transaction that re-reads it and acts only if it is still `open`, still at the level the query saw, and still past its deadline. It then sets `level + 1`, the next owner, severity one step higher (capped at critical), a new deadline `now + ackWindow(new severity)` (none after the last level), appends the step to `escalations`, and stages the notification for the new owner. A second escalator run, a concurrent run, or a run long after the deadline cannot take two steps at once: the new deadline is computed from now. The function runs with `maxInstances: 1` as well. *Reason:* "a missed deadline escalates exactly once per step"; the fence is the re-read compare, the same pattern as the sweeper's per-row re-read.

**R6. Acknowledgment and resolution (the owning role).** Four routes under `/api/platform/alerts` on the `api` router (U-1: it is the only entry point to P5 operations, so no new `onRequest`):
- `GET listAlerts` (firm; `alert.read`; optional `state`; paginated with `limit` and `cursor`): the partner worklist, newest `lastSeenAt` first, the firm's alerts only.
- `POST acknowledgeAlert {alertId}` and `POST resolveAlert {alertId}` (firm; `alert.ack`).
- `POST operatorAlertAction {alertId, action: "acknowledge" | "resolve"}` (firmless; `platformAdmin` claim, like `setPlatformAiKillSwitch`).
`alert.read` and `alert.ack` are new rows of the shared P5 table, partner only, staff only, accounts refused (the table's existing order). *Why a new table row:* an action the table does not know falls through to `allow ok` for every staff role, intern included; the row makes the routes fail closed. Owner rule: an alert at level *k* may be acted on by the owners of levels 0 to *k*: the operator always; a partner from level 1 (the partner owns it once it has escalated to the firm; at level 0 it is the operator's, and a partner gets 403 `alert_not_owner`). Another firm's alert, or none, is 404 `not_found` (no existence oracle). Acknowledge needs `open` (else 409 `alert_already_acknowledged` or `alert_resolved`); resolve needs `open` or `acknowledged` (else 409 `alert_resolved`). The transition, the `actions` entry and the call's audit row (`audit.stage`, which also stages the idempotency effect marker) commit in one transaction. No note is taken: a free-text note would put staff prose into the alert (R2); the audit trail is the actor, role, level and time.

**R7. One notifier interface.** `AlertNotifier.deliver(notification)`. Each owner change stages one outbox row `ops_alert_notifications/{alertId}_e{episode}_l{level}` (deterministic id, so a transaction retry rewrites the same row) with the targets: always `{kind: "oncall"}`, plus `{kind: "user", uid}` for the partners (level 1) or the firm administrator (level 2). For each user target the same transaction writes `notifications/{outboxId}_{uid}` (`firmId`, `userId`, `kind: "ops_alert"`, `alertId`, `condition`, `severity`, `level`, `read: false`, `readAt: null`), which the existing rule lets that user read and mark read. The escalator's delivery pass hands each `pending` outbox row to the notifier, then marks it `delivered` in a transaction that re-reads it. The production notifier writes `logger.error("ops_alert.notified", { alertId, firmId, condition, severity, level, ownerRole, episode, users })`: the F32 manifest registers it, the rendered Terraform matches it and notifies `google_monitoring_notification_channel.oncall`. Delivery is at least once: a crash between the log line and the mark re-sends one page. *Reason:* a duplicate page is safe, a lost one is the finding. Real email, SMS or pager delivery is NOT DEMONSTRATED.

**R8. Conditions, their owners of derivation and thresholds** (section 4 has the full catalogue):
- `job.dead_lettered` (high, per job): in the dead-letter transaction (worker claim at attempt 4, worker commit, sweeper query B).
- `job.dispatch_stalled` (high, per firm and job type): the sweeper. A re-dispatch that brings a row's `redispatches` to 3 or more, or that finds the row due for 15 minutes or more, is recorded; after the sweep each firm and type gets one raise. Three sweeper re-dispatches without a claim take about 3.5 minutes (30 + 60 + 120 s of backoff) and mean the queue is not delivering. *Why after the sweep and not in each row's transaction:* a broken queue stalls every job; one alert document written by hundreds of row transactions would be a hot document (about one write a second sustained) and would make the sweeper's own transactions fail during the very incident. The rows' `redispatches` and `nextAttemptAt` are the durable state; a failed raise is logged `ops_alert.raise_failed` at ERROR and derived again at the row's next re-dispatch (at most 600 s later), and the checker's `job.queue_age` covers a sweeper that is not running at all.
- `job.commit_failed` (high, per firm and job type): the worker, after a commit transaction fails, in a transaction of its own bounded to 5 s. The commit failed, so there is no transaction to share; the durable backstop is `job.queue_age` (the row stays `running` past its lease) and, at attempt 4, `job.dead_lettered`.
- `job.queue_age` (high, per firm and job type): the checker. Oldest `queued` or `failed` engine row due 15 minutes ago or more, and `running` rows whose lease expired 15 minutes ago or more.
- `saga.age` (high, per firm and saga type `entity.unmerge`): the checker. `merge_events` whose `unmerge.status` is `in_progress` and whose `unmerge.startedAt` is 60 minutes old or more. A healthy un-merge finishes in seconds to minutes.
- `ai.budget_threshold` (70: warning, 90: high; per firm, month and threshold): in the P1 commit transaction that creates `ai_budget_alerts/...`.
- `ai.kill_switch_blocked` (warning; per firm and switch scope `platform` or `firm`): in the commit transaction of a call blocked by a kill switch.
- `ai.reservation_failed` (high; per firm): in the commit transaction of a call blocked `reservation_failed` (the reservation or the attempt record failed).
- `ai.reservation_unresolved` (high; per firm): the checker. Reservations still `reserved` 10 minutes or more after their lease (the reconciler runs every minute), and every `reconcile_failed` (quarantined) reservation. This is also the durable form of `p1.usage_log_failed`, whose reservation stays held.
*Reason:* thresholds are judgements recorded here, each well above its mechanism's normal latency and well below "indefinitely"; they are constants in `alerts/model.ts`, unit-pinned.

**R9. Transaction coupling in P1 and P2.** Firestore transactions read before they write. In the worker and the sweeper the dead-letter decision is known right after the row is read and before anything is written, so the alert is read there (`willRetry`, shared with `stageFailureRow` so the two cannot disagree). In `p1/gateway.ts` `stage`, the alert reads follow the existing reads and precede the first write; `CommitArgs` gains an optional `nowMs` (the call's clock) for the alert times, defaulting to `Date.now()` (the reconciler's own `stage` call is unchanged). Gateway edits are limited to these lines because F34 edits the same file.

**R10. The checker and the escalator are two schedules.** `alertChecker` every 5 minutes (timeout 60 s, budget 40 s, at most 500 rows per query, oldest first); `alertEscalator` every minute (timeout 45 s, budget 30 s; escalation first, then delivery, so an escalation's page goes out in the same run). Both `maxInstances: 1`, internal ingress, the runtime account. Each pass is caught on its own and logged `ops_alert.pass_failed` (ERROR, registered), so a missing index on one query does not stop the others. *Reason:* escalation needs minute granularity; scanning queues every minute would read up to 2,000 rows a minute for thresholds of 15 minutes and more.

**R11. Alert policies as code.** `infra/deploy-manifest.json` registers `ops_alert.notified`, `ops_alert.raise_failed` and `ops_alert.pass_failed` (ERROR, runbook `functions/src/alerts/README.md`) and declares `alertChecker` and `alertEscalator`; `infra/terraform/alerts.tf` is re-rendered (`infra/render_terraform.py --write`); the F32 gate stays green. The existing lines (`job.deadLettered`, the P1 ERROR lines) keep their policies: the durable alert is added, not substituted.

**R12. Rules and indexes.** `ops_alerts` and `ops_alert_notifications` are server-only (`allow read, write: if false`): the worklist is read through `listAlerts`, which applies P5, so no client read rule is needed. Composite indexes: `jobs (status, nextAttemptAt)`, `merge_events (unmerge.status, unmerge.startedAt)`, `ops_alerts (state, escalateAt)`, `ops_alerts (firmId, lastSeenAt desc, __name__ desc)`, `ops_alerts (firmId, state, lastSeenAt desc, __name__ desc)`, `ops_alert_notifications (status, createdAt)`. No TTL: alerts are records of who was told and who acted (retention belongs to F42); no new `expiresAt` field, so the F32 TTL checks are unaffected.

**R13. Corpus source freshness is a follow-up.** It is not in Firestore. The exact hook: `corpus_service/scraper/tasks/job_record.py` `_alerts` (:291) and the two `logger.error("F28 source alert: ...")` sites (:125, :287) should call an alert writer for `corpus.source_stale` / `corpus.source_failing` (per source), either into this collection through a Functions endpoint the corpus service can reach or into a Postgres table the checker reads. Recorded as F43-FU1; nothing in `corpus_service` changes here.

**R14. What stays log-only, and why.** The remaining ERROR and WARN lines in section 4 are either already registered in the manifest and covered by a durable alert above (for example `p1.usage_log_failed`, durable as `ai.reservation_unresolved`), or are diagnostics without a human action (`job.lease_lost`, `event.fanout_ignored`, `*_budget_spent`). `autoconfirm.backlog_stale` (F38) and the audit-outbox lines (F11) already have durable state of their own (`backlog.alert`, `audit_dead_letter`) and registered policies; turning them into `ops_alerts` is F43-FU2.

## 5. Flows

**Dead letter.** Worker or sweeper transaction: read job → (dead letter) read alert → write job, events, audit, alert, outbox L0 → commit. After commit the existing `job.deadLettered` log line. The next escalator run delivers the L0 page.

**Broken dispatch.** Enqueue → dispatch throws → sweeper re-dispatch 1, 2, 3 (each stamps `redispatches`) → at the third, the sweep's stall set holds the row → one raise for (firm, job type) → L0 page. If the sweeper is down too: the checker raises `job.queue_age` at 15 minutes.

**Escalation.** L0 deadline passes → escalator: L1, severity +1, `notifications` for each active partner, outbox L1 → L1 deadline passes → L2, critical, the founding partner (or the partners), outbox L2 → no further step. Acknowledge at any point clears `escalateAt`; the escalator's query no longer returns it.
