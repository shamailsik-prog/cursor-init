## 2. Rulings

**R1. The lifecycle lives on the staging rows, with an append-only transition log beside them.** `scraper_staging` (case law) and `statutes_staging` (statutes) each gain `lifecycle_state` (NOT NULL, default `parsed`), `state_changed_at` (NOT NULL, default `now()`), `state_reason` and `published_id`. A new ORM table `corpus_lifecycle_transitions` records every move: `record_table`, `record_id`, `from_state`, `to_state`, `reason`, `actor` (the consumer), `job_id` (the run that moved it), `details` (JSON) and `at` (`clock_timestamp()`, so two moves in one transaction keep their order). There is no foreign key from a transition to its record: the evidence outlives a deleted staging row (F23 ruling 5's pattern). *Reason:* the brief allows columns or a transitions table; the columns make claims and per-state counts cheap and indexable, the log keeps the history of a legal record (who or what moved it, when, in which run). *Steelman for a separate `corpus_records` table:* one table for both kinds. Rejected: it duplicates the staging rows' identity, and F23's route, F19's mapping and every harvester already speak staging rows.

**R2. States and legal moves.** The vocabulary is the brief's, plus two terminal states the code needs:

| From | To |
| --- | --- |
| `discovered` | `downloaded`, `failed`, `duplicate`, `dead_letter` |
| `downloaded` | `parsed`, `failed`, `duplicate`, `dead_letter` |
| `parsed` | `normalised`, `failed`, `duplicate`, `dead_letter` |
| `normalised` | `quarantined`, `approved`, `dead_letter` |
| `quarantined` | `approved`, `rejected`, `dead_letter` |
| `approved` | `published`, `dead_letter` |
| `published` | `embedded`, `dead_letter` |
| `embedded`, `rejected`, `duplicate`, `failed`, `dead_letter` | nothing (terminal) |

- `rejected` (added): an F23 reviewer rejected the record. A reviewer's decision is not a failure, and `failed` would hide it among bad input.
- `duplicate` (added): the normaliser found an earlier record of the same source, URL and content (R6). Without it, every 12-hour court run would put the same 40 PDFs in front of a reviewer again.
- `failed`: the record's own content is unusable (R6's validation codes). Never retried.
- `dead_letter`: a consumer refused the record permanently for a reason that is not its content (a record-specific database error at publication, a source no longer trusted at publication time, a published row that vanished, a review resolved before F23 with no evidence). Needs an operator.
- `embedded` means **handed off**: an `embedding_queue` row exists for the published record (R9). The vector itself is F27's work; the report shows the queue row's own status (R11).

A row enters the lifecycle at `parsed`: every harvester discovers, downloads and parses a document inside one item step of one run, and only then is there anything durable to keep (HTML and its cleaned text, or a PDF kept in the raw store by sha256 and parsed in the F26 sandbox). A discovery or download failure is an F28 per-item failure, counted by its error code in the run's `scraper_jobs` row (`http_404`, `pdf_too_large`, ...); the next scheduled run discovers the URL again. `discovered` and `downloaded` stay in the vocabulary, with their moves, for a source that stages before it fetches (the PakistanLawSite import folder is the candidate, R-3); the reconciler counts and alerts on them like any other state. *Steelman (the brief's literal "fixture rows move discovered → ..."):* a row per discovered URL, updated as it is fetched and parsed. Rejected: two more commits per document, and a failed download would then leave a staging row, which changes what F28 pins (`count("scraper_staging") == 0` after a failed run, in four tests) for no recovery gain, since re-discovery is already the recovery. The entry point is the row's `created_at` and `job_id` (R5), not a transition row.

**R3. One guarded writer of the state.** `scraper.tasks.lifecycle.move(db, row, to_state, ...)` is the only code that assigns `lifecycle_state`: it refuses an illegal move (`IllegalTransition`, before anything is written), sets the state, `state_changed_at = now()` and `state_reason`, and adds the transition row in the caller's transaction, so the state and its log commit or roll back together. The database enforces what is cheap to enforce: a CHECK on each staging table's state vocabulary; a CHECK that a terminal-bad state (`failed`, `duplicate`, `rejected`, `dead_letter`) carries a reason; and a CHECK on the transition log that every logged `(from, to)` pair is legal (a NULL `from` is allowed only for migration 005's backfill rows). A static test fails if any other module assigns `lifecycle_state`. *Not chosen: a row trigger comparing OLD and NEW states.* It is the stronger guard, but it adds a trigger function whose drift migrate must detect and repair (F23 needed rulings R1-R3 for exactly that), and F23's route and F19/F20's tests update staging rows without touching the state, which the trigger would have to allow anyway.

**R4. Four registered consumers, claiming one row per transaction with `FOR UPDATE SKIP LOCKED`.**

| Beat entry | Task | Every | Moves |
| --- | --- | --- | --- |
| `normalise-corpus` | `scraper.tasks.corpus_pipeline.normalise_corpus` | 300 s | `parsed` → `normalised` / `failed` / `duplicate` |
| `promote-corpus` | `scraper.tasks.corpus_pipeline.promote_corpus` | 300 s | `normalised` → `quarantined` / `approved` (the review gate, R7) |
| `publish-corpus` | `scraper.tasks.corpus_pipeline.publish_corpus` | 300 s | F23 decisions: `quarantined` → `approved` → `published` → `embedded`, or → `rejected` (R10); then `approved` → `published` → `embedded` (R8) |
| `reconcile-corpus` | `scraper.tasks.corpus_pipeline.reconcile_corpus` | 3600 s | repairs and alerts (R11) |

Each tick opens one session and loops at most `BATCH` times (normalise 200, promote 100, publish 100): one transaction per row, whose first statement claims the oldest row in the consumer's state with `SELECT ... ORDER BY created_at, id LIMIT 1 FOR UPDATE SKIP LOCKED`, excluding rows this tick already tried. Two workers never take the same row: the second skips the first's locked row, and the WHERE clause is re-checked on the locked version, so a row moved since the scan is not returned. A row locked by anything else (a reviewer's transaction, a hung worker) is skipped, not waited on, so one stuck row cannot stall a tick. Every move is idempotent under retry: a retried tick finds the row in its new state and does not claim it again. *Reason:* the brief's "bounded batches, transactionally, SKIP LOCKED, never double-processed, idempotent". *Steelman for F27's durable lease (claim, commit, work, fenced write):* it survives a hung worker without a held lock. Rejected for these moves: each is local to the database and fits in one transaction, so the row lock is the claim and a crash rolls the whole move back (R15); a lease only pays for itself around work outside the database, which is why F27 needs it and this does not.

Failures inside a row's transaction follow promotion's existing classification (`is_transient_db_error`, `is_record_specific_db_error`): a transient or systemic failure leaves the row in its state, counted `failed` for the tick, and after `SYSTEMIC_FAILURE_LIMIT` (3) consecutive systemic failures with the same SQLSTATE or class the tick stops early; a record-specific failure (SQLSTATE class 22 or 23) is settled in a fresh transaction: the gate keeps F19's quarantine `promotion_error:<Class>` / `batch_invalid:<code>`, the normaliser and the publisher move the row to `dead_letter` with `<consumer>_error:<SQLSTATE>`. An interruption (F28's `INTERRUPTIONS`: Celery's soft time limit, `asyncio.CancelledError`) is re-raised before any `except Exception` (F28 R23), in the new consumers and now also in `promote_staging_records`' per-record handler, whose bare `except Exception` swallowed `SoftTimeLimitExceeded` (it was harmless only because nothing scheduled it).

**R5. Every tick and every harvested row names its run.** A consumer tick that claimed a row, or failed, writes one `scraper_jobs` row (F28 R13's rule for embedding batches: an idle tick writes none, 288 rows a day of nothing), with `source_site = 'corpus_lifecycle'`, `job_type` `normalise` / `promote` / `publish` / `reconcile`, its counts and a `result_summary`; the reconcile tick always writes one, because its summary is the hourly report. The tick's job id is drawn before the first claim and stamped on every transition it writes. A tick that tried rows and moved none raises `outcomes.BatchFailed` after recording (F28 R13's rule), so Celery records FAILURE. The harvest side finally fills the existing `scraper_staging.job_id` / `statutes_staging.job_id` columns: `run_source` binds its F28 job id for the harvester (`lifecycle.bind_run_job`), as it already binds the tally. **Lane note:** `scraper_jobs.ck_jobs_type_values` gains the four job types (model and migration 005). It is outside the brief's model lane (staging and master tables); no open PR touches that table (F27 changes `embedding_queue` only), and the alternative, re-using `incremental` or `embed`, would mix lifecycle ticks into F28's per-source `no_progress` and `stale` queries and the embed records F27 reads.

**R6. Normalisation is validation, identity and dedup; it invents nothing.** For a case row: the text must contain a letter or digit (else `failed`, `empty_text`); `content_hash = sha256(raw_text)` and `source_url_hash = sha256(source_url)` when absent. For a statute row: an act name, a section number of at most 100 characters (the `statutes_master` column) and a section text with a letter or digit (else `failed`: `act_name_missing`, `section_number_missing`, `section_number_too_long`, `short_name_too_long`, `empty_text`); `act_hash = sha256(act name, section number, text)`. Then dedup: a row whose source (its `source_id`, else its `source_site` label), URL hash and content hash (statutes: act hash) match an earlier row that is not itself a duplicate becomes `duplicate` (`duplicate_of:<id>`), under a transaction advisory lock on that key so two workers cannot both keep one document. Otherwise the row is `normalised` (`normalised = true`, `normalised_at`). A harvester's pre-gate quarantine label (`quarantined = true` with no `quarantine_queue` row: the six court harvesters on main, and any row an un-upgraded worker writes during a deploy) is cleared here and recorded in the transition's details, because the review gate, not the harvester, decides quarantine. *Not done:* extracting a citation, bench, court or date from a court PDF's text. The first citation in a judgment's text is usually a precedent it cites, not its own; publishing it as the record's citation would mis-attribute authority. F19 D12 ("courts, judges, bench size and decision date are not invented") applies. Citation-free court rows therefore go to review (`citation_missing` or `review_source`), where F23 allows a reviewer to publish a citation-free record.

**R7. One review gate for cases and statutes, with two documented differences.** The gate is F20's `publication_decision` (trusted with confidence ≥ 0.5 promotes; `review`, `blocked`, unknown, low confidence quarantine with that reason) and a `quarantine_queue` row for every record it holds back, for both kinds.
- *Cases:* exactly `promote_staging_records`' existing decision (`_decide`: F22's citation check, F20's trust, F19's Annex A publication under the per-citation lock), unchanged. Annex A promoted (`promoted`, `updated`, `attached`) is `approved`; anything Annex A quarantines (`missing_bench`, `citation_not_canonical`, ...) is `quarantined` with its reason, as today.
- *Statutes:* the same `publication_decision` and the same source resolution (`_resolve_source`); a held-back statute gets a `quarantine_queue` row with `statutes_staging_id` (the column exists for this). **Difference 1:** a statute's identity check is act + section (R6), not a citation. **Difference 2:** a statute is not published into Annex A: harvested statute text is current text only, which B-5 stores at version confidence 0.5 and F05 ruling 4 makes the authority reader ignore, so it would add nothing the reader uses; Annex A statute histories come from curated batches (`publication/cli.py`). **Difference 3:** F23's promote route requires a case staging row (`staging_record_missing` otherwise), so a reviewer can reject a quarantined statute but not publish it; human statute promotion is follow-up 1. On main no statute was ever reviewed: the direct routes published trusted sources' statutes unreviewed and skipped every other source.

**R8. Publication is the retrieval projection plus the embedding outbox, in one transaction.** `scraper.publication.retrieval` writes the published record into the store that search and the embedder read today, then the outbox row:
- *case:* under F23's per-citation advisory lock (namespace `0x0F23`, key `citation_lock_key`), so a reviewer's promote and this projection of one citation serialise; an existing `case_law_master` row with that citation is attached (its id becomes the record's `published_id`, nothing is rewritten); otherwise a row is inserted with a deterministic id `uuid5(NAMESPACE_URL, "corpus-service:case_law_master:staging/<staging id>")` (F23 uses `quarantine/<queue id>`, so the two never collide), `is_promoted = true`, F23's field mapping plus provenance (`source_site` = the resolved source's name, which is what F24's published predicate checks; `source_url`; `source_file_path` = the kept PDF; `confidence_score`), and the year only inside the table's CHECK range;
- *statute:* under a per-section advisory lock (namespace `0x0F21`); an existing `statutes_master` row with the same `(short_name, section_number)` (the table's unique key), or, without a short name, the same source, act name and section, is attached; otherwise a row is inserted with a deterministic id from that natural key. `statutes_staging.promoted`, `promoted_at` and `promoted_to_id` are set here (cases keep F19's meaning: Annex A promoted at the gate).
- Before writing, the source is resolved again and read `FOR SHARE` (F23 ruling 1's pattern), and `publication_decision` must still promote; a source blocked or no longer trusted since the gate sends the row to `dead_letter` (`source_not_promotable:<reason>`), never into the retrieval store.

*Steelman against R8 (F19 ruling 10 and B-3):* "Annex A replaces the master tables; F19 removed promotion's `case_law_master` write; writing it again builds two sources of truth." *Answer:* the gate still writes none (F19's tests that assert an empty `case_law_master` after `promote_staging_records` pass unchanged); the projection is a separate, later move, taken only for records Annex A promoted (cases) or the gate approved (statutes). Until F24 follow-up 1 repoints public reads at Annex A and F27 follow-up embeds Annex A, the master tables are the only store search reads (F24 ruling 1) and the only one the embedder reads (F27 R9: any other table is `unknown_table`). F23 ruling 8 kept its destination there for exactly that reason. Without the projection an approved record stays invisible to search and unembedded, which is the audit's failure scenario word for word ("search/retrieval sees no reviewed published update"). The projection is one module, so the repoint can drop it in one place. *Devil's advocate:* (a) an Annex A `updated` judgment (new trusted text for a published citation) is attached in the retrieval store, not rewritten, so search keeps the first text (R-5); (b) a changed statute text is attached likewise, recorded `content_changed` in the transition, never silently overwritten under a completed embedding (R-5); (c) re-reading trust at publication can strand an Annex A-promoted judgment in `dead_letter` if its source is blocked between the two ticks; that is the fail-closed direction.

**R9. `embedded` hands off through F23's outbox insert, and nothing else.** `retrieval.enqueue_embedding` is F23's `_enqueue_embedding` statement (`INSERT ... ON CONFLICT ON CONSTRAINT uq_embedding_table_record DO NOTHING`, then the existing row's id): `table_name` `case_law_master` or `statutes_master`, the two F27 embeds (F27 R9), `status = 'pending'`. It sets no F27 column, so it holds under main's `embedding_queue` and under PR #87's (its lease and operation columns are nullable or defaulted, and its CHECKs accept a plain `pending` row; checked against `origin/claude/remediate-f27` @ 6cb440a). `embeddings.py` is not edited.

**R10. F23 decisions move the lifecycle; the route is not edited.** F23's promote is one transaction that writes `case_law_master`, the outbox row, `scraper_staging.promoted` and a `quarantine_decisions` row; its reject resolves the queue row. The publish tick (and the reconciler) claim `quarantined` rows that have since been decided (`SKIP LOCKED`) and record what F23 did: a `promoted` decision moves the row `quarantined` → `approved` (decision id, reviewer) → `published` (`published_id` = the decision's `published_id`) → `embedded` (the decision's outbox id; re-enqueued through R9 if that row is gone). A record whose queue rows are all resolved with no promoted decision is `rejected` (`review_rejected`, decision id). A queue row marked reviewed before F23 with no decision (F23 residual 8) moves the record to `dead_letter` (`review_resolved_without_evidence`): no evidence is invented, and an operator sees it. Lock order stays acyclic: F23 takes queue row, staging row, source, citation lock; the sync takes only the staging row and reads the rest.

**R11. The completion boundary: a per-source report, stalled-row alerts on F28's line, and a reconciler.** `scraper.tasks.reconcile.lifecycle_report()` returns, per source (the resolved source name, else the row's label), per table and per state: the count and, for every non-terminal state, the oldest `state_changed_at`; for `embedded` rows, the count by their `embedding_queue` status. Each reconcile tick logs every stalled group at ERROR on F28's corpus alert line, `F28 source alert: <source> stalled: <n> <table> rows in <state> for more than <h> h (oldest since <iso>)`, keeps the alerts and the report in its `scraper_jobs` summary, and an operator can print the report with `python -m scraper.tasks.reconcile report`. Thresholds: 6 hours for a machine state (`discovered` to `normalised`, `approved`, `published`: twelve 5-minute ticks after a full backlog drains), 7 days for `quarantined` (a human review backlog). Repairs: a `published` row without an outbox row is enqueued (R9) and moved to `embedded`, or to `dead_letter` (`published_record_missing`) if its retrieval row is gone; a `quarantined` row with no review-queue row at all (nothing a reviewer can see) goes to `dead_letter` (`quarantined_without_review_row`); decided rows are synced (R10). No new alert channel.

**R12. No source task writes a master table.** PakistanCode and NationalAssembly stage into `statutes_staging` (with the source stamp, job id, provenance, NationalAssembly's kept PDF in `raw_pdf_path`, confidence 0.85, the default `statutes_master` gave the rows these routes wrote on main) and their routes become `staging`. The six court harvesters stop setting the quarantine label. The `direct` route kind stays in the dispatcher with its trusted-only check (F20 test_k pins that a `direct` route fails closed), but no route uses it. Gate: `tests/test_f21_corpus_lifecycle_rules.py` fails if any route is `direct`, if any module under `scraper/tasks/` other than the reviewed updaters (`embeddings`, `cross_reference`) touches a master table for writing, or if any module outside `scraper/publication/retrieval.py` and the F23 route writes one, reusing F20's AST scanner (`tests/test_trust_policy.py`), with mutants that put a write back into a harvester.

**R13. Migration 005, independent of 004.** `migrations/005_corpus_lifecycle.py` (listed after 003 in `NUMBERED_MIGRATIONS`) reads the catalog and adds only what is missing: the four columns, their CHECKs and the claim index on each staging table, and the extended job-type CHECK. When it adds `lifecycle_state` to a table, it backfills that table's existing rows once, from their flags, logging each with a `from_state = NULL` transition (actor `migration_005`, the legacy flags in details):

| Legacy row | State |
| --- | --- |
| `promoted` with an F23 `promoted` decision | `embedded` (F23 wrote the outbox row) |
| `promoted`, its `promoted_to_id` is a `case_law_master` row with an outbox row | `embedded` |
| `promoted`, its `promoted_to_id` is a `case_law_master` row without one | `published` (the reconciler enqueues it) |
| `promoted` otherwise (F19's Annex A judgment id) | `approved` (the publish tick projects it) |
| `quarantined` with a review-queue row | `quarantined` (the sync moves it if decided) |
| `quarantined` with no review-queue row | the label is cleared; `normalised` if `normalised`, else `parsed` |
| `normalised` | `normalised` |
| otherwise | `parsed` |

`state_changed_at` is set to the row's `created_at` for `parsed` and `normalised` (they have waited that long) and `updated_at` otherwise. A current database (a fresh one, or one migrated before) gets no DDL and no backfill, so the migration never needs ownership of a table it does not change (F27 R14's rule). It does not read or write `embedding_queue`'s F27 columns, and does not depend on 004.

**R14. Consumer impact at deploy.** Existing staging rows enter the lifecycle by R13's table. The legacy backlog then drains at the tick rates above; expect `stalled` alerts for each source's legacy rows until it has. Re-staged court duplicates become `duplicate`, so a reviewer sees each document once. Statutes already in `statutes_master` stay; the next PakistanCode run's rows attach to them (no unique violation any more) and are enqueued for embedding once.

**R15. Crash recovery.** The claim is the row lock, taken in the transaction that makes the move, so a worker killed mid-move takes its uncommitted writes with it (Postgres rolls back when the connection closes) and the row is claimable again at its previous state; the next tick of any worker completes the move exactly once. A hung (not dead) worker keeps its lock until Celery's hard time limit (3600 s) kills its child; other workers skip that row meanwhile, and it shows in the report as stalled. The reconciler handles what crosses components (F23 decisions, outbox rows) and what no consumer can move.

**R16. Not weakened.** F23's gate: the route, its checks, its lock order and its evidence are untouched; this change only adds records to its queue (statutes, and court records that never reached it). ## 4. Residual risks and follow-ups

- **R-1. Human promotion of a statute** has no route (F23's promote needs a case staging row); a quarantined statute can only be rejected. Follow-up 1: an F23-style statute decision.
- **R-2. Two published stores.** Approved records reach Annex A (cases, from the gate) and the retrieval tables (R8). They converge when F24 follow-up 1 repoints reads and F27's follow-up embeds Annex A; until then the retrieval projection is the bridge.
- **R-3. PakistanLawSite import folder** still copies files without staging them (`pakistanlawsite.py`); it writes no master table, so it is not a direct writer, but its imports are not in the lifecycle. Follow-up 2: stage imports at `downloaded`.
- **R-4. No citation or bench extraction for court PDFs** (R6); their records need a reviewer or a curated batch to reach Annex A.
- **R-5. Changed content of an already published record** is attached, not rewritten (R8 devil's advocate a, b): the retrieval store keeps the first text and its embedding. Re-publication with re-embedding needs F27's requeue semantics. Follow-up 3.
- **R-6. Staging growth.** Duplicates are terminal but kept; retention is out of scope.
- **R-7. A hung worker** holds its row until the hard time limit (R15).
