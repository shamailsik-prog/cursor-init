## 1. Reproduction on origin/main (1f0cc27)

Every probe ran in a clean extraction of `origin/main` (`git archive`, no `node_modules`). The full log is the builder's evidence file; the results that decide the design are these.

**Toolchains.** Every CI job uses `actions/setup-node` with `node-version: "22"` and nothing pins npm. Today that resolves to Node 22.23.3, which bundles npm 10.9.9 (the v2 auditor's "Node 22.23.3"). Node 24.22.0, the line eve@0.56.0 requires (`engines.node >=24`, F48), bundles npm 11.19.1. The repository had no `packageManager`, no `devEngines`, no `engines.npm`, no `.npmrc`; `.nvmrc` says 22.

**Real frozen installs on CI's npm line (npm 10.9.7):** root `npm ci` exit 0 ("added 1488 packages"); `functions/` `npm ci` exit 0 ("added 580 packages").

**`npm ci --dry-run --ignore-scripts` (npm's own lockfile validator, no install) by npm version:**

That is the audit's message ("the package.json eve undici@8.11.2 override is missing from package-lock.json"). **F39 reproduces under npm >= 11.2.0.** The v2 re-audit could not reproduce it because it ran npm 9.2.0, and CI passes because Node 22 ships npm 10.9.x. The audit's onboarding most likely ran Node 24 (eve requires it), and so npm 11.

**Lockfile drift** (`npm install --package-lock-only --ignore-scripts`, then compare): with npm 10.9.7 the root lock gains only six `inBundle` entries (the bundled dependencies of the optional `@tailwindcss/oxide-wasm32-wasi` package; 66 lines, no version or tree change) and `functions/package-lock.json` is byte-identical. With npm 11.21.1 the root lock also gains `node_modules/@ai-sdk/provider-utils/node_modules/undici` at 8.11.2.

## 2. Root cause

- `package.json` declares `"overrides": { "eve": { "undici": "8.11.2" } }` (added in eb69045, #5): eve@0.56.0 pins `undici` 8.9.0 exactly, and the override moves eve's copy to 8.11.2 for GHSA-rfgv-xxqx-mfg5 and GHSA-w293-vg96-wgc3 (`docs/audits/known-advisories.md`).
- npm never writes `overrides` into `package-lock.json` (`@npmcli/arborist/lib/shrinkwrap.js`, `pkgMetaKeys`: the lock's root entry carries the dependency maps, engines, os, cpu, bin, workspaces and similar, never overrides). A lock reflects an override only through the tree npm resolves. Whether a lock "contains" the override therefore depends on how the resolver applies it.
- eve also declares `ai` (^7.0.93) as a peer dependency. npm <= 11.1 applies eve's override set to eve's own `undici` edge only. npm >= 11.2 carries it across that peer edge into `ai -> @ai-sdk/provider-utils -> undici` (declared `^7.29.0`) and forces 8.11.2 there too, so its ideal tree has one more `undici@8.11.2` node than the npm-10 lock: "Missing: undici@8.11.2 from lock file".
- The converse also fails: a lock regenerated by npm 11.21.1 is rejected by npm 10.9.7 and 9.2.0 ("Invalid: lock file's undici@7.29.1 does not satisfy undici@7.30.1"). With that override, **no single lockfile satisfies both npm 10 and npm >= 11.2.** Nothing pinned npm, so which side a machine landed on depended on its Node version.
- Second consequence, not in the audit: on npm >= 11.2 the override silently moves a production dependency of the AI SDK (`@ai-sdk/provider-utils`, used by the P1 gateway's `ai` package) from undici 7 to undici 8, a major version its own manifest does not accept. The override's documented intent is "eve's copy ... the same major".

So the defect is in the manifest/lock pair, compounded by an unpinned package manager; the lockfile alone cannot be repaired.

## 3. Design rulings

### Ruling 1: key the override on the version it exists to replace; regenerate the lock with npm

`"overrides": { "eve": { "undici@8.9.0": "8.11.2" } }`. A key with a version applies only to edges whose requested range intersects it (`@npmcli/arborist` override sets match `name@keySpec` against the edge's spec). eve's edge (`8.9.0`) matches; `@ai-sdk/provider-utils`'s (`^7.29.0`) does not, so the npm >= 11.2 peer-edge leak no longer reaches it, and npm 10 behaves exactly as before. The lock is regenerated with `npx -y npm@10.9.9 install --package-lock-only --ignore-scripts` (the pinned version, ruling 2); it is never hand-edited.

Measured on the repaired pair: the resolved tree is identical to main's at every path (eve's undici 8.11.2, node-gyp's undici 8.11.2, root undici 7.29.1; no entry of main's lock changes; the lock gains only the six bundled entries npm 10 and npm 11 both write, and a second regeneration is byte-identical). One install-time effect follows from those bundled entries: on linux-x64 a clean `npm ci` extracts 1,523 package directories instead of main's 1,527. The four no longer extracted are `@emnapi/core`, `@emnapi/wasi-threads`, `@napi-rs/wasm-runtime` and `@tybys/wasm-util`, optional dev-only helpers whose only users are the wasm32 bindings (`@tailwindcss/oxide-wasm32-wasi`, `@unrs/resolver-binding-wasm32-wasi`), which are not installed on x64 either way; now that the Tailwind wasm binding's own copies are recorded as bundled, npm prunes them with the platform-skipped bindings. Every package present in both installs has the same version. `npm ci --dry-run` passes under npm 9.2.0, 10.8.2, 10.9.7, 10.9.9, 11.0.0, 11.1.0, 11.2.0, 11.19.1, 11.21.1 and 12.2.0, whether npm 10.9 or npm 11.21 regenerated the lock.

Alternatives rejected:
- *Keep the override and only pin npm 10.* CI stays green, but the lock stays valid for one npm major only and moves the AI SDK onto undici 8 for anyone whose npm ignores the pin (npm < 10.9 does not read `devEngines`, and `--force` bypasses it). The pin should guard reproducibility, not hide a manifest that two resolvers read differently.
- *Regenerate the lock with npm 11.* It then fails on CI's npm 10 (section 2).
- *A top-level `"undici@8.9.0"` key.* It works too, but drops eve's scope: a future direct dependency on undici 8.9.0 would be overridden silently. The eve-scoped key changes nothing beyond what main intended.
- *A range key such as `"undici@<8.10.2"`.* `^7.29.0` intersects it, so the npm >= 11.2 leak returns.

The exact key stops applying when eve changes its undici pin. That is intended (`known-advisories.md`: remove the override once eve pins >= 8.10.2): any eve upgrade changes the lock and goes through review and the dependency-audit gate, which catches a vulnerable undici. `docs/audits/known-advisories.md` records the keyed form and why.

### Ruling 2: pin npm to the version line CI uses

Both manifests gain:

```json
"packageManager": "npm@10.9.9",
"devEngines": { "packageManager": { "name": "npm", "version": "~10.9.0", "onFail": "error" } }
```

- **`packageManager`** names the reference build: npm 10.9.9, what `setup-node` "22" installs today. Corepack and dependency bots read it.
- **`devEngines.packageManager`** is the enforced pin. npm >= 10.9.0 checks it on `install`, `ci`, `update`, `audit` and `run` (npm 11 also on `exec`) and refuses an npm outside `~10.9.0` (`>=10.9.0 <10.10.0`) with `EBADDEVENGINES` before it resolves anything. Measured: npm 10.9.7 and 10.9.9 pass; npm 11.19.1 and 12.2.0 fail with `EBADDEVENGINES ... Invalid semver version "~10.9.0" does not match "11.19.1" for "packageManager"`; npm 9.2.0 and 10.8.2 do not know the field and ignore it.
- **A patch range, not an exact version.** CI's npm is whatever Node 22's latest patch bundles (10.9.7 in March, 10.9.9 now). An exact pin would break CI on the next Node 22 patch, or need an npm install step in every job. Within 10.9.x the resolver is stable; the hazard F39 shows is between minors and majors (11.1 vs 11.2). A minor or major move (npm 10.10, npm 11) is refused until someone bumps the pin in a reviewed change.
- **Not `engines` + `engine-strict`.** `engine-strict` applies to every dependency's `engines`, and eve@0.56.0 declares `node >=24` (F48), so every Node 22 install would fail. Root `engines` is also written into the lock's root entry. `devEngines` is the field for the project's own toolchain.
- **Node is not pinned here.** `.nvmrc` (22) and `functions` `engines.node` already state it; splitting eve's Node 24 task from the Node 22 toolchain is F48's correction.
- **Effect on Node 24 users (eve).** Node 24's bundled npm 11.19.1 is refused at this root for `ci`, `install`, `run` and `exec`/`npx` alike (measured: `npm run eve:info` and `npx eve` both stop with `EBADDEVENGINES`). Two routes work: `corepack npm <command>` (corepack reads `packageManager` and runs npm 10.9.9; measured with corepack 0.34.6), or switching that Node 24 install to npm 10.9 with `npm install -g npm@10.9.9` (a global install is not checked against a project's `devEngines`; measured with npm 11.19.1). The eve binary itself, `./node_modules/.bin/eve`, involves no npm. The README says so. When F48 moves the repository to Node 24, the pin moves to npm 11 in the same reviewed change; the e2e test shows the repaired lock is already valid under npm 11.
- **Effect on deploy builders.** A builder that installs with npm >= 11 (for example a Node 24 image) now stops with `EBADDEVENGINES` instead of resolving a different tree. That is the point of the pin; see residual 3.

### Ruling 3: a frozen-install guard, static in G-0 and dynamic in CI

`ci_gates/check_lockfiles.py [--root DIR] [--npm-ci] [--npm CMD]`. It finds every `package.json` and lockfile under the root (skipping `node_modules`, `.git`, `.next`, `.stryker-tmp`, `.eve`, `.vercel`, `.turbo` and `fixtures` directories, and any nested repository or worktree, that is a directory holding its own `.git`, such as `.claude/worktrees/*`) and fails closed.

Static checks (G-0 check [18], offline, milliseconds):
1. The root has a `package.json` and a lockfile, whatever it declares (ruling R3b). Every `package.json` that declares dependencies or overrides has a lockfile beside it, and every lockfile has a `package.json` beside it. A directory holding both `npm-shrinkwrap.json` and `package-lock.json` fails, and the shrinkwrap is the one checked (ruling R3a). A `yarn.lock`, `pnpm-lock.yaml`, `bun.lock` or `bun.lockb` fails (the pinned package manager is npm).
2. Each lockfile is `lockfileVersion` 3 with a `packages` map and a root entry (`packages[""]`).
3. The root entry equals the manifest for every field npm copies into it: `name`, `version`, `dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies`, `peerDependenciesMeta`, `bundleDependencies` (or `bundledDependencies`), `engines`, `os`, `cpu`, `workspaces` (an empty object or list counts as absent). This catches what `npm ci` tolerates: a range edited in `package.json` that the locked version still satisfies (seeded: `zod` `4.5.4` to `^4.5.4`, `npm ci` exit 0).
4. Every direct dependency has an entry at `node_modules/<name>` in the lock.
5. Every manifest with a lockfile declares the pin of ruling 2: `packageManager` `npm@X.Y.Z` and `devEngines.packageManager` `{ name: "npm", version: "~X.Y.0" or "X.Y.Z", onFail: "error" }`, with the `packageManager` version inside the range, and all manifests declare the same pin.
6. No install surface runs a non-frozen npm install: `.github/workflows/*.yml`/`*.yaml`, `.cursor/environment.json`, `.claude/hooks/*` and every manifest's `scripts`. A violation is an `npm` command whose subcommand is `install` or one of its aliases (`i`, `add`, `in`, `ins`, `inst`, `insta`, `instal`, `isnt`, `isnta`, `isntal`, `isntall`), `install-test`/`it`, `update` (`up`, `upgrade`, `udpate`), `uninstall` (`un`, `unlink`, `remove`, `rm`, `r`) or `dedupe` (`ddp`), unless it is global (`-g`, `--global`, `--location=global`), or any `--package-lock=false` / `--no-package-lock`. Every directory a surface runs `npm ci` in must hold a `package.json` and a lockfile (ruling R3b). Commands are read with a shell lexer, working directories are followed, and an unreadable `npm ci` target fails closed unless vouched (ruling R3c). Full-line comments are skipped.

Dynamic checks (`--npm-ci`):
7. The npm that runs (`npm --version`, or `--npm CMD`) is inside the pin.
8. For each lockfile directory, `npm ci --dry-run --ignore-scripts --no-audit --no-fund --prefix <dir>` exits 0. That is npm's own validator, the same one `npm ci` runs before it installs: it catches an override added, changed or removed without the lock (seeded: all three exit 1 with `Missing:`/`Invalid:`), a dependency added without the lock, and `EBADDEVENGINES`. About 2 s for the root and 1 s for `functions/`.

Wiring: G-0 runs the static checks as [18]. The gates job in `gate-g0.yml` gains one step after "Gate G-0 static", before "Install": `python3 ci_gates/check_lockfiles.py --npm-ci`. `npm run gate:lockfiles` runs the same locally.

Rejected: a "regenerate and compare" check (`npm install --package-lock-only`, then diff). It is not hermetic: it fetches registry metadata, so a package deprecated or republished upstream would fail main with no change in the repository. The repaired lock was checked this way once, with the pinned npm, and is byte-stable (the plan's ledger).

### Ruling 4: every lockfile installs frozen, everywhere

Every CI job already installs with `npm ci` / `npm --prefix functions ci` (checked: `gate-g0.yml`, `mutation.yml`, `legal-os-continue.yml`; `security.yml` only audits), as do `.cursor/environment.json` and `.claude/hooks/session-start.sh`. Static check 6 keeps it that way. The guard validates every lockfile it finds whether or not a job installs it. `README.md` "Run locally" said `npm install` (which rewrites the lock); it now says `npm ci` and `npm ci --prefix functions`, and states the npm pin.

### Ruling 5: release provenance comparison deferred

The audit's correction ends "require a clean npm ci plus an artifact provenance comparison for every release". There is no release pipeline: no workflow builds or deploys a release artifact, and F32 records that no deployment manifest exists. Within this change, every install is a frozen `npm ci` under the pinned npm, the guard proves the lock is consistent before any job installs, and `npm ci` verifies each tarball against its `integrity` (sha512) in the lock. Comparing a built release artifact against a rebuild (or attaching SLSA provenance) needs that pipeline; it is residual 1 and a follow-up for the release work.

### Ruling 6: tests

- `tests/f39-lockfile-guard.test.ts`: fixture tests of the guard in temporary trees (offline, fast). A consistent pair passes; each drift class fails and names its file and field: range edited, dependency added, dev dependency removed, version or name changed, override-free root-entry drift, lockfile without manifest, manifest without lockfile, foreign lockfile, `lockfileVersion` 2, a missing root, each pin defect (absent, not npm, warn-only, version outside the range, two manifests disagreeing), each non-frozen install form in a workflow, the Cursor environment, a hook and a script, and the allowed forms (`npm ci`, `npm --prefix functions ci`, `npm install -g`, `npx playwright install`, `pip install`). `--npm-ci` with an npm outside the pin (a stub) fails before any `npm ci`.

  - (b) the same copy with an override added to `package.json` and not to the lock (`"ms": "2.1.2"`) fails the guard, with npm's `Missing: ms@2.1.2 from lock file`;
  - (c) the reported failure: under Node 24's npm (`npm@11.19.1`), with the pin taken out of the copy (it would refuse npm 11 by design, case (d)), `npm ci --dry-run` on the checked-in lock exits 0; the same copy with main's override restored fails with `Missing: undici@8.11.2 from lock file` (the control that shows the test sees the defect);
  - (d) with the pin in place, npm 11.19.1 is refused with `EBADDEVENGINES` before it resolves anything.

- `tests/g0-gate-e2e.test.ts`: the minimal tree G-0 accepts now includes `package-lock.json` beside the `package.json` it already copied, because check [18] requires a root lockfile. No case is removed or weakened.

## 3a. Review round (Codex P2 x2 on PR #66, head fd31e77)

### Ruling R3a: two lockfiles in one directory fail; the shrinkwrap is the one checked (thread 4305265180)

The guard keyed lockfiles by directory, so with both `npm-shrinkwrap.json` and `package-lock.json` present it kept `package-lock.json` (the later name) and never checked the shrinkwrap, which is the file `npm ci` uses when both exist. Codex's case, a valid `package-lock.json` beside a shrinkwrap at `lockfileVersion` 2, exited 0. Ruling: a directory holding both fails ("two lockfiles in one directory; npm ci uses npm-shrinkwrap.json and ignores package-lock.json (keep one)"), because a second lockfile that `npm ci` silently ignores is drift by definition; and the shrinkwrap is the file paired with the manifest and checked, so its own defects are reported as well. A shrinkwrap on its own stays allowed and is checked like a `package-lock.json` (this repository has none).

### Ruling R3b: the root always needs a lockfile, and so does every directory an install surface runs `npm ci` in (thread 4305265184)

The lockfile requirement followed the manifest's declarations, so a root `package.json` with no dependencies and no lockfile passed although `npm ci` fails there. Ruling: the root needs a lockfile whatever it declares. For other manifests the rule is tied to what is installed, not to every `package.json`: every directory an install surface runs `npm ci` in (any `ci` alias, including `install-ci-test`) must hold a `package.json` and a lockfile. The target is the command's `--prefix` or `-C` value, else the root; a package script's `npm ci` runs in its own package's directory. A target held in a variable or command substitution (`.claude/hooks/session-start.sh` loops `npm ci --prefix "$dir"`) is not guessed. A manifest that declares nothing and that no surface installs (for example one that only sets `"type": "module"`) still needs no lockfile. Not read: a step's `working-directory:` or a preceding `cd`; such an `npm ci` is attributed to the root (residual 6).

Tests (`tests/f39-lockfile-guard.test.ts`, "review round"): six cases. RED against fd31e77's guard: 4 failed / 43 passed (47); each of the four defect cases ended `=== lockfile guard PASSED ===`; the two controls (a shrinkwrap alone is checked; `npm ci` where lockfiles exist, with a variable prefix, passes) passed already. GREEN after the fix: 47/47. Ruling R3c below replaces the "not guessed" treatment of a variable target.

### Ruling R3c: commands are read with a shell lexer; npm ci targets follow working-directory and cd, and an unreadable target fails closed unless vouched (Copilot, high, thread 4305283954; review round 2, head f86510c)

The guard found an `npm` word with a regex and ended the command at the first quote, `;`, `&`, `|` or `)`. A quoted option value therefore cut the command before its subcommand: `npm --prefix "functions" install`, `npm --prefix '$dir' i`, `npm -C "x" add foo`, `npm "install"` and an escaped quote inside a value all passed, on a workflow, a hook, the Cursor environment or a package script, and `--npm-ci` could not catch them (it validates lockfiles, not install commands).

- **Reading.** Each command text is lexed with `shlex` under POSIX rules (`punctuation_chars`, whitespace splitting, no comment handling): quotes group words and never end a command; a run of `();<>|&` is one operator, which splits commands, except that a redirection (`>`, `2>`, `<`) and its target are dropped. A quoted word that mentions npm and contains whitespace or an operator is itself read as shell (to depth 3), which covers `bash -c "..."` and `sh -c '...'`. The npm executable is the word `npm`, a path ending in `/npm`, or `npm@<version>` (through `npx` or `corepack`); the subcommand is the first word after it that is not an option or an option's value. Workflow files are read per step (`run:` inline or as a block, line by line), other workflow lines that mention npm from the root, hooks top to bottom as scripts, `.cursor/environment.json` per JSON string literal, and package scripts from their own package directory. Backslash continuations are joined.
- **Fail closed.** A text that mentions npm but cannot be lexed (an unbalanced quote) fails with "cannot read this line as shell commands". A quoted string that merely mentions `npm install` in prose on an install surface now fails too; rephrase it.
- **Residual 6 closed, cheaply.** The `npm ci` target is its `--prefix` / `-C` value read against the working directory, which starts as the step's `working-directory:` (the key in the step, or on its dash line), else the root, and follows each `cd` before it in the same run script or hook (`cd A || cd B` makes it unknown unless the alternative is `exit`/`return`; `cd "$(git rev-parse --show-toplevel)"` is the root). A target the guard cannot read fails closed: a variable or command substitution in `--prefix` or in a `cd`, an absolute path, a path that leaves the repository, or a job- or workflow-level `defaults.run.working-directory` (not followed: set it on the step).
- **Vouching.** `ci_gates/lockfile_install_allowlist.json` lists, per surface, the exact npm command (as the guard prints it, quotes removed) whose target it cannot read, the directories it installs, and why. A vouched command passes only if each listed directory holds a `package.json` and a lockfile; an entry that matches nothing fails as stale; an entry missing a field, or naming a directory outside the repository, fails. It vouches for the three real cases: `.claude/hooks/session-start.sh`'s `npm ci --prefix $dir --no-audit --no-fund --no-update-notifier --loglevel=error` (`install_pkg .` and `install_pkg functions`), and `.cursor/environment.json`'s `npm ci` and `npm --prefix functions ci`, which follow a `cd` to the checkout (`/agent/repos/cursor-init`, or `$(git rev-parse --show-toplevel)`). Without the file, the real tree fails with exactly those three lines (measured).
- **Tests.** Sixteen cases ("review round 2"): the nine quoting forms of the finding (the four `bash -c` / `sh -c` ones were controls that already failed on the old guard), the hook / Cursor / script surfaces, the unbalanced quote, working-directory inline and in a block, `cd` (followed, chained over lines, and unreadable), a job default and a variable `--prefix`, the allowlist (unvouched, vouched, a vouched directory without a manifest) and stale or malformed entries. RED against f86510c's guard: 12 failed / 51 passed (63); each quoting-bypass case ended `=== lockfile guard PASSED ===`. GREEN: 63/63.
- **Changed test expectations** (the behaviour they pinned changed; nothing removed): the hook case reports the whole command, `npm install --prefix $dir --no-audit` (the old string encoded the truncation); the two cases with a variable `--prefix` in a hook now write an allowlist entry; the e2e copies the allowlist with the surfaces; the G-0 e2e base tree adds the vouched surfaces and `functions/package.json` and its lockfile (the vouched directories).

## 4. Adversarial check

- **Steelman of a reviewer: "the finding says repair the lockfile; you changed package.json."** The lock has no field for overrides, and with main's override no lock satisfies both npm 10 and npm >= 11.2 (both directions measured), so a lock-only repair can only choose which half of the npm versions fails. The manifest change is the narrowest one that makes a single lock valid everywhere, and it leaves the resolved tree identical.
- **"CI is green on main, so this is not P0."** CI is green because Node 22 happens to ship npm 10. The v2 auditor's npm 9 passes for the same reason. The project's own optional agent requires Node 24, whose npm fails. Green CI here proves the CI toolchain, not reproducibility from the manifests.
- **Devil's advocate on the pin.** It refuses Node 24's npm at this root, which makes eve work under Node 24 less convenient (ruling 2 gives the commands), and a deploy builder on npm >= 11 now stops (residual 3). The alternative, a warn-only pin, would let two resolvers produce two trees from one manifest again, which is the defect.
- **Devil's advocate on the guard.** Static check 6 lexes command text as a POSIX shell would (ruling R3c) but does not run one: a deliberately obfuscated install (`eval`, a variable holding `install` or the npm path, a script file a surface calls) gets past it. It is a hygiene check on the repository's own install surfaces, not a security boundary; the dynamic check and `npm ci` itself still validate every lock. Check 8 needs registry access when a manifest asks for something the lock lacks, as `npm ci` itself does.
- **Bias check.** "11.2.0 is the first failing release" is a bisection over sampled versions (11.0, 11.1, 11.2, 11.3, 11.4, 11.5, 11.6, 11.10, 11.14, 11.17, 11.19.1, 11.21.1); the npm changelog entry behind it was not read and is not cited. The guard's static checks reflect npm 10.9's lock format; npm 11 writes the same root fields for this repository (measured), but a future npm could add one.

## 5. Residual risk

1. **No release provenance comparison** (ruling 5). Follow-up: when a release pipeline exists (F32), its release job runs `python3 ci_gates/check_lockfiles.py --npm-ci`, installs with `npm ci`, builds, and compares the artifact digest with a clean rebuild or records SLSA provenance.
2. **Node is still floating within 22** in CI (`node-version: "22"`), so npm floats within 10.9.x. A Node 22 patch that bundled npm 10.10 would stop every job with `EBADDEVENGINES` until the pin moves. The failure is loud and the fix is a reviewed one-line pin bump.
3. **Third-party builders** (a Functions or hosting build on Node 24 / npm 11) are refused by the pin. No deployment manifest exists in the repository (F32), so none could be tested here.
4. **npm < 10.9 ignores `devEngines`.** On such an npm only the guard (in CI) enforces the pin; the repaired lock is valid under npm 9.2.0 and 10.8.2 too (measured).
5. **The override is still needed.** It disappears when eve pins undici >= 8.10.2 (`known-advisories.md`). F40 (dev-dependency advisories, 35 findings) is unchanged.
6. **Closed by ruling R3c** (was: `npm ci` targets read from the command only). What remains: the guard reads text, not a running shell. A command that only exists at run time (`eval`, an npm executable held in a variable such as `"$NPM" install`, a script file a surface calls, like `bash scripts/x.sh`, which is not itself a surface) is not read; YAML anchors, `${{ }}` expressions in a run script and folded (`>`) scalars are read line by line as written; and an allowlist entry is a reviewed statement, not a proof, of where its command installs.
