# Phase 3a: P2 Job Engine core (design)

Status: approved under the owner's standing autonomy instruction (CLAUDE.md, 2026-10-07). Every design decision below is a recorded ruling, not a question.
Governing text: `docs/architecture/SIKANDER_AI_Architecture_Set_v19.txt` ("Lnnnn" = line). Erratum Set No. 2 (`docs/architecture/ERRATUM_SET_2_PROPOSED.md`, E-23..E-41, O-15..O-29) is PROPOSED and unsigned; this spec builds on it under the same instruction, as 2a and 2b-A did. Phase 2 specs: `2026-10-07-phase2a-matter-spine-conflict-design.md` (P2-1..P2-22) and `2026-10-08-phase2b-entity-review-design.md` (P2-23..P2-41). This spec starts its own series at P3-1.

## 1. What this builds and why

P2 is the Job Engine: "Every heavy or AI-backed task runs as a tracked Job rather than fire-and-forget: queued → running → done/failed, with logs, input/output references, a retry cap, and full audit" (L981-984). "'Every AI action is a Job' is a system non-negotiable" (L987-988, L1969-1973). Layer 18 makes it the `internal` call type: "A P2 Cloud Task: { jobType, payload, classification, idempotencyKey, retryPolicy: exponential 1s/5s/25s, max 3, deadLetterQueue, opikTraceId }. Used for anything that calls an external provider, takes more than 2 seconds, or must survive a process crash" (L8142-8144). Its service register entry is "P2 Job Engine — P2; dead-letter queue … /api/platform/jobs/* — CORE · Phase 1" (L7993-7995). Today nothing in `functions/` runs background work: E-39(4) records that "there is no P2 Cloud Tasks queue; work the set assigns to `internal` calls runs in process", and the `events` rows that 2a and 2b-A write in-transaction have no consumer (`d1/conflict/ops.ts` 166: "no outbox exists in functions/").

Phase 3 is split (P3-1):

| Part | Scope | Why separate |
| --- | --- | --- |
| **3a (this spec)** | The engine core: the `jobs` collection, transactional enqueue, the Firestore-trigger → Cloud Tasks → worker runtime with leases, the 1s/5s/25s retries and dead-letter, the sweeper, the `events` fan-out mechanism, the scheduled-job primitive, four `/api/platform/jobs/*` routes, permission actions, rules, the system audit path, one diagnostic job type. Also lint for `functions/` and the registry-version discipline check that PR #8 left open. | Emulator-testable with an in-process dispatcher; every later job type depends on it; building it without a consumer keeps its contracts general. |
| 3b | The un-merge saga (2b-B): `unmergeEntity`, one job per affected collection, "unmerge in progress", partner-approved retry, `entity.unmerged`, eager staleness of checks (P2-21). The first real job type. | Needs the 3a engine. It is the hardest consumer (L8411-8414), so the 3a contracts are tested against its needs (saga flag, partner-only retry, no cancel) without building it. |
| 3c | O-28: materialising the 30-day auto-confirm as a scheduled job. | Lands after 3b: a materialised auto-confirm sets `state: "confirmed"`, which closes the 2b-A late-dispute path (P2-28), so un-merge must exist first or auto-links become irreversible (L6928-6929). |

Work lands in Cloud Functions, region asia-south1 (L910, E-23). Success for 3a: a Cloud Functions operation can create a job in its own transaction; the job runs at least once and its transactional effect commits exactly once, however often it is delivered; a failing job retries at 1 s, 5 s and 25 s and then dead-letters with a `job.deadLettered` event and an alert log line; a partner sees the firm's queue and can requeue a dead-lettered job (at most three times) or cancel a job that is not running; a lost trigger or dispatch is recovered by the sweeper within about 90 seconds, and a crashed worker's job once its lease expires; no job row, error, event, log or API response carries payload values; cross-firm access is denied; `npm run lint` covers `functions/`; every write to the conflict registry is proven to bump the registry version; and a G-4 Phase 3a script proves all of it.

| P3-3 | **States and transitions.** `queued`, `running`, `failed`, `done`, `dead_lettered`, `cancelled`. | P3-4 | **Enqueue is a transactional outbox.** `enqueueJobs(tx, specs, { now })` (and `enqueueJob(tx, spec, { now })` for one) runs inside the caller's own Firestore transaction, so a job exists if and only if its cause committed. It reads every target doc, then creates the missing ones, so it is called after the transaction's last read (the Admin SDK throws on a read after a write, so misuse fails loudly). A spec is `{ firmId, jobType, classification, matterId, payload, inputRefs?, idempotencyKey, runKey?, createdBy }`; an unregistered `jobType`, an unknown label, an absent `matterId`, a payload over 16 KiB or not plain JSON, or an unsafe ref throws (a programming error: 500 `internal` through `runAudited`). The doc id is deterministic: `"j" +` the first 40 hex characters of SHA-256(`firmId` NUL `jobType` NUL `idempotencyKey`), so one key in two firms gives two jobs. An existing doc with the same `payloadHash`, `classification` and `matterId` is reused (no write; result `reused: true`); any difference throws `HttpError(409, "job_key_conflict")`. New rows get `dispatchSeq: 0` and `dispatchedAt` = enqueue time. Keys: a job caused by an HTTP call uses `jobKey(session, suffix)` = `` `${session.idempotencyKey}:${suffix}` `` (the router now passes the request's Idempotency-Key to POST/PUT operations as `session.idempotencyKey`); a key the architecture names is used as named (un-merge `mergeEventId + collection`, L8412; a research run `note_id:run_no`, L9511); a scheduled run uses `jobType:period` (L8147); a fan-out job uses `eventId:subscriberId` (P3-15). There is no public `createJob` route (C-2): jobs are created by the owning service in its transaction; "never a direct import" (L8144) is about running the work, not about creating the row. | L8151: "Jobs carry the same key so a retried HTTP call does not enqueue a second job"; forensic test 1 expects one OCR job for three deliveries (L8491). An enqueue after commit can be lost to a crash; an enqueue in the transaction cannot. | A caller that must enqueue after reads-and-writes restructures its transaction; 3b's `unmergeEntity` enqueues last. |
| P3-5 | **Delivery: Firestore trigger → Cloud Tasks → worker.** `onJobCreated`, an `onDocumentCreated("jobs/{jobId}")` trigger, dispatches `{ jobId, seq: 0 }` through a `JobDispatcher` interface. | P3-6 | **Worker: claim, lease, fence, handler contract.** *Claim* (one transaction): drop the task unless the row is an engine row, `seq == dispatchSeq`, and either (`status` is `queued` or `failed`, and `nextAttemptAt <= now + 2 s`) or (`status == "running"` and `lease.expiresAt <= now`). Otherwise set `running`, `attempts + 1`, `totalAttempts + 1`, `lease = { owner: <random UUID>, expiresAt: now + 600 s }`, `startedAt`, a log entry and a system audit row (P3-18); a reclaim with `attempts` already 4 dead-letters instead (P3-7). `JOB_LEASE_MS` (600 s) must exceed the worker timeout (300 s) by at least 60 s; the module asserts it at load, as `http/idempotency.ts` does for its lease. *Handler* (registered in `p2/registry.ts`): `{ jobType, saga, errorCodes, parse(payload), run(ctx) }`. `parse` validates the payload and throws a permanent `invalid_payload` error. `run(ctx)` returns `{ apply?(tx), outputRefs? }`; `apply` stages Firestore writes (no reads) that commit with `done`. `ctx` gives `job` (id, firmId, jobType, classification, matterId, attempt, totalAttempts, traceId), the parsed payload, `now()`, and `runFenced(fn)`, which runs a transaction that first re-reads the job and checks the fence before `fn(tx)`. The handler is raced against a 240 s budget (`JOB_HANDLER_BUDGET_MS`); overrun is the retryable error `handler_timeout`. *Commit* (one transaction): re-read the job; the fence holds iff `status == "running"` and `lease.owner` is this claim's owner. If the fence is lost, nothing is written (logged as `job.lease_lost`, code only). Otherwise `apply(tx)`, `status: "done"`, `outputRefs`, `lease: null`, `nextAttemptAt: null`, `finishedAt`, a log entry and the audit row. Handlers must be idempotent (L8148). Effects staged through `apply` or `runFenced` commit exactly once per job. Effects outside Firestore (later provider calls) happen at least once and carry the job id or key. **Amended in execution (2026-10-08):** the worker accepts any dispatched `seq` <= `dispatchSeq` while the row is claimable (queued or failed and due, or running with an expired lease); the lease serialises the runners. The fence turns duplicate and stale workers into no-ops for transactional effects. | A handler that needs more than 240 s is split into fenced steps or raises the budget with the timeout and lease (the load-time assertion keeps the three consistent). |
| P3-7 | **Retries and dead-letter** (resolves extract conflict C-3). One attempt plus three automatic retries: `RETRY_DELAYS_MS = [1000, 5000, 25000]`, `MAX_ATTEMPTS = 4` per round. | P3-8 | **Sweeper and clock discipline.** `jobSweeper`, an `onSchedule("every 1 minutes")` function, is the safety net. ## 4. Data flow

**Happy path.** An operation's transaction calls `enqueueJob` last → commit creates `jobs/j…` (`queued`, `dispatchSeq 0`) → `onJobCreated` dispatches task `j…-0` → `jobWorker` claims (`running`, `attempts 1`, lease 600 s, `job.start` audit) → handler `run` → commit transaction: fence holds → `apply(tx)` + `done` + `job.done` audit.

**Failure path.** The handler throws a retryable error → commit transaction: `failed`, `lastError`, `nextAttemptAt = now + 1 s`, `dispatchSeq 1`, `job.failed` event, `job.fail` audit → dispatch `j…-1` at `nextAttemptAt` → the next attempt runs. After the fourth failure: `dead_lettered`, `job.failed` + `job.deadLettered` events, `job.dead_letter` audit, then the alert log line. A partner calls `retryFailedJob` → `queued`, `attempts 0`, `manualRetries 1`, `dispatchSeq + 1`, dispatch of task `j…-<dispatchSeq>`.

**Recovery.** A lost trigger or failed dispatch leaves a due row → after 30 s the sweeper's query A re-dispatches it with seq + 1. A worker that dies after claiming leaves `running` → after the lease (600 s) query B re-dispatches it, and the worker reclaims with `attempts + 1`, or dead-letters it at 4.

**Events.** `registerClient` commits `events/{…}_candidate` → `onEventCreated` → `fanOutEvent` creates one job per matching subscriber (none in production in 3a).
