# F28: a failed corpus job ends as a failure (design)

**Finding.** Audit F28 (HIGH, P0), `docs/audit/2026-10-13-forensic-audit.md:618`: "Source failures can be acknowledged as successful Celery jobs." The dispatcher retries only exceptions it sees. Several source tasks catch and log network or parse failures and return normally; the embedding task catches an outer failure and returns 0. No producer of durable `scraper_jobs` records exists for these paths. Failure scenario: every fetched page fails, or the embedding database becomes unusable, yet Celery records a successful task. A source never updates while beat keeps firing it. Recommended correction: typed task results; propagate retryable faults; write run and completion records; distinguish empty success from failure; bounded backoff; alert on source freshness and on repeated zero-progress runs. The v2 re-audit (`docs/audit/2026-10-14-forensic-audit-v2.md:101`) has it OPEN, code unchanged.

**Rule for closure** (`docs/audit/REMEDIATION.md`): a merged PR with an end-to-end test of the real flow that fails on main and passes after it, then an independent re-audit.

## 1. What main does today (f3bbcc9)

| Path | What swallows the failure | What Celery records |

A further defect, found while writing the tests and verified by a probe (evidence log): the application's pooled engine (`database.py:17`, `pool_size=20`) keeps asyncpg connections bound to the event loop that opened them. Each Celery task calls `asyncio.run`, a new loop each time, so in a prefork child the **second** task's first query fails (`InterfaceError: cannot rollback; the transaction is in error state`). On main the harvesters and the embedding task swallowed those errors too.

## 2. Rulings

Each ruling records the decision and the reason (owner's standing instruction).

**R1. A job ends in one of five outcomes, and only two are failures of the work.** `ok` (rows written, no item failed), `partial` (some items failed, at least one succeeded), `empty` (the run worked and found nothing to write), `skipped` (a deliberate policy decision not to run) and `failed`. The Celery task succeeds for the first four and raises for `failed`. *Reason:* the finding asks to distinguish "ran, found nothing new" from "could not run". A partial run is a success with its failures counted, not a failure: retrying it would re-write every row the run already wrote (no harvester deduplicates; R12), and FINAL_2 mandatory rule 1 ("never crash on parse failure") wants one bad page not to sink the run.

**R2. A run fails when it could not do its work:**
- an exception escapes the harvester: a network error or a boundary refusal (F25 `FetchRefused`) on the request the run depends on (the PakistanCode index request, the National Assembly index request), any database error, or a bug;
- every listing request of the run failed (court discovery, Nasir reporter pages, an NA index answering 4xx/5xx): `SourceRunFailed("every listing request failed")`;
- every document the run tried failed: `SourceRunFailed("every document request failed")`;
- the dispatcher refuses the source (R5) or the harvester breaks its contract (R6).
*Reason:* these are exactly the cases the finding names ("all fetched pages fail", "the embedding database becomes unusable") plus the brief's list (network, parse, refused URL, database).

**R3. Per-item failures are counted, never silently skipped.** Each harvester records every document it tries in a `Tally` (`scraper/tasks/outcomes.py`): `item_ok(rows)` or `item_failed(error)`. A non-200 answer is a failure (`http_<status>`); a body that is not a PDF where a PDF was expected is a failure (`not_pdf`). Nasir now checks a case page's status before staging it, so a 404 or 500 page is no longer staged as a judgment. A document that loads but holds nothing to write (a PakistanCode statute page with no parsable section) is `item_ok(0)`. *Reason:* "all pages fail" can only be detected if each page's outcome is counted; on main a non-200 answer simply disappeared.

**R4. A database error always fails the run at once.** The per-item handlers re-raise any SQLAlchemy or driver error instead of counting it. *Reason:* the brief lists database errors as failures. After a failed commit the session is unusable, so on main every later item failed with `PendingRollbackError` and was swallowed. A record-specific data error (SQLSTATE class 22/23) also fails the run; that is louder than main's behaviour, never quieter, and the failure streak alert (R10) reports it.

**R5. The dispatcher refuses a source it cannot run; policy decisions are skips.** Refusals (failures, never retried): no `scraper_sources` row for the name (`source_not_found`), no route (`no_harvester`), a route without a valid kind (`invalid_route_kind`). Skips (success, outcome `skipped`, job status `cancelled`): inactive source, a trust level that is not harvestable, a `direct` route for a source that is not trusted. `_run_async` keeps its F20 contract: it returns the decision (or the harvest result) and logs exactly the lines it logged before; `run_source` turns a refusal into `SourceRefused` and records it. *Reason:* FINAL_2 Section 4 skips an inactive or blocked source and raises on an unknown access method, i.e. configuration faults are errors and trust decisions are not. A beat entry for a source that does not exist is the finding's "beat continues firing" case. Keeping `_run_async`'s return contract keeps the F20 tests (`test_e`, `test_k`) meaningful without editing them.

**R6. Harvesters return a typed `HarvestResult`; anything else is a contract failure.** `HarvestResult(attempted, succeeded, failed, written, errors, note)` with `outcome` = `partial` / `ok` / `empty`. `run_source` fails a run whose harvester returned anything else (`HarvesterContractError`, never retried). *Reason:* fail closed. A future harvester that swallows and returns `None` must not be read as a success.

**R7. Retries are explicit and bounded.** `run_source_job` keeps `max_retries=3` and retries only a retryable failure, with backoff `min(300 * 2**attempt, 3600)` s: 300, 600, 1200. Retryable: an httpx timeout, network or remote-protocol error, `TimeoutError`, `ConnectionError`, a database error whose connection was invalidated or whose SQLSTATE is class 08, 40, 53 or 57 or 55P03, and a `SourceRunFailed` whose item failures were **all** transient (those classes, or HTTP 408, 425, 429, 500, 502, 503, 504). Never retried: an F25 refusal (R10 of the F25 spec: a refused URL is never retried), a refusal or contract failure (R5, R6), a parse error or any other exception. After the bound, or for a non-retryable failure, the task raises the original exception and Celery records FAILURE. A direct call (no worker) is recorded with `max_retries=0`, since it cannot be retried. The embedding task is not retried by Celery: beat fires it every 5 minutes and each item has its own attempt bound (3). *Reason:* the brief asks for bounded explicit retries. "All transient" rather than "any transient" keeps a source that serves consistent 404s from being re-fetched four times a run. The SQLSTATE classes are promotion's transient set (`promotion.py:78-79`), copied, not imported, to keep this change out of F23's lane.

**R8. Every source run writes a durable record in `scraper_jobs` (no schema change).** The table and model already exist (`models.py:530`) and the runtime role already has DML on it (compose provisioning; conftest `ORM_TABLES`). Per attempt: one row, inserted as `running` before the harvest (job type `incremental`, `celery_task_id`, worker, `retry_count` = attempt, `max_retries`, `started_at`), then finished as `completed` (`ok`/`partial`/`empty`), `cancelled` (`skipped`) or `failed`, with `pages_scraped` (documents attempted), `records_extracted` (rows written), `records_failed`, `finished_at`, `duration_seconds`, `next_retry_at` when a retry is scheduled, and `result_summary` (outcome, reason, counts, per-error-class counts, raised error class, retryable, will_retry, retry_in_seconds, attempt, alerts). A failed run that wrote some rows before failing records them, because the dispatcher binds the run's tally (a context variable) and the harvester counts into it. Recording a failure never masks the failure: if the record cannot be written, that is logged and the original exception is raised. A success whose record cannot be written raises `RunRecordFailed`, never retried (the rows are already written). *Reason:* the finding says no producer of durable run records exists. One row per attempt is the simplest truthful record; the latest row per source is the source's state. No migration is needed, so F23's `002_*` and the reserved `003_*` are untouched.

**R9. The source row carries freshness.** On a run that ran: `last_scraped_at`; on success `last_success_at`, `consecutive_failures = 0`; on failure `consecutive_failures + 1` and `last_failure_reason`; `total_records_extracted` and `total_pages_scraped` accumulate. A skip changes nothing. `consecutive_failures` counts failed **attempts**, retries included, so a source that is down raises the `failing` alert within one scheduled run (its third attempt, about 15 minutes in) instead of after three scheduled runs (up to six days for PakistanCode). *Reason:* these columns exist for exactly this and were never written; an operator needs the alert while the outage is current.

**R10. Alerts.** Evaluated on every recorded run, logged at ERROR as `F28 source alert: <source> <alert>` and stored in `result_summary.alerts`: `failing` when `consecutive_failures >= 3`; `no_progress` when the source's last 3 runs that ran all completed with 0 rows; `stale` when the last successful run (or, if none, the source's creation) is older than 2x `scrape_frequency_hours`. *Reason:* the finding asks to alert on freshness and repeated zero-progress runs. A log line with a fixed marker is what this service can emit today (there is no metrics or alerting stack in `corpus_service`); a monitor that runs when beat itself stops is a follow-up (F28-FU2).

**R11. Zombie runs are reconciled.** Before a new attempt starts, rows of the same source and job type still `running` after 2 hours are closed as `failed` (`abandoned`). *Reason:* `task_time_limit` is 3600 s, so a row still running after 2 hours lost its worker (hard kill, container restart). The finding names "zombie progress".

**R12. The engine is disposed at the end of each task's event loop.** `job_record.in_task_loop(coro)` awaits the work and then `database.engine.dispose()` before `asyncio.run` closes the loop. Used by `run_source_job` and the embedding task. *Reason:* the probe in section 1. With failures now propagating, the pool defect would turn every second task in a worker child into a recorded failure and a retry; disposing costs one new connection per task (tasks run minutes apart).

**R13. Embedding job outcome (F27 stays out).** `process_embedding_queue` no longer catches its outer failure: a database fault, a missing `openai` package or any other escape raises and Celery records FAILURE. A database error inside the item loop re-raises (R4) instead of trying to commit on a broken session. If items were tried and none succeeded, the batch raises `BatchFailed` after the per-item attempt counts are committed, so failed items stay `pending` or `failed`, never `completed`. The function returns a typed summary (`outcome`, `claimed`, `completed`, `failed`, `missing`) instead of an int. A batch that claimed work or failed writes one `scraper_jobs` row (job type `embed`); an empty queue and a missing `OPENAI_API_KEY` (outcome `skipped`) write none (every 5 minutes, 288 rows a day of nothing). The selection, claim, lease, `next_attempt_at` and missing-record handling are unchanged: that is F27. *Reason:* the brief: "an embedding failure is a failure, not a silent success; do not redesign the claim".

**R14. Scope.** No change to `scraper/net/*` (F25, PR #67), the F24 public corpus files, `routers/quarantine.py` or promotion (F23), `requirements*.txt`, the Dockerfile (F31), `config.py`, `main.py`, `init.sql`, `models.py` or `conftest.py`, and no existing test changes. *Reason:* the brief's lanes. The new code uses only public names of the fetch boundary (`fetch_policy.FetchRefused`) and nothing PR #67's guard refuses (no `socket`, `sys.modules`, dynamic imports or private boundary members); PR #67's guard was run against this tree with PR #67's boundary in place (evidence log).

**R15. A failure survives Celery's result serialisation (found going GREEN).** Each F28 exception keeps its constructor arguments, in order, as `args`, so Celery can pickle it or rebuild it from a JSON result as `cls(*args)`. The first GREEN run had keyword-only constructors, and the eager result carried `UnpickleableExceptionWrapper` instead of `SourceRunFailed` / `BatchFailed`. A unit test pins the round trip. *Reason:* the error class is part of the recorded outcome the finding asks for; a worker would otherwise report a wrapper class to whoever reads the result backend.

## 5. Review round (PR #72: Codex x2, Cursor Bugbot, Copilot x6)

Every finding was a case where a run could still report success, or record the wrong thing, after a real failure. Each was fixed test first (RED on the reviewed code, then GREEN). These rulings amend R3, R10, R13 and R8.

**R16. An unreadable PDF is a failed document, never progress (Codex 4305694221, Copilot 4305705140 and 4305705122; amends R3).** `extract_pdf_text` returns `""` when parsing and OCR both fail (`pdf_extractor.py:290`). On the reviewed head, the harvesters called `item_ok(1)` on that and staged an empty record. A run of unreadable PDFs therefore ended `ok` and reset the failure streak. National Assembly took an empty or non-PDF body to `item_ok(0)`, an empty success.

Every harvester that extracts PDFs (SHC, Supreme Court, Lahore, Peshawar, Balochistan, Islamabad, National Assembly) now checks two things:
- the `%PDF-` signature **before** extraction (`outcomes.looks_like_pdf`; failure key `not_pdf`). This replaces the courts' looser 4-byte `%PDF` check; National Assembly had no check.
- the text **after** it (`outcomes.has_text`: empty or whitespace only is `empty_pdf_text`, Copilot's key).

Either failure is a failed item: never staged or written, and not progress. A run whose every PDF is unreadable fails ("every document request failed", not retried, so the streak grows); a mix is `partial`. Nasir and PakistanCode extract HTML, not PDFs. PakistanLawSite copies import files without extracting them. `pdf_extractor.py` itself is untouched, since its bounds and sandboxing are F26's. *Reason:* an empty extraction is the parse failure R2 names. Staging it would be the silent stale corpus the finding describes.

**R17. Every IHC feed request is counted (Codex 4305694225, Copilot 4305705087).** On the reviewed head, an IHC listing page that loaded and named its AJAX feed was a discovery success, while the feed requests themselves were never counted. Every feed failing, with no direct PDF in the markup, left discovery empty, and the run became an empty success. Discovery now keeps a feed tally. A feed fails on an exception, an answer other than 200, or a payload that does not parse (`feed_unparseable`; `_parse_feed_rows` tells it from a valid empty list). Two cases follow:
- **Every feed failed, and no other discovery path found a PDF:** the run fails with `SourceRunFailed("every feed request failed")` before anything is written. It carries the feed error counts and their transient classification, so a set of 5xx answers is retried.
- **Otherwise:** the feed failures go into the run's result (`HarvestResult.discovery_failed` / `discovery_errors`) and make it `partial`.

*Reason:* Copilot's wording, which is "required only when nothing else was found". A judgment found in the markup is real work (R1 partial), and failing at discovery keeps a retry free of duplicate writes.

*Sweep:* I checked every request site in every harvester. The court listing crawls (including child listings), the Nasir reporter and case pages, the National Assembly index and PDFs, and the PakistanCode index and slugs were already counted. The IHC feed was the only uncounted secondary discovery request.

Listing pages other than the seeds still do not make a run partial on failure, as R2 already set out. The court seeds include deliberate legacy fallbacks ("retained as a fallback"), and child listings are keyword-matched link guesses, so their failures are expected noise. A feed, by contrast, is an endpoint named by a live page.

**R18. A run whose record cannot be written is not a harvest failure (Bugbot 4305696998; amends R8).** On 9403795, `finish_skipped` sat inside the harvest `try`. A failed skip record was therefore recorded as a failed run: it grew the failure streak, and on a transient SQLSTATE it was retried. Cursor's Autofix commit c6af66d moved the skip's record write out of that `try`, the same way the finished path already was. It was reviewed, found correct and in scope, and kept as is (fast-forwarded, not rebased).

Added on top of c6af66d:
- one `except` covers both paths and logs at ERROR: `F28 run record failed: <source> <outcome> run could not be recorded (<class> (SQLSTATE x)); not retried, freshness unchanged`;
- the sweep found one more write outside that isolation, the embedding batch's success record, whose failure surfaced as the raw database error. It now raises `RunRecordFailed` with the same line, and the batch's own work stands.

`RunRecordFailed` is never retried and never touches the streak. For a source attempt, the row opened at the start stays `running` until R11 closes it. An embedding batch is different: it inserts its record only after processing, and R11 reconciles source jobs only. So a batch whose terminal insert fails leaves no row to recover; the ERROR line is its only record (Copilot 4305832756).

**R19. A failed embedding batch records what it did (Copilot 4305705063; amends R13).** An exception escaping the item loop, such as a database error after earlier items had committed, carried no counts. The failed record therefore said attempted, written and failed were all 0. The recording wrapper now owns the counters (`BatchCounts`: the item tally, claimed, missing) and passes them in. A database-failed item is counted before the re-raise, and the failed record is filled from the counters. The original exception is still raised.

**R20a. Only an HTTP 200 is a loaded page (Copilot 4305705102).** Nasir staged a case page on any status below 400, so a 204, or a 302 without a `Location` (which `PolicyFetcher` returns), was staged as a judgment. Every check that accepted 2xx/3xx was swept: the six court listing crawls, the IHC feed, the Nasir reporter and case pages, and the National Assembly index all used `>= 400`. All now require 200 and count anything else as `http_<status>`, as the PDF and statute-page checks already did. The PakistanCode index status stays unread, because its body is not used.

**R20b. A skipped source is still checked for staleness (Copilot 4305705096; amends R10).** A skip closed its record with no source effect, which bypassed `_alerts`. An inactive, blocked or untrusted source could therefore go stale silently. The alerts (`stale`, `failing`) are now evaluated on a skip too. The freshness counters are still not touched, since a skip is not a run.

**Test seam for this round.** The new e2e tests need pages on the courts' real hostnames. A local server cannot serve those: it would need port 443 and a certificate for the court's name. So the network edge for these tests is the F20 harness's seam, `fetch_policy.fetcher_for` returning canned answers. Every URL is still checked against the source's real registered policy first. The harvesters, the PDF extractor (the real one for unreadable bytes; the test environment has no PDF library, so a readable text layer is a marked fixture), the dispatcher and Postgres are all real. Discovery is real in the SHC and IHC discovery scenarios, but the six-court unreadable-PDF test replaces `_discover_pdf_urls` with a fixed result (`tests/test_f28_source_outcomes_e2e.py:697–711`). That test proves the per-document accounting, not discovery, for all six courts (Copilot 4305832771).

## 6. Re-audit round 2 (M1, L1, L3–L6)

The independent re-audit of the merged code (ae50c5b, spec as corrected by #75) failed F28 at 7/10 on one MEDIUM, M1, and listed LOW findings L1–L7. This round closes M1 and the LOWs L1 and L3–L6, test first. L2 (soft-404 HTML counted as progress) and L7 (informational) are out of scope and listed as follow-ups. The rulings below are new; where one supersedes an earlier ruling it says so, and the earlier text above stands as the record of what was decided then.

**M1 as found.** A run cut off by Celery's soft time limit was never recorded and never alerted. Celery recorded `FAILURE SoftTimeLimitExceeded`, but the `scraper_jobs` row stayed `running`; `consecutive_failures`, `last_failure_reason` and `last_scraped_at` were unchanged; the rows already written were not counted; no alert fired. Two time-limited runs on a source 30 days stale raised 0 alerts where two refused runs raised 2. When the limit landed inside harvester code, the per-item `except Exception` swallowed it. Three causes:
- billiard raises `SoftTimeLimitExceeded` from a signal handler. While the event loop waits on I/O the exception escapes the loop, and `asyncio.run` then cancels the run's task, so the coroutine sees `asyncio.CancelledError`, a `BaseException` that `run_source`'s `except Exception` never sees. A probe (evidence log) confirmed the coroutine can still await after catching it, and that the `CancelledError`'s `__context__` is the `SoftTimeLimitExceeded`.
- Alerts were evaluated only in `_close`.
- The R11 sweep closed an abandoned row but neither counted it nor evaluated alerts.

**R21. A run cut off by the time limit, or cancelled, is a recorded failure (M1; amends R8, R9 and R10).** `run_source` catches the interruption family `outcomes.INTERRUPTIONS` = (`celery.exceptions.SoftTimeLimitExceeded`, `asyncio.CancelledError`) before its `except Exception`. It records the attempt with `finish_failed`, passing an `outcomes.RunInterrupted` in place of the raw exception, then re-raises the original, so Celery still records `FAILURE SoftTimeLimitExceeded` and asyncio still sees its cancellation. The record:
- keeps the counts the run reached (the bound tally): documents attempted, rows written, items failed;
- carries a neutral reason, chosen from the exception and its context chain: `time limit exceeded` when `SoftTimeLimitExceeded` is the exception or its context (the cancellation `asyncio.run` delivers after the limit escapes the loop), otherwise `cancelled before it finished`. `error_message` and `last_failure_reason` read `RunInterrupted: <reason>`; `result_summary` adds `interrupted_by` (the original class);
- goes through `_close`, so the source's freshness counters move (R9) and the alerts are evaluated (R10).

*Reason:* the finding. The soft limit is the one realistic way a degraded site ends a run (a fetch may take 300 s, a court run fetches 40–60 PDFs with up to 3 tries), and that is the outage F28 exists to surface. Recording a stand-in exception keeps the class and the message neutral and redacted (nothing from the cut-off frame reaches the record), and re-raising the original keeps Celery's and asyncio's own semantics.

**R22. `KeyboardInterrupt`, `SystemExit` and `GeneratorExit` propagate untouched and are not recorded by the run.** Nothing catches them. The row they leave `running` is closed by the sweep (R24), which now counts it and alerts. *Reason:* they mean "stop now". Recording one would put a database round trip, which can block for the pool's checkout timeout when the database is the reason for the restart, between the signal and the exit. `GeneratorExit` cannot be recorded at all: a coroutine that awaits while closing raises `RuntimeError`. In a prefork child, where production runs, billiard sets `SIGINT` to `SIG_IGN` and a cold shutdown kills the child without an exception, so these reach a run only under the solo pool or a direct call. If one of them escapes the event loop while it waits on I/O, `asyncio.run` cancels the task and R21 records `cancelled before it finished`, which is also true.

**R23. A per-item handler never counts an interruption as an item failure (M1).** `Tally.item_failed` re-raises an interruption before it counts anything, which covers every harvester's document, listing and feed handlers through one place. The courts' `_request_with_retries` / `_post_json_with_retries` re-raise it instead of retrying, and the embedding item handler re-raises it before it touches the item's attempt count (R26). Only `SoftTimeLimitExceeded` can reach an `except Exception`; `CancelledError` already passes through. *Reason:* the finding's "the per-item `except Exception` swallows it". The tally is the single point every harvester counts through. *Limit:* a library that swallows the exception itself (the PDF extractor, F26's lane; the statute parser; the fetch boundary, F25's lane) still turns it into an ordinary failure. Such a run goes on and either ends with its own truthful outcome, the cut-off document counted as a failed item, or is killed at the hard limit and then closed and counted by the sweep (R24). Recorded as a residual risk.

**R24. The sweep records what it closes (M1; supersedes the R11 text on what a closed row says and amends R9 and R10).** Before an attempt starts, `job_record.start` still closes rows of the same source and job type `incremental` that are `running` 2 hours after they started. Now, in one transaction:
- it locks the source row first, the same lock order `_close` uses, then closes the rows with `UPDATE … WHERE status = 'running' … RETURNING`, so two concurrent sweeps never close or count the same row;
- each closed row reads `failed`, `result_summary.reason` `abandoned` (unchanged), and the neutral text `abandoned: still running 2 hours after it started, with no outcome recorded; cause unknown` in `error_message`. The old text, "its worker was lost", claimed a cause the sweep cannot know: a hard kill, a container restart, or a recording failure (R18);
- every closed row that started after the source's `last_success_at` (all of them when there is none) adds 1 to `consecutive_failures` and sets `last_failure_reason` to that neutral text. A row that started before the last success is closed but not counted, because it does not belong to the current streak;
- the alerts (R10) are evaluated, logged as `F28 source alert: <source> <alert>` and stored in each closed row's `result_summary.alerts`.

`last_scraped_at` and the totals are not touched: the sweep does not know when the abandoned run stopped or what it wrote. *Reason:* the finding: three abandoned attempts followed by one real failure gave `consecutive_failures` 1 and no `failing` alert. Now it is 4, with `failing` raised at the sweep and again at the failure.

**R25. A time-limited run is not retried.** `SoftTimeLimitExceeded`, `CancelledError` and `RunInterrupted` are in the never-retried set, and the attempt counts toward the streak, so two time-limited runs on a source 30 days stale give `consecutive_failures` 2 and 2 `stale` alerts, exactly as two refused runs do. *Reason:* the run has already held a worker for 55 minutes against a slow site. Three retries could hold it for up to four more hours (each retry comes back to the same site within 5–20 minutes) and keep other sources waiting. No harvester deduplicates (F21), so each retry would also write again the rows the cut-off run wrote. The next scheduled run comes on time, and a persistent cause raises `failing` after 3 attempts and `stale` after twice the frequency. *Steelman for retrying:* a site slow for a few minutes would be caught sooner. That is what R7's retry is for, and its faults end in seconds, not after an hour.

**R26. An interrupted embedding batch is recorded as failed (M1; amends R13 and R19).** `run_embedding_batch` catches the interruption family too: it writes the failed `embed` row from the batch's counters (R19) with `RunInterrupted` and re-raises the original. The item handler re-raises an interruption before it increments the item's attempts, so the item the batch was on stays `pending` with its attempt count unchanged. *Reason:* "any equivalent task entry point". The interruption belongs to the batch, not to the item, and counting it against the item would dead-letter items because the provider is slow.

**R27. `cross_reference` disposes the engine at the end of its loop (L3; F28-FU1; amends §3 "cross_reference").** Its task now runs `asyncio.run(job_record.in_task_loop(...))`, as R12 does for the source and embedding tasks. *Reason:* the re-audit showed the next task in the same worker child failing with `InterfaceError`: not retried, no row written, freshness unchanged. §3 called its errors "already propagated", which understated this.

**R28. Transient database connection faults are retried (L4; amends R7).** These join the transient set:
- `socket.gaierror` with `EAI_AGAIN`, "temporary failure in name resolution": `-3` under glibc and musl (the service's Linux images), `2` on BSD and macOS. The F25 guard keeps the `socket` module out of corpus code, so the class is matched by its name and module;
- `OSError` with `ENETUNREACH` or `EHOSTUNREACH`;
- SQLAlchemy's pool checkout timeout, `sqlalchemy.exc.TimeoutError`.

Other `getaddrinfo` failures (`EAI_NONAME`: the name does not exist) stay permanent: that is a wrong host in configuration, not a moment. *Reason:* a DNS blip on the database host at job start got 1 attempt instead of 4.

**R29. The run record redacts credentials in more shapes (L5; amends R8).** Before control characters are escaped and the text is capped, `describe_error` redacts:
- URL userinfo up to the last `@` of the token, so a password containing `@` or `/` is covered;
- the value of any `name=value` whose name ends in `token`, `key`, `secret`, `password`, `passwd`, `pwd`, `sig`, `signature` or `credential` (query strings, `api_key=`, `access_token=`, and keyword-style DSNs such as libpq's `password=`), quoted or not;
- the credential after `Authorization:` / `Proxy-Authorization:` (with or without a `Bearer`, `Basic` or `Token` scheme), after `X-Api-Key:`, and after a bare `Bearer`;
- `sk-…` style API keys.

A database error stays class and SQLSTATE only. *Reason:* 7 of the auditor's 13 cases passed through. No secret the service holds reaches these paths today, and the endpoints are admin-only, but the record is durable and is read by people.

**R30. Listing failures are recorded; Nasir's reporters make a run partial (L1; amends R17 and R2 for Nasir).** Each court's `_discover_pdf_urls` now takes the run tally (`tally=`, as IHC's already did), and Nasir's harvester uses its own. After the all-failed check (R2, unchanged), the listing stage's failures go into the run's `discovery_errors` under keys prefixed `listing:` (`listing:http_404`, `listing:ConnectError`). The feed keys of R17 are unchanged, and the prefix tells the two apart.
- **Courts:** recorded only. `discovery_failed` and the outcome do not change, so R17's reasoning about legacy seeds and keyword-guessed child listings stands.
- **Nasir:** its 5 reporters are fixed, live listing pages, so R17's legacy-seed reasoning does not apply to them. Their failures also count in `discovery_failed`, so a run with 4 of 5 reporters down is `partial`, never an error-free `empty`. If it wrote nothing, it still counts toward `no_progress`. All 5 down still fails the run (R2).
- **National Assembly and PakistanCode:** unchanged. The NA index is the run's only listing, so its failure fails the run; the PakistanCode index status is unread (R20a).

*Reason:* the finding. An operator must see that 3–6 of a court's listing pages failed even when the run found nothing, and a Nasir run that fetched nothing because its reporters were down is degraded, not idle. *Devil's advocate:* a `partial` Nasir run is still a success, so a reporter down for weeks raises no alert while the other four keep producing rows. A degraded-run alert is new scope (residual).

**Compatibility with F26 (#76, open while this round was built).** #76 routes every PDF through `pdf_intake` and adds `except outcomes.DocumentRejected: tally.item_failed(rejected)` ahead of each per-PDF `except Exception`. Both behaviours hold together:
- a `DocumentRejected` is never an interruption, so it is counted as before;
- a `SoftTimeLimitExceeded` raised in the intake's synchronous code reaches `except Exception`, and the tally re-raises it (R23);
- while the sandbox parses (`asyncio.to_thread`), the limit lands in the event loop's wait, so the run is recorded through R21's `CancelledError` path.

Neither change edits the other's lines. This branch merges origin/main with a merge commit once #76 lands.

**Residual risks (this round).**
- A library that catches `Exception` itself turns the limit into an ordinary failure (R23's limit). Examples: the statute parser; the fetch boundary; before F26, the PDF extractor.
- A hard kill is recorded only by the next attempt's sweep, up to the source's frequency plus 2 hours later, and not at all if beat stops (F28-FU2).
- The concurrent-sweep guarantee rests on the lock order and `UPDATE … RETURNING`; no concurrency test.
- A `partial` run raises no alert (R30's devil's advocate).
- Redaction is by pattern: an unlisted shape such as a JSON `"apiKey": "…"` still passes.
- EAI_AGAIN is recognised by its errno value.

Each now has an end-to-end test through the beat entry. Each mutant was re-run against the new tests and is killed (plan ledger).
