# Phase 4a: the gated draft in Cloud Functions (D4-1 store, D4-2 citation gate)

Date: 2026-10-11. Status: rulings made under the owner's standing autonomy instruction (7 October 2026); pending the partner's signature with Erratum Set No. 2.

## Why

The build order places "Phase 4 drafting + citation gate (D4-1, D4-2)" after the AI layer (Phase 1 plan, "Later plans"). The v6 MVP journey ends "Ghost Writer draft → citation gate → partner approval → export" (Architecture Set v19, L2051-2054). G-1 needs "a draft produced, gated and approved, end to end" (L7384-7386), with forensic tests 4 (an overruled authority blocks approval; a partner reason is required to override, L8497) and 5 (temporal mismatch, L8498-8499).

The citation gate is the safety spine. Its purpose is "a mechanical guarantee that no unverified or overruled authority reaches a partner unflagged" (L1716), and "every court-facing output passes the citation gate and a human approval; the gate checks currency of the authority, not merely its existence" (R-3, L6713-6714).

Today the gate exists only in the transitional Next.js tree (E-23), on the in-memory store. Cloud Functions has no drafting, citation, document, corpus or approval code.

## Observe: what exists

- **Pure gate code (Next.js tree), bundle-able into Functions through the `@/` alias:**
  - `services/d4-2/citations.ts` (`extractCitations`, `analyseCitations`, `normaliseCitation`, `isUnrecognisedRef`). It covers reporter-first and year-first forms, Urdu spellings and generic case references. Anything authority-like that is not read exactly becomes an `UNRECOGNISED:` suspect, so the gate fails closed. Statute references are not extracted.
  - `services/d4-2/citationFold.ts`.
  - `services/d4-2/draftCharset.ts` (`requireSupportedDraftBody`, `requireSupportedDraftTitle`, 500,000 / 500 character caps, 422 `unsupported_characters`).
  - About 127 citation tests, with the linear-time and fuzzing rulings (Phase 1 rulings 38-44).
- **The verdict (`services/d4-2/draftingIntelligence.ts`).** A known judgment is VERIFIED unless an `overruled` treatment exists. It is OVERRULED when the treating bench outranks the treated one (or is marked larger); otherwise it is UNVERIFIED. Anything unknown or unrecognised is UNVERIFIED. The worst status wins; any non-OK result blocks unless an effective partner override is present. The function is typed over the in-memory `SpineStore`.
- **Temporal check.** `getSectionAsAt(store, sectionId, asAt)` takes no jurisdiction (E-39(1), assigned to Phase 4). With no version history it reports TEMPORAL-MISMATCH, not "unavailable" (E-39(2), assigned to Phase 4).
- **Override.** `services/d4-2/partnerOverride.ts`: the caller must be a partner of the matter's firm, and a reason is required (E-31, Phase 1 ruling 44: a partner may clear UNVERIFIED with an audited reason).
- **Approval stand-in.** `services/d4-3/filingPackage.ts` pins the body by SHA-256, re-runs the gate at approval, and locks the draft.
- **Cloud Functions.** The HTTP `api`, `CallAudit`, `requirePermission`, `stageAudit` and `events` rows. Matters carry `classification` and an optional `courtId`, but no `caseNumber` and no `relevant_law_dates`. P1 (`callP1`) lands with Phase 3d.
- **Firestore rules.** `drafts` and `draft_versions` are client-writable: `gateResult`, `status` and `approvedBy` can be forged. The `drafts` create rule lacks `atOrAboveMatter`.
- **Corpus.** The Annex A contract (`postgres/ddl/001_corpus_contract.sql`) has no producer and no consumer. Nothing in Functions can read authorities, so in production every citation is UNVERIFIED until a corpus connector exists.
- **Seed.** `data/documentTypes.json` holds 159 types, all VERIFIED. Each carries `courtIds`, `temporalBindingRule`, `requiredFields`, `checklist` and `templateId`.

A save whose body and title equal the current version writes nothing and returns the current version. "Every save is a version" (L3778) holds for every change.<br>• `masterVersion` is null until P6 exists (O-62). | L8287, L3759-3792 (L5.1; "Every save is a version", L3778), L17.3 #19-#20. | No version cap yet (O-63). |
| P4-5 | **Creating a draft.**<br>• `createDraft { matterId, documentTypeId, title, body, classification? }`.<br>• The type must exist in the seed with status `VERIFIED`. When the matter has a `courtId`, the type's `courtIds` must include it (422 `court_mismatch`).<br>• **Classification.** The strictest of the matter's label and the caller's label: monotonic (L17.3 #20); a lower label is refused (422 `classification_below_matter`). | P4-6 | **The gate.** `gateDraft { draftId, version, temporalChecks? }` gates exactly the named version, which must be the current one (409 `draft_changed`).<br>• **Inputs.** Citations are `extractCitations(title + "\n" + body)`. `temporalChecks` is up to 20 caller-supplied `{ sectionId, asAtDate (YYYY-MM-DD), jurisdiction, usedText (≤ 10,000 characters) }` entries (body extraction is 4c, O-64).<br>• **Citation status per authority:** `VERIFIED`, `UNVERIFIED` or `OVERRULED`.<br>• **Temporal status per check:**<br>  – `OK` when the in-force text equals `usedText` exactly after NFC;<br>  – `TEMPORAL_MISMATCH` otherwise, carrying the in-force text so the two can be shown side by side (L6895);<br>  – `TEMPORAL_UNAVAILABLE` when there is no history: "temporal check unavailable — verify manually", never a silent pass (L6900). This closes E-39(2).<br>  `getSectionAsAt` takes `jurisdiction`, which closes E-39(1).<br>• **Overall status.** Severity order: OVERRULED, then TEMPORAL_MISMATCH, then UNVERIFIED, then TEMPORAL_UNAVAILABLE, then OK. Anything but OK blocks approval (E-22).<br>• **Result.** `GateResult = { draftId, version, bodySha256, status, citations: [...], temporal: [...], gatedBy, gatedAt }`, stored in `draft_gate_results/{draftId}_{version}` (server-only, replaced on a re-gate of the same version). The draft holds a summary. The gate writes `draft.gated` and an audit row.<br>• **Reporting, not rewriting.** The gate reports and blocks. It never edits the body. Marking with `[CITATION REQUIRED — PARTNER REVIEW]` is 4d (O-65), because the owner's standard forbids placeholders in final drafts. | L1699-1716, L6895-6908, L7286, E-22, E-39(1)-(2). | A caller who omits `temporalChecks` gets no temporal check. Body extraction (4c) closes that gap. |
| P4-7 | **Partner override.** `overrideGate { draftId, version, reason }`.<br>• The caller must be a partner who is a member of the matter (R-2: no role is exempt). The reason is 20 to 2,000 characters.<br>• The override binds to the stored `GateResult`'s version and `bodySha256`. It is written once, immutably, to `draft_gate_overrides/{draftId}_{version}` as `{ firmId, matterId, draftId, version, bodySha256, by, at, reason, cleared: [items with their statuses] }` (a second override of the same version: 409 `already_overridden`). The draft summary shows `overridden: true`. and clears OVERRULED, TEMPORAL_MISMATCH, UNVERIFIED and TEMPORAL_UNAVAILABLE (E-31; G-1 test 4: "partner reason required to override").<br>• Any new version needs a new gate and a new override; an override never survives a body change.<br>• The author-partner may override their own draft (small firms; the audit row names them).<br>• The audit action is `draft.gate_override`, with the override document as its target. | L6918, L8497, E-31, R-2. | A partner can approve over an overruled authority with a recorded reason. The architecture's text permits this. |
| P4-8 | **Approval stand-in.** `approveDraft { draftId, version }`.<br>• Partner only, and a member of the matter. The version must be current (409 `draft_changed`).<br>• It re-runs the gate on that version against the store as it is now. It re-runs it with the temporal checks recorded in that version's gate result; a version that was never gated is refused (409 `not_gated`). It approves only if the fresh result is OK, or if the override bound to that version and hash cleared every item that is still non-OK, with the same status. A cleared UNVERIFIED that has since become OVERRULED is not cleared. Otherwise it refuses with 409 `gate_blocked` and returns the fresh findings.<br>• On success it sets `status: "approved"`, `locked: true`, `approvedBy`, `approvedAt` and `approvedVersion`, and writes `draft.approved` and an audit row.<br>• A locked draft refuses saves and restores (409 `draft_locked`).<br>• This stands in for D2-3 approval routing ("pending → changes-requested → approved → finalised", L3270-3305), which replaces it (O-61). | E-22 (approval depends on the gate), the filing-package precedent, L8497. | Only partners approve until D2-3 routing exists. |
| P4-9 | **What 4a does not exempt.** Matters have no `caseNumber` yet (D6-1). The own-case exemption (E-32(a)) cannot apply: a pleading that cites its own case number gets UNVERIFIED and needs an override (O-66). | E-32(a). | One extra override on such pleadings. |
