# Phase 3c: auto-confirm materialisation (O-28)

Date: 2026-10-10 (dated 11 October in #17; merged 10 October). Status: rulings made under the owner's standing autonomy instruction (7 October 2026); pending the partner's signature with Erratum Set No. 2.

**Amended by the Phase 3c auto-confirm fixes (2026-10-10).** The rulings below stand except where `docs/superpowers/specs/2026-10-10-phase3c-autoconfirm-fixes-design.md` (P3-53..P3-59, Erratum E-47) changes them: fenced step ids are positional, `autoconfirm-<n>`, not taken from the chunk's pair ids (P3-48, P3-53); the merge event's `priorState` is `auto_confirmed`, not `candidate` (P3-45, P3-55); each pair also writes one `audit_log` row (P3-54); each step re-reads the L17.2 flag, and a failed read at the start of a run is a retryable `flag_read_failed` (P3-44, P3-56); and the merge event id is deterministic (P3-57). The `gate:g4:phase3c` CI step (P3-50's follow-up) was added by #20, and the gate now selects twenty-nine tests (P3-59). #19's close-out (`docs/superpowers/specs/2026-10-11-phase3c-closeout-design.md`, P3-51, P3-52, E-46) adds the scheduled-tick retry and closes O-43. The file keeps its `2026-10-11` name.

## Why this slice

The Phase 3 split (3a engine, 3b un-merge saga, 3c O-28) leaves 3c as the next slice: 3a (PR #9), 3b (PR #12) and the 3b close-out (PR #16) are on `main`, and O-28 names no input from the partner. Today the 30-day auto-confirm (L18 §7.1) is computed at read time (P2-28): an auto-confirmed pair has no `merge_events` row, so L17.2 #16 ("every merge is an immutable event") does not hold for it, it cannot be un-merged (E-43(f)), and a late dispute re-opens it. 3b made un-merge exist first, as the 3a spec required, so this slice may now set `state: "confirmed"`.

Success: each undisputed candidate pair that is 30 days old has, within a day, the `merge_events` row a human confirmation would have written (actor `system`), its rows `confirmed`, and an `entity.confirmed` event; a partner can un-merge it.

## Rulings

| Id | Ruling | Basis | Cost if wrong |
| --- | --- | --- | --- |
| P3-42 | **Scope.** One job type, `d1.autoconfirm`, one scheduled run per firm per PKT day. No route, no permission action, no rules change, no new index (the review queue's `(firmId, state, disputed, createdAt)` index serves the query). | O-28 text; the smallest slice that closes it. | None. |
| P3-43 | **Schedule.** `SCHEDULED_JOBS` gains `{ jobType: "d1.autoconfirm", cron: "15 2 * * *", period: "day" }` (02:15 Asia/Karachi), deployed as `d1AutoConfirmTick` through `scheduledJobFunction`. The run key is `d1.autoconfirm:YYYY-MM-DD` (P3-16); payload `{ period }` only; job label `internal`, `createdBy: "system"`; `saga: false` (a dead letter is retried or cancelled by anyone who may, P3-12/P3-13). | P3-16 primitive; 02:15 is off-hours, after the 02:00 conventions of the other firm-level jobs (none yet). | A tick that fails for one firm is not retried (O-43, still open); the next day's run finds the same pairs, because eligibility is stored state and not the day, so the loss is at most one day. |
| P3-44 | **Eligibility** (the read-time rule, unchanged): L17.2 on for the firm (`l17_2Enabled`; unreadable firm doc reads as off, so nothing is confirmed), and for the pair every key row has `effectiveLinkState(row, now, true) === "auto_confirmed"`: `state "candidate"`, `disputed === false`, `createdAt` at least 30 days old, no un-merge in progress. A pair with any other row (confirmed, rejected, disputed, young, un-merging) is left alone. Re-checked inside each step's transaction. | The job must agree with what the engine already treats as confirmed, so materialising changes no conflict outcome. | A pair that gains a second key row later is mixed and waits until every row has aged (the same rule `confirmMerge` applies to a pair). |
| P3-45 | **What is written, per pair, in one transaction:** a `merge_events` row `kind: "link_confirmed"`, `basis: "auto_confirm"`, `priorState: "candidate"` (O-28's text: the stored state before the job), `actorId` and `actorRole` `"system"`, `confirmedAt` (the run's time), `effectiveAt` (latest row `createdAt` + 30 days, the instant the pair became confirmed at read time), evidence note and key values, snapshot of both entities, `reverted: false`, label = max over rows, entities and clients; every row `state: "confirmed"` with `confirmation { by: "system", role: "system", at, note, mergeEventId, auto: true, effectiveAt }`; an `entity.confirmed` event keyed `${mergeEventId}:confirmed`. The shape is the one `confirmMerge` writes, so `unmergeEntity` and the saga run on it unchanged. | L17.2 #16; reuse over a second event shape. | A reader that tells human from automatic confirmation must read `basis` or `confirmation.auto`; both are set. |
| P3-46 | **Consequences, accepted.** After materialisation `disputeLink` answers 409 `link_not_candidate` (E-41(d) and P2-28's late dispute are superseded); the remedy is `unmergeEntity` (partner), which reopens the pair as a disputed candidate that never auto-confirms again (P3-27). Between day 30 and the next run (at most about a day) the pair is still a candidate in storage and can still be disputed. E-43(f) ("an auto-confirmed pair cannot be un-merged") is superseded. | The 3a spec held 3c until un-merge existed for this reason. | A partner who wants to reverse an auto-link uses two steps (un-merge, then the review queue) instead of one. |
| P3-47 | **Registry discipline (P3-20).** A step that writes any row bumps the registry version in the same transaction; a step that writes nothing does not. Confirming does not change what the conflict screen concludes, but `entity_links` is in `REGISTRY_SCOPE`. | The write recorder fails any transaction that writes an in-scope field without a bump. | A `openMatter` re-screen runs once more than strictly needed. |
| P3-48 | **Bounds.** The run reads at most 2,000 aged candidate rows (ordered by `createdAt`), groups them into pairs, and materialises up to 480 pairs, in fenced steps of 10 (`AUTO_CONFIRM_STEP_PAIRS`) with a step id from the chunk's pair ids (at most 48 steps of the 50 a job may record). The rest wait for the next day's run. | Per-step transaction size (about 7 writes a pair); MAX_FENCED_STEPS. | A first run over a very large backlog drains over several days. Rows of pairs skipped as mixed can crowd the 2,000-row page until they age; a firm with that many is O-26 territory. |
| P3-49 | **Label.** The job row is `internal` (it carries no matter content and returns no output); the event rows carry the pair label so `merge_events` and `events` reads stay clearance-filtered. | Same rule as `confirmMerge`. | None. |
| P3-50 | **Gate.** `gate:g4:phase3c` (`ci_gates/gate_g4_phase3c.sh`) runs the 3b gate's sixteen named tests and the four auto-confirm tests (twenty in all, selected by exact name), route coverage (21 d1 routes, 4 jobs routes), boot, lint and G-2; its `gate-g0.yml` CI step is a follow-up (the autopilot token cannot edit workflows), as PR #12's was. | Same pattern as the earlier gates. | None. |
