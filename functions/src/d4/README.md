# D4 drafting and the citation gate

The gated draft in Cloud Functions (spec `docs/superpowers/specs/2026-10-11-phase4a-gated-draft-design.md`, rulings P4-1 to P4-15; errata E-50 and E-51 in `docs/architecture/ERRATUM_SET_2_PROPOSED.md`). It is the D4-1 draft store (versions, restore, lock) and the D4-2 citation and temporal gate, with an audited partner override and a partner approval stand-in. The safety property is L1716's: no unverified or overruled authority reaches a partner's approval unflagged, and every court-facing draft passes the gate and a human approval (R-3, L6713-6715). Since audit finding F06 (2026-10-13) an empty check is not a pass: a gate run that assessed nothing (no citation, no temporal check) is `NOT_ASSESSED`, and approving a law-dependent document needs the type's review checklist with evidence.

Phase 4a has no AI generation. A partner pastes or types the text; generation through P1 is Phase 4b. In production the authority port is empty (below), so every citation is UNVERIFIED and every temporal check unavailable until the corpus connector exists (O-59), and the partner override carries the load.

The pure gate code is shared with the Next.js tree through the `@/` alias: `services/d4-2/citations.ts` (the extractor), `draftCharset.ts` (the charset and size rule) and `citationVerdict.ts` (the verdict rule, `verdictFromTreatments`). The Next.js `/api/d4/drafts` route and the filing-package stand-in stay as the transitional path (E-23) until the app calls Functions (O-67).

**F06 dependency on F01 (recorded by the F06 re-audit, 2026-10-14).** The Next.js copy of the gate (`verifyCitations` in `services/d4-2/draftingIntelligence.ts`, `runDraftPreflight` in `services/d4-1/drafts.ts`) still reports OK for uncited prose. It has no scope, no NOT_ASSESSED and no review checklist. That copy serves `/api/d4/drafts` (preflight, compose) and the flag-exempt filings core of `/api/d4/filings` (`create_package`, `decide_package`, `services/d4-3/filingPackage.ts`). No production user can reach it today: the repo has no deploy target for the Next.js app, `firestore` persistence fails closed (F01), and with the memory escape hatch the identity layer refuses every caller. **Before Next.js persistence or identity is made production-capable (any F01 correction, including a production Admin adapter), both the drafts route and the filings `create_package`/`decide_package` path must either be retired or be brought to the same NOT_ASSESSED, assessed-scope and review-checklist semantics as this gate.** O-67 covers the drafts route only; this dependency covers the filings path too.

## Routes

On the existing HTTP `api` (E-37: no onCall). Every POST needs an `Idempotency-Key`. A blocked approval (409 `gate_blocked`) is stored and replayed for its key, because it commits the fresh gate result before it answers; every other D4 409 commits nothing and a same-key retry runs again. Every route is rate kind `general` (no provider call). Lists paginate with `?limit=` (1 to 100, default 20) and `?cursor=`.

R-2 holds for every action: no role is exempt from matter membership.

## Collections and shapes

All writes are by Cloud Functions, in transactions. `firestore.rules` denies every client write (P4-11). Through the client SDK, `drafts` and `draft_versions` are readable only as `draft.read` allows through the API: a partner, associate or clerk (interns stay denied; O-68 is closed) who is a member of the draft's matter and is cleared for the row's own label and for the matter's current label, so a label raised after a row was written binds it too. `draft_gate_results` and `draft_gate_overrides` are unreadable by any client.

| Path | Holds |
| --- | --- |
| `drafts/{auto id}` | `firmId`, `matterId`, `documentTypeId`, `title`, `classification`, `status` (`draft` or `approved`), `currentVersion`, `currentBodySha256`, `locked`, `masterVersion` (null until P6, O-62), `gateResult` (the summary: `version`, `bodySha256`, `status`, `gatedAt`, `overridden`, `resultId`; null until the current version has been gated), `lastGatedVersion`, `approvedBy`, `approvedAt`, `approvedVersion`, `reviewChecklist` (set by the approval when it has one, F06: `[{ item, evidence }]` in the type's order; returned by `getDraft` and `approveDraft`, never by `listDrafts`), `createdBy`, `createdAt`, `updatedAt`. Never the body. |
| `draft_versions/{draftId}_{n}` | one immutable row per stored version, n dense from 1: `firmId`, `matterId`, `draftId`, `version`, `title`, `body` (inline), `bodySha256`, `classification`, `kind` (`create`, `save` or `restore`), `restoredFrom?`, `createdBy`, `createdAt` |
| `draft_gate_results/{draftId}_{n}` | the latest gate run of version n: `resultId`, `firmId`, `matterId`, `draftId`, `version`, `bodySha256`, `classification`, `status`, `citations`, `temporal`, `scope` (F06: `{ citations, temporalChecks, assessed }`; recorded for the reader, and derived again from the findings on every read, so a result stored without it reads correctly), `gatedBy`, `gatedAt`, `gateRuns` (the count of `gateDraft` runs of n) |
| `draft_gate_overrides/{draftId}_{n}` | the one immutable override of version n: `firmId`, `matterId`, `draftId`, `version`, `bodySha256`, `resultId`, `classification` (the draft's label: the reason is the partner's text about the matter), `by`, `at`, `reason`, `cleared` (for a NOT_ASSESSED result, the one item `{ kind: "scope", status: "NOT_ASSESSED" }`) |
| `events/{draftId}_{n}_{suffix}` | see Events and audit |

The body hash is the SHA-256 of the stored body in UTF-8 (the title is not part of it). A body is stored NFC-normalised, inline (the content pointer of L8287); R2 object storage is O-2. A body is at most 500,000 characters and at most 900,000 UTF-8 bytes (422 `draft_too_large`, never truncated: Firestore limits a document to 1 MiB). A title is one line of 1 to 500 characters with no control character (400 `invalid_title`; 422 `title_too_long`). Text with bidirectional or invisible characters or confusables is 422 `unsupported_characters` before anything is stored or gated.

Two indexes back the list routes (`firestore.indexes.json`): `drafts` by `firmId`, `matterId`, `updatedAt` descending, and `draft_versions` by `firmId`, `draftId`, `version` descending. The stored text and findings are exempt from single-field indexing, since nothing queries them: `draft_versions.body`, `draft_gate_results.citations` and `.temporal`, `draft_gate_overrides.cleared` and `.reason`, and `drafts.reviewChecklist` (the approval's evidence, F06).

### Saves and versions

A save names the version it edits (`baseVersion`). If another save landed first it is 409 `draft_changed`, so two editors never silently overwrite each other; two or four saves racing on one base give exactly one new version and the numbers stay dense. A locked draft is 409 `draft_locked` (checked first). A save whose title and body equal the current version's writes nothing but its audit row. A new version is not gated: the draft's gate summary is reset (the old result stays in `draft_gate_results`).

### Classification

A draft's label is the strictest of the matter's label, the caller's label and `internal` (monotonic, L17.3 #20; the `internal` floor is ruling R3, the one P1 applies to caller-authored free text). A caller label below the matter's own is 422 `classification_below_matter`; the caller's clearance must reach the result (403 `clearance`). A save or a restore reads the matter in its transaction and gives the new version, and the draft, the strictest of the draft's label and the matter's current one, so a matter label raised after the draft was created binds every later version and never falls; earlier versions keep the label they were written with. Events, gate results and overrides carry the draft's label. A closed matter takes no new draft (409 `matter_closed`, R4); saves and restores on an existing draft of a closed matter are still allowed (O-70).

### Document types

`documentTypeId` must be a `VERIFIED` row of `data/documentTypes.json` (159 types; E-15). When the matter has a `courtId`, the type must list it exactly, list a family `X_*` that admits it (`X` itself and any `X_…`), or list `NON_FORUM` (notices, contracts and affidavits, 74 types, suit a matter in any court; R2); otherwise 422 `court_mismatch`. Eleven seed types are restricted to courts absent from `data/courts.json` (38 name at least one; O-69).

## The gate

`gateDraft` gates exactly the named version, which must be the current one (409 `draft_changed`). The gate is a pure function of the draft and an authority store (`gate.ts`: `runGate`). It reports and blocks; it never edits the body. Marking with `[CITATION REQUIRED — PARTNER REVIEW]` is Phase 4d (O-65).

**Citations** are `extractCitations(title + "\n" + body)`, de-duplicated by judgment id (or by canonical ref when unknown). Each authority is `VERIFIED`, `UNVERIFIED` or `OVERRULED`. A known judgment is VERIFIED unless an `overruled` treatment exists; it is OVERRULED when the treating bench outranks the treated one (or the recorded treating bench is `larger`), and UNVERIFIED when there are overrulings but none qualifies. Anything the store does not know is UNVERIFIED. Anything authority-like that the extractor cannot read exactly becomes an `UNRECOGNISED:` suspect, which is UNVERIFIED and is never looked up.

**Temporal checks** are caller-supplied (`temporalChecks`, at most 20) until Phase 4c extracts statute references from the body (O-64): each is `{ sectionId, asAtDate (a real YYYY-MM-DD date), jurisdiction (an upper-case code matching /^[A-Z0-9_.:-]{1,50}$/, R11: `PK`, `AJK`, `SINDH`; a space, a no-break space or lower case is refused), usedText (1 to 10,000 characters) }`, no two on the same (sectionId, asAtDate, jurisdiction), and all `usedText` together at most 200,000 UTF-8 bytes (400 `invalid_temporal_checks`, R8).

**A check applies only to text the draft pleads (F06 ruling C).** Every check of a run, the caller's and the carried ones alike, must have its `usedText` occur in the version's title and body as `runGate` reads them (`title + "\n" + body`). The comparison applies the body's own normalisation to both sides (`normaliseDraftBody`: paste artefacts removed, CRLF as LF, NFC, ASCII digits and dashes) and folds every run of whitespace to one space; it is otherwise exact (`unpleadedChecks` in `gate.ts`). A check the draft does not plead is refused with 422 `temporal_check_not_in_draft` after the merge and before any evaluation, and nothing is stored (no result, no summary, no event; one deny row). An unrelated but true check therefore cannot make uncited prose "assessed" and OK. A carried check (R10) that a new version no longer pleads is refused the same way until the caller re-supplies the same (sectionId, asAtDate, jurisdiction) with the text this version pleads; the caller's `usedText` wins on a shared key, and the key never leaves the draft's set. `approveDraft` applies the same rule to the checks recorded on the version's stored result before it re-runs the gate (F06 follow-up): a result stored before the ruling can record a check the version never pleads, and a true one would make the approval's run OK with no override. Such a draft is refused with 422 `temporal_check_not_in_draft`, with nothing stored, nothing approved and one deny row; the recovery is a re-gate of the version that re-supplies the check on its key with the text the version pleads, which shows the partner what the draft actually pleads (a superseded text is a `TEMPORAL_MISMATCH`), then approval on that run.

**Checks are carried forward per draft (R10).** Every gate run uses the caller's checks together with the checks recorded on the draft's most recent stored result, of any version (`draft_gate_results/{draftId}_{lastGatedVersion}`, read in the run's transaction), merged by (sectionId, asAtDate, jurisdiction); where both carry the same key, the caller's `usedText` wins. A recorded check never leaves the draft's set: a re-gate or a new version gated without it still re-checks it against the store as it is then, and a partner override clears its status on that version only. The caps hold for the merged set (at most 20 checks and 200,000 bytes, else 400 `invalid_temporal_checks`). A draft whose callers never supplied a check gets none until 4c (O-64); a wrong `sectionId` blocks every later version until a partner overrides each (O-75). A run whose carried result was replaced while it ran is 409 `draft_changed`. A carried result that is missing (a retention job or a manual clean-up removed it, O-63), not this draft's, or malformed, and a `lastGatedVersion` that is not a version number, are 409 `not_gated`: a recorded check is never dropped silently, so retention must keep each draft's latest result.

| Temporal status | Meaning |
| --- | --- |
| `OK` | the text in force on that date in that jurisdiction equals `usedText` exactly, after NFC on both sides |
| `TEMPORAL_MISMATCH` | it differs; the finding carries the in-force text so both can be shown side by side (L8499) |
| `TEMPORAL_UNAVAILABLE` | the store has no history for that section, date or jurisdiction: "temporal check unavailable — verify manually", never a silent pass (L6900). A date before the first version, after a closed last one, or another jurisdiction's section is this too |

The overall status is the most severe across all findings, in this order, and anything but `OK` blocks approval (E-22):

| Overall | Arises from |
| --- | --- |
| `OVERRULED` | a citation OVERRULED |
| `TEMPORAL_MISMATCH` | a check TEMPORAL_MISMATCH |
| `UNVERIFIED` | a citation UNVERIFIED |
| `TEMPORAL_UNAVAILABLE` | a check TEMPORAL_UNAVAILABLE |
| `NOT_ASSESSED` | no applicable check ran: no citation finding and no temporal check (F06) |
| `OK` | every citation VERIFIED and every check OK, with at least one citation or check |

**Assessed scope (F06).** An empty check is not a pass. Every gate result carries `scope: { citations, temporalChecks, assessed }`: the number of citation findings (an `UNRECOGNISED:` suspect is one, so it is UNVERIFIED, not NOT_ASSESSED), the number of temporal checks run (each one the draft pleads: ruling C, above), and `assessed`, true when at least one of either ran. A run with `assessed: false` is `NOT_ASSESSED`: the gate found nothing it could check, which proves only that no legal verification took place, never that the prose is right (uncited text asserting a thirty-day statutory deadline is the audit's example). Like every status but OK it blocks approval (E-22); only the partner override clears it, so citation-free documents are not banned, they need a partner's explicit approval. The scope is derived from the findings whenever a result is read, never taken from what is stored: a result stored before F06 (status `OK`, no findings) reads as `NOT_ASSESSED`, can be overridden, and approval decides on its own fresh run, not on the stored status.

The gate fails closed. A status outside its domain counts as UNVERIFIED (a citation or the overall status) or TEMPORAL_UNAVAILABLE (a check), never OK, and the stored overall status is never lower than the runner's own.

The caller's text the gate stores (a `usedText`, an override reason) passes the draft charset rule (422 `unsupported_characters`, R7) and is stored with paste artefacts removed, CRLF turned into LF and NFC-normalised, with no dash or digit folding, because it is compared exactly with statute text, which keeps its em dashes. (A jurisdiction with such a character is already refused by its pattern, 400.) A run whose findings would exceed 900,000 bytes is 422 `gate_result_too_large` (R8): nothing is stored or approved and the in-force text is never truncated.

`gateDraft` writes the result to `draft_gate_results/{draftId}_{n}` with a fresh `resultId` (replacing an earlier run of that version), the draft's summary and `lastGatedVersion`, the `draft.gated` event and the audit row, in one transaction. A locked draft is 409 `draft_locked`.

`getVerificationReport` returns the stored result of the draft's last gated version, that version's override if any, and `current`: whether that result is for the draft's current version and body (after a save it is not).

## The override and approval rules

**Override** (`overrideGate`, P4-7). The caller must be a partner and a member of the matter (R-2); the author-partner may override their own draft (the audit row names them). The reason is 20 to 2,000 characters once trimmed (400 `invalid_reason`) and passes the charset rule (422). The override clears all five non-OK states: OVERRULED, TEMPORAL_MISMATCH, UNVERIFIED and TEMPORAL_UNAVAILABLE (E-31), and NOT_ASSESSED (F06), which it records as the one cleared item `{ kind: "scope", status: "NOT_ASSESSED" }`. It is written once, immutably, and records the authenticated caller (`by`, never a body field), the reason, the body hash, the `resultId` and every item it cleared with its status. An associate or a clerk cannot clear a NOT_ASSESSED result, as for any other. Refusals, in the order checked: 409 `draft_locked`, 409 `draft_changed` (the version is not the current one), 409 `not_gated` (no stored result for this body), 409 `gate_result_changed` (R6), 409 `nothing_to_override` (the result is OK), 409 `already_overridden`. An override never survives a body change: a new version, a restored old text included, needs its own gate and its own override.

**R5, frozen checks.** Once a version has an override, `gateDraft` on it is 409 `already_overridden`. The check set the partner cleared cannot be narrowed or swapped by a later re-gate (a re-gate with fewer or different checks would change what approval re-checks).

**R6 and R9, result binding.** Every write of a gate result carries a fresh `resultId`. `overrideGate` and `approveDraft` require the `resultId` of the result the partner reviewed (400 `invalid_result_id` if it is not a string) and refuse with 409 `gate_result_changed` if another run has replaced it since, so a partner clears and approves what was shown, never a later result: a re-gate without a check after the partner was shown its block cannot carry an approval. The `resultId` is on the gate result the routes return and on `getVerificationReport`.

**Approval** (`approveDraft`, P4-8; the stand-in for D2-3 routing, O-61). Partner only, a member of the matter, on the current version (409 `draft_changed`); a locked draft is 409 `draft_locked`; a version that was never gated is 409 `not_gated`; the stored result must be the one the partner reviewed (`resultId`, R9: 409 `gate_result_changed`). A law-dependent type needs its review checklist (F06, below): 422 `review_checklist_incomplete` otherwise, checked before the gate re-runs, so nothing is written. Every temporal check recorded in the version's result must be pleaded by the version (F06 ruling C, above): 422 `temporal_check_not_in_draft` otherwise, also before the gate re-runs, so nothing is written. It re-runs the gate on that version against the authority store as it is now, with the temporal checks recorded in the version's result. It approves only if the fresh result is OK, or if the override bound to that version and body hash cleared every item that is still non-OK with the same status (a NOT_ASSESSED result needs the override's scope item). A cleared UNVERIFIED that has since become OVERRULED is not cleared, nor is a cleared TEMPORAL_UNAVAILABLE that is now a mismatch (an item is matched by its kind, its reference or section key, and its status; O-71). Otherwise it refuses with 409 `gate_blocked`; it stores the fresh result and summary first, so `getVerificationReport` shows why (ruling R1: the router carries `{ error: { code } }` only). A re-gate that lands during the approval's re-run makes the approval 409 `draft_changed`. On success it sets `status: "approved"`, `locked: true`, `approvedBy`, `approvedAt` and `approvedVersion`, stores the review checklist (`reviewChecklist`) when there is one, and writes `draft.approved`. Two approvals at once give one approval and one `draft_locked`. An approved draft refuses saves, restores, gates, overrides and approvals (409 `draft_locked`).

**The review checklist (F06).** A document type is law-dependent (`isLawDependent`, ruling A) when it is filed in a forum, its `courtIds` not listing `NON_FORUM` (85 of the 159 seed types), **or** its own seed checklist names a legal-verification item. `LEGAL_VERIFICATION_ITEM` in `doctypes.ts` is the one test for that: a case-insensitive, whole-word match on Gate 33, L17.1, citation(s), statute or statutory, limitation, provision(s), jurisdiction, or "sources cited". Over the seed it selects exactly 19 NON_FORUM types, which the unit tests pin: the suits `property_suit_possession` and `property_injunction_suit`, `secp_complaint`, the applications `compromise_application`, `land_regularization_application`, `mutation_application`, `demarcation_application`, `record_of_rights_application`, `cantonment_application`, `kda_application` and `dha_application`, and the memos `legal_opinion`, `arguments_brief`, `counter_arguments_brief`, `case_strategy_memo`, `case_compendium`, `due_diligence_report`, `contract_review_memo` and `company_incorporation_checklist`. **Or** its id is in `LAW_DEPENDENT_BY_RULING` (`doctypes.ts`), the code-side ruling of the F06 follow-up audit. The audit read every VERIFIED NON_FORUM type's checklist, `firstGroundRule` and required fields; the map lists, each with a one-line reason, the 17 whose validity turns on a substantive rule of law that no line of their checklist matches: the will `will_wasiyat` ("Dispositions within the permitted third or heirs' consent": the limit on bequests), the gift `gift_deed` (hiba: declaration, acceptance and delivery of possession), the instruments of immovable property whose transaction a statute requires to be registered (`sale_deed`, which a right of pre-emption also touches, `sale_agreement`, `mortgage_deed`, `lease_agreement_commercial`, `lease_agreement_residential`, `tenancy_agreement`, `development_agreement`, `release_deed`, `partition_deed`), the notices whose period or precondition is statutory (`eviction_notice`, `termination_notice`, `defamation_notice`), the regulatory reply `secp_response` (its first ground is maintainability and limitation), the declaration of legal heirs `heirship_affidavit` (the law of succession fixes the heirs) and the covenant in restraint of trade `non_compete_agreement`. The seed is partner-approved (L18 Annex C) and is not edited for this. Clerical items (parties, recitals, consideration, the execution block, stamp duty and court fee marked MANUAL) never make a type law-dependent, and the template line "Registration where compulsory" does so only for the instruments of immovable property. The other 38 NON_FORUM types (contracts on the general law of contract, corporate records, generic notices and replies, affidavits of fact, a translation, a retainer letter, a vakalatnama) are not law-dependent; the unit tests pin both lists and check that every id of the ruling map is a VERIFIED NON_FORUM seed id the checklist rule leaves out. That makes 121 law-dependent types: 85 forum types, 19 by their checklist and 17 by ruling. Every approval of a law-dependent type, whatever the gate says, needs `reviewChecklist: [{ item, evidence }]` that names every item of the type's seed `checklist` (`getTypeProfile`) exactly once, by exact string, in any order, and nothing else; a seed row that repeats an item (`sale_deed`'s stamp-duty line) is answered once. Each `evidence` is the reviewer's text, one or more lines, **at least 20 characters once trimmed** (ruling B, the override reason's floor) and at most 2,000; it passes the draft charset rule (422 `unsupported_characters`, R7) and is stored as an override reason is (paste artefacts removed, CRLF as LF, NFC), trimmed. A malformed checklist (not an array, more than 50 entries, an entry that is not `{ item: string of 1 to 500 characters, evidence: string }`, evidence over 2,000 characters) is 400 `invalid_review_checklist`, checked with the other 400s before the permission; a missing, extra or repeated item, or evidence under 20 characters once trimmed (an item answered with "x" is not answered), is 422 `review_checklist_incomplete`, after the permission. For any other type the checklist is optional, but one that is sent must meet the same rule. The approval stores the entries on the draft in the type's order and returns them (`reviewChecklist`, null when there is none); `getDraft` returns them too, `listDrafts` never does. A draft whose type is no longer a verified type is not approved (404 `document_type_not_found`). The checklist records the human review; it is not a gate status and the gate never reads it.

After an override, a worsened status needs a body edit, because the override is immutable and the version is not re-gated (O-72).

**R12, the permission in the transaction.** Every route that writes a draft (create, save, restore, gate, override, approve) decides the caller's permission twice: once on entry (`loadDraftForCaller` or `requireMatterAction`, audited by P5), and again inside its write transaction (`requireStillPermitted`), on the matter and the caller's `matter_members` row as read in that transaction. A member removed, or the matter's label raised above the caller's clearance, while the call runs (the gate's run on the authority store sits between the two checks) is refused 403 with the table's reason (`not_member`, `clearance`, `role_not_permitted`) and nothing is written but the deny row; a matter that is gone is 404 `not_found`.

## The authority port

`authority.ts` defines `AuthorityStore`, the only thing the gate knows about the corpus:

- `findJudgment(canonical)` → `{ judgmentId, benchType } | null`
- `listTreatments(judgmentId)` → the recorded treatments (`kind`, treating bench)
- `getSectionAsAt(sectionId, asAtDate, jurisdiction)` → `{ text } | "no_history"`

A call carries only a canonical citation, a judgment id or a section key (with a date and a jurisdiction), never a matter id or party data (L9633). Every adapter returns a treatment `kind` in lower case (`"overruled"`, `"followed"`, ...) and a bench as one of `"single"`, `"division"`, `"full"`, `"larger"`: the verdict rule counts only a kind that is exactly `"overruled"`, so an adapter that returned `"Overruled"` would pass an overruled judgment as VERIFIED (the O-59 parity test asserts it). The production adapter is `EMPTY_AUTHORITY_STORE`: no judgment, no treatment, no history. Until the corpus connector exists (O-59) every draft that cites an authority is UNVERIFIED and every temporal check is `TEMPORAL_UNAVAILABLE`, so every draft that cites an authority or carries a check needs a partner override to be approved (a check, once supplied, is carried to every later run and version, R10, and approval is bound to the result the partner reviewed, R9); a draft that cites nothing and was never given a check is NOT_ASSESSED (F06) and needs one too. That is honest and fails closed: on the production store no draft is approved without a partner's explicit override. `activeAuthorityStore()` returns the empty store unless a test has set another with `setAuthorityStoreForTests`, which throws when `NODE_ENV` is `production`. `InMemoryAuthorityStore` is for tests; its fixtures use the year 2099 and `test_act_s1`-style ids so they never look like real authority (P4-13).

## Events and audit

Events (payload `{ draftId, matterId, documentTypeId, version, gateResult: status | null, masterVersion: null }`, the draft's classification, id `<draftId>_<version>_<suffix>`; the status is any overall status, `NOT_ASSESSED` included; no event carries the review checklist):

- `draft.autosaved` once per stored version (create, save and restore; an identical save writes none), suffix `autosaved`.
- `draft.gated` per `gateDraft` run, suffix `gated_<n>` with n the version's run count, so a re-gate never collides. An approval's re-run writes no `draft.gated`.
- `draft.approved`, suffix `approved`.

One `audit_log` row per decision, in the decision's transaction: `draft.create`, `draft.edit`, `draft.gate`, `draft.gate_override` (target the override document), `draft.approve` and `draft.read`. A refusal is audited as a deny. `draft.generated` is 4b; `draft.finalised` comes with D2-3 (O-61).

## Error codes

| Status | Codes |
| --- | --- |
| 400 | `matter_required`, `invalid_document_type`, `invalid_title`, `invalid_body`, `invalid_classification`, `invalid_version`, `invalid_temporal_checks`, `invalid_reason`, `invalid_result_id`, `invalid_review_checklist`, `invalid_query`, `invalid_cursor`, `invalid_limit` |
| 403 | `clearance`, and the permission refusals (`not_member`, `intern_channel_denied`, role) |
| 404 | `not_found`, `document_type_not_found`, `version_not_found` |
| 409 | `draft_changed`, `draft_locked`, `not_gated`, `nothing_to_override`, `already_overridden`, `gate_blocked`, `gate_result_changed`, `matter_closed` |
| 422 | `court_mismatch`, `classification_below_matter`, `unsupported_characters` (no code-point details, O-73), `draft_too_large`, `title_too_long`, `gate_result_too_large`, `review_checklist_incomplete`, `temporal_check_not_in_draft` |

The shape of a request (the 400 codes) is checked before the permission, in a stated order, and the first failure wins. One 400 comes after it: the merged-set caps of R10 (`invalid_temporal_checks`) need the draft's recorded checks, so a caller refused for the permission never reaches them. The text rules (the 422 codes) are applied only after the permission, so a caller who is not allowed is refused for the permission and learns nothing about a body (no oracle).
