# P1 AI gateway

The single routing point for every AI call in Cloud Functions (spec `docs/superpowers/specs/2026-10-11-phase3d-p1-ai-layer-design.md`, rulings P3-60 to P3-73; errata E-48 and E-49 in `docs/architecture/ERRATUM_SET_2_PROPOSED.md`). A layer that needs a provider calls `callP1` with a classification and never calls a provider itself (Layer 18 §9, rule 6). `callP1` records every decision, allowed or refused, in `ai_usage_logs`, and the provider guard and the fetch allowlist let only `functions/src/p1/`, `platform/p1` and `platform/committeeBrain` reach a provider. Since audit F18, G-0 check [19] (`ci_gates/check_next_ai_egress.py`) also holds the Next and eve runtime, `platform/p1` included, to no AI SDK, provider SDK, provider key or provider host, so in the app only this directory can reach one (the corpus service's allowlisted embedding call, FA-D3C-002, is outside the app and in the F27 lane).

P1 is CORE, with no layer flag. Audit F18 (spec `docs/superpowers/specs/2026-10-18-f18-legacy-ai-path-closed-design.md`) closed the Next.js legacy path. The Next.js and eve runtime holds no provider transport: `platform/p1/gatewayTransport.ts` is deleted, and `callCommitteeBrain` masks, applies policy and is blocked (`PHASE0_NO_CREDENTIALS`). In a Firebase session the Next.js `/api/p1/committee-brain` route forwards the request to `committeeBrain` below with the caller's own ID token, firm and Idempotency-Key, so the kill switches, the budget and the cost log govern it too. The eve bridge has no signed-in caller or matter and stays blocked. The Next.js and eve deployment must hold no provider key: under `NODE_ENV=production` a key there refuses every call there with the alert line `p1.provider_key_in_next_runtime`, and eve refuses to start. `AI_GATEWAY_API_KEY` belongs to the `api` function only.

## Entry point

`callP1(request, opts?)` in `gateway.ts` is the v6 `internalAICaller`. The request carries `firmId`, `actorId` (a uid or `"system"`), `matterId | null`, `jobId | null`, `taskType` (`committee` is the only one), `classification`, `body`, `purpose` and `partyNames?`. The result carries the outcome (`ok`, `failed` or `blocked`), the block reason, the masked `text` (only when `ok`), the usage row id, the trace id, the model, the token counts, `costMicroUsd`, the masked outbound body and purpose with the `redactionCounts` and `residualCounts` (audit F15) of the body (the system message is platform text, not user data: audit F16 review round, R3a), the system record `system: { policyId, version }` (audit F16; the registry policy by reference, never its text, R4a), and `accounting` (audit F08). `accounting` is `settled` when the usage row and month total are committed. It is `pending` when they are not, and then any provider spend is still held by the call's reservation until the reconciler settles it. So whether the result is available and whether its accounting is complete are told apart. `committeeBrain` returns and stores `accounting` too.

Spend is counted per provider call, not per request. A replay of a stored 2xx never reaches P1. A `committeeBrain` request makes at most one provider call per Idempotency-Key (audit F09, which closes O-58 pending re-audit). The operation's effect marker (`idempotency_effects/{id}`) is created with the provider-attempt record in step 8c, so an operation dispatches at most once. The provider's answer is recorded on the marker in step 9b, so a same-key retry after a failed output write or a crash publishes that answer instead of calling again (see "Collections and documents"). A job attempt that calls the provider again has been billed again and gets its own row.

## Pipeline order (P3-61)

The first refusal wins. A refusal at steps 2 to 8c makes no provider call, costs 0, and is still traced and logged (steps 10 and 11) with outcome `blocked` and a fixed `blockReason`.

1. Classification guard: a missing or unknown label throws, before any read or write (L8473).
2. Kill switch: the platform's, then the firm's (P3-66). Both are read fresh on every call.
3. Route: task type to model (P3-62).
4. Outbound request (audit F16, see "Role-separated requests" below): the registry's system message for the purpose, then the body as the user's own turn, the body masked with the party names (`maskOutboundPII`) and its envelope tag look-alikes neutralised; the system message is immutable platform text, never masked (R3a); the purpose is masked too; the residual detector's counts over the body (`residualPII`, audit F15). See "What the mask does and does not do" below.
4a. System message (audit F16 review round, R3a), after step 2's kill switches: it must be exactly the registry text its record names (`verifySystemMessage`), else `system_unverified` and nothing is sent.
5. Provider policy: `providerAllowedFor("ai-gateway", classification)`, and at rank 3 and above `assertMinimised` on the user message and the masked purpose (the verified system message is platform text, R3a): a mask re-run must find nothing and `residualPII` must find nothing.
6. Price: the model must have one.
7. Budget: one must be set, and the call's worst case must fit beside the month's spend and the holds of its live reservations (P3-64, audit F07). This first look uses the pre-call read; step 8b decides again on fresh figures.
8. Credentials: `AI_GATEWAY_API_KEY` must be set.
8b. Reservation (audit F07). One transaction re-reads both kill switches, the month total, the firm's config and the learned request overhead (`platform/p1Overhead`) and creates `ai_reservations/{usageLogId}` holding the worst case, adding it to the month's `reservedMicroUsd`. The worst case is the input ceiling of the masked messages (for each, one token per UTF-8 byte of the largest of its content and its four Unicode normal forms, plus 16 tokens for its role and turn markers, audit F16; then the model's request overhead: the larger of the cost table's, 1,024, and the one learned from a breach) plus the 4,096-token output ceiling, at the model's price (re-audit R1-D1, R2-D3; Copilot finding on PR #40). It refuses, in this order: `kill_switch_platform` and `kill_switch_firm` (a switch set after step 2's read still stops the call here, re-audit R1-D3); `budget_not_set`; `accounting_indeterminate` (the firm has a provider attempt whose lease lapsed unsettled, or a reservation the reconciler quarantined, F08); `budget_exhausted` unless spent + reserved + the new reservation is at most the budget; and `concurrency_exhausted` when the firm already holds `maxConcurrentCalls` live reservations (default 4). If the reservation cannot be written within its deadline, the call is refused `reservation_failed`. In every refusal nothing is sent.
8c. Provider attempt (audit F08). A second small transaction records `providerAttempt: { attemptedAt, outcome: "pending" }` on the reservation, only while it is still held. If that write fails, the call is refused `reservation_failed`, nothing is sent and the commit releases the hold. For an HTTP operation (`committeeBrain`, audit F09) the same transaction is the dispatch fence. It reads the operation's effect marker and creates it (`kind: "p1_dispatch"`, the usage row id and trace id, the request's binding and its `matterId`) when absent. A marker with another trace id means the operation already dispatched under another attempt: the call is refused `reservation_failed` and nothing is sent.
9. Transport call (the role-separated `messages`, posted as given: `{ model, messages, max_tokens }`), then the response mask. Any transport error is outcome `failed`, reason `transport_error`. It is charged when the provider may have billed it (a timeout or abort, a 2xx that is not JSON, a 2xx without usable content): the usage the response reported where it is a valid count, else the estimated input (over every message sent, the system message included) and the 4,096-token ceiling, with `tokensEstimated: true`. A non-2xx and a request that never left (a refused connection, DNS, a refused redirect) cost 0. A transport that resolves without text is billed like `gateway_no_text`; any error that is not a billable `P1TransportError` costs 0. A billed failure keeps the provider's ids like an answer does (Codex P2 on PR #40): the transport reads the request-id header before it parses the body, so a 2xx that is not JSON keeps `requestId`, and one without usable content keeps `responseId` and `requestId`; both ride on the `P1TransportError`.
9b. What the provider answered and what the call is charged go on the reservation's attempt (`outcome: "returned"`, `result`, the token counts, `costMicroUsd`), with the provider's response id (`responseId`, the body's `id`) and the Gateway's request id (`requestId`, the `x-request-id` or `x-vercel-id` header) when each is a plain id (re-audit R1-D5), for an answer and for a billed failure alike. Which request-id header the Gateway sets is to be confirmed at G-1 (O-57). This write is fail-open, and lands only while the reservation is still held, so it never rewrites the attempt of a reservation the reconciler has settled. It lets the reconciler settle at that charge if the commit fails. For an HTTP operation the same transaction records the attempt receipt on the operation's marker (audit F09): the outcome, the masked text, the token counts, the cost, the model, the classification and the masked outbound. The receipt never goes on the reservation. The write is attempted up to 3 times, waiting 100 then 200 ms, all within its 2 s share of the time budget (re-audit LOW-2). If it still fails, `logger.error("p1.receipt_record_failed", { firmId, usageLogId, operationId, traceId, code })` names the charged call whose answer a retry can no longer resume.
10. Trace export (P3-67), fail-open.
11. One transaction: the usage row, the month total, any threshold alerts, the audit row and the event. The same transaction settles the reservation: the actual cost is added to `spentMicroUsd`, the hold leaves `reservedMicroUsd`, and the reservation takes `state: "settled"` (an ok call or a billed failure) or `"released"` (an unbilled failure, or a call refused after it reserved), with `actualMicroUsd`. A reservation the reconciler already settled is never counted twice: the commit fails on it and finds the reconciler's usage row.

No raw (unmasked) body, purpose or response text reaches the transport, a trace, a usage row, an event, an audit row or a log line. Provider error text is never returned, stored or logged: the transport throws a `P1TransportError` whose code (`gateway_timeout`, `gateway_request_failed`, `gateway_status`, `gateway_not_json`, `gateway_no_text`) and message are fixed, and the gateway logs only the code (`p1.transport_failed`). The transport refuses redirects (`redirect: "error"`), so the key and the masked body go to the Gateway URL only.

### Role-separated requests (audit F16)

Spec `docs/superpowers/specs/2026-10-17-f16-prompt-trust-roles-design.md`. A request is `[{ role: "system", content }, { role: "user", content: body }]`, built by `buildOutbound` (`platform/p1/outboundPrompt.ts`), never one flattened string.

- **System text comes only from the registry** (`platform/p1/systemPolicy.ts`): one fixed, versioned policy per purpose (`committee-brain`, `summarise`, `research`, `translate`, `ops-audit`); any other purpose gets `committee-brain`. No caller can supply system text. The policies carry no secret, no firm or client name and no classification label, and tell the model that text inside the `<untrusted_content>` envelope is data, never instructions.
- **Immutable and verified** (review round, R3a): the system message is never masked or neutralised, so a party name equal to one of its sentences cannot redact a rule; it adds nothing to the redaction or residual counts and is left out of `assertMinimised`; and step 4a refuses `system_unverified` unless it is exactly the registry text its record names.
- **Envelopes** (`platform/p1/promptEnvelope.ts`): untrusted content (a tool result, a document) travels between `<untrusted_content source="...">` and `</untrusted_content>`, each on its own line. Every look-alike of the tag name in non-platform text (case, spacing, full-width, Cyrillic or Greek look-alikes, invisible characters) is replaced by `[envelope tag removed]` first, so no envelope can be closed from inside. The committee route sends no envelope today (`documentIds` are refused); the user's body is neutralised all the same.
- **Recorded by reference plus the body** (R4a): the result's and the receipt's `outbound.system`, the output row's `outbound.system` and the trace's `input: { system, prompt }` hold `{ policyId, version }`, never the system text, which `systemPolicyText` re-derives (the registry keeps every version's texts). A receipt recorded before F16 has no `system` and still resumes; one whose `system` is not exactly `{ policyId, version }` of a registry entry (an unknown id or version, an extra key such as a text) is refused (409).
- **Budget**: `requestTokenCeiling(messages)` (each message's ceiling plus `MESSAGE_OVERHEAD_TOKENS`, 16) is reserved as `reservedBodyTokens`, so the system message is never left out of the worst case.
- Model-level injection resistance is NOT DEMONSTRATED here: the structure is tested (`tests/f16-injection-structure.test.ts`, a versioned corpus); the live evaluation runs only with `AI_GATEWAY_API_KEY`.

### Grounded committee output (audit F17)

Spec `docs/superpowers/specs/2026-10-17-f17-grounded-committee-output-design.md`. A successful provider call says nothing about whether its content is true; `committeeBrain` grades every answer before it is stored and returned.

- **Contract.** Registry version `f17.1` asks the committee-brain model for one JSON object: `{ sections: [{ heading, text, claims: [{ statement, authorities: [{ kind, citation, pinpoint? }] }] }], caveats: [] }` (`platform/p1/committeeAnswer.ts`: a strict reader, no code fence or prose around it, no duplicate key, no `\u` escape, bounded; a zod `.strict()` schema with bounded sizes). An answer that is not the contract is still a successful call: it is stored and returned, masked, as `unstructured`.
- **Independent resolution** (`grounding.ts`). Every claim authority and every citation the D4 extractor finds in the prose is resolved through the D4 gate's own steps (`lookUpCitation`, `verdictOfJudgment`, `budgetedStore` in `functions/src/d4/gate.ts`) against `activeAuthorityStore()`: VERIFIED, OVERRULED, PENDING_OVERRULING, UNVERIFIED (not in the corpus, or any authority declared statute, rule or other, which the port cannot look up by citation), UNRECOGNISED or UNAVAILABLE. Only an authority a claim declares `judgment` goes through the judgment path (rules `f17.2`, review round: Codex P1 on PR #63): any other kind is never looked up, is UNVERIFIED and, when its citation reads as a reported judgment citation, is marked `kindMismatch: true`; a prose hit of the same citation verifies only itself, never the claim. Every prose field (heading, text, statement, pinpoint, caveat) is also read by `proseAuthority.ts` for what the D4 extractor does not see (rules `f17.3`, re-audit ruling R7a): a foreign or other law report, a short case or petition number, a case name (`v.`, `vs`, `versus`, `v/s`, `the X case`, `X (supra)`, the Urdu `بنام`), a page-only reference and `reported at/in/as`. A report shape that reads as one reported citation is resolved like any other; every other mention is an UNRECOGNISED suspect (masked, then bounded) unless a VERIFIED citation follows a case name or number directly (`Qalvo v. Nura (PLD 2099 SC 101)`), or precedes a page directly, so such an answer is at most `partially_grounded`. Since rules `f17.4` (re-audit round 2, ruling R7b) each field is normalised first (NFKC, format characters, Arabic-Indic and full-width digits, dashes) and masked whole, and read by shape: possessive and prefixed case names (`Qalvo's case`, `In re`, `Ex parte`, `In the matter of`, `the judgment in X`), `X, supra` and `ibid`, capital-group case numbers (`Crl.P.L.A.`, `C.M.`, `W.P.(C)`), paragraph references, reporters in any case, US and bracketed-volume reports, a guarded catch-all, and the Urdu `بمقابلہ`, `مقدمہ X`, `X کیس`; statutes with a year and the matter's FIR number stay grounded. Refs are cut at a word boundary. The detector is linear (64 KB and 256 KB time-budget tests) and leaves the D4 gate unchanged. With no corpus configured nothing is ever grounded.
- **Record.** The row, the API answer and the stored Idempotency-Key answer carry `grounding: { status, rules: "f17.4", policy, claims: { total, supported }, citations, omitted }` and `advisory` (true unless `grounded`), plus `model` (configured), `modelReported` and `modelMatch`. Status: `grounded`, `partially_grounded`, `ungrounded`, `unverifiable`, `unstructured`, `not_assessed` (no text, or no citation at all: F06, never OK). **Grounded means** every claim's authorities are VERIFIED and the prose holds no unverified authority in a recognised form; a bare name with no case marker (e.g. "as observed in Qalvo") cannot be detected.
- **Time and spend.** Grounding starts from `callP1`'s `onAnswer` hook the moment the masked answer exists and runs beside steps 9b to 11, within `GROUNDING_BUDGET_MS` (20 s), which an import-time check holds inside those phases (29 s): the worst case is unchanged. It reserves and charges nothing. A failure never loses the answer: `unverifiable`, logged `p1.grounding_failed { code }`.
- **Resume (F09).** The receipt never carries grounding: the resume path grades the receipt's masked text at publication. A receipt carrying `grounding`, or a `modelReported` that is not a model id, is refused (409). A receipt recorded before F17 still resumes.
- **Evaluation and change gate.** `docs/evals/committee-brain-eval-set.json` (version `f17.4`: 89 items, English and Urdu, synthetic responses) is graded on every test run (`functions/test/f17-eval-set.test.ts`); `npm --prefix functions run eval:committee-live` runs it against the real model only with `AI_GATEWAY_API_KEY` (NOT RUN otherwise). Gate G-0 [17] (`ci_gates/check_committee_eval_record.py`) fails any change of `TASK_MODEL`, the Next legacy model, `SYSTEM_POLICY_VERSION`, `GROUNDING_RULES_VERSION` or the set without a matching `docs/evals/committee-brain-eval-record.json`; a live record must cover every item (`passed` equal to the set's items, `failed` 0, integers only: review round, Codex P2 on PR #63), its note must not say NOT RUN (in any case), and neither it nor the record may be dated more than a day ahead; the gate reads each value from its one declaration in code, outside comments and string or template literals, as a plain string literal (re-audit L3 and round 2).
- **Not caught:** a fabricated statute in the prose beside a verified judgment still grades `grounded` (statutes are not extracted from prose; re-audit L5); a bare name with no case marker; a citation split across two prose fields.
- **Not demonstrated here:** no model was called. Whether the model follows the contract, cites only real authority or resists an injection asking it to claim verification is measured only by the live run, which did not run.

### What the mask does and does not do (audit F15)

Masking reduces risk; it is not anonymisation. A call that passes the mask, and at rank 3 and above `assertMinimised`, has had the recognisable identifiers and the recorded names removed. That does not prove that nothing identifying remains.

- **Before detection** (`platform/p1/piiText.ts`), the text is read through a normalised view that changes nothing that is sent. Format characters, every default-ignorable code point (zero-width spaces and joiners, directional marks, soft hyphens, the combining grapheme joiner, variation selectors, Hangul fillers, Mongolian and Khmer invisibles, tags) and every combining mark (accents, underlines, keycaps, harakat) are dropped. Every decimal digit of any script, and every enclosed or dingbat digit, becomes ASCII. Dashes, spaces, and Arabic and ideographic separators are normalised.
- **Masked** (`platform/p1/maskOutboundPII.ts`):
  - Everything main masked, Unicode glue included: main's algorithm also runs on the raw text as written, and the mask writes the union of its spans with the detection view's (audit F15 round 4, R4-1). Every scan resumes where its last match, a run of joined emails included, ended, so `a@b.pk.a@b.pk.a@b.pk` is read once and later positions never shift (round 5, R5-1); stage 0's spans equal main's exactly. Differential tests against main are in `tests/f15-r3-mask.test.ts`, `tests/f15-r4-mask.test.ts` and `tests/f15-r5-mask.test.ts` (the re-auditor's generator, 24,000 inputs each, compared span by span; round 5's also joins 3 to 8 emails).
  - CNICs: 5-7-1 with any run of spaces, line breaks, dots, dashes, commas, slashes or underscores between the groups, and thirteen digits in form boxes or 4-4-4-1 groups.
  - Pakistani mobiles: +92, 0092, 92 or 0 prefix, any grouping, any run of whitespace, dots, commas, dashes, brackets, colons or underscores between groups, and a slash only where it touches whitespace (`0300 / 1234567`; `03/01/2021 123` is a date and a number).
  - Landlines with their area code, and UANs.
  - Emails, with local parts and domains of any script.
  - PK IBANs, with any run of spaces or dashes between groups.
  - NTNs (`NTN`, `N.T.N`, with `No.`) and labelled passports, with any run of colons, spaces, dashes, hashes or dots after the label; passports also as two capitals and seven digits.
  - The names of the matter's `matter_parties` rows, of its client record (`canonicalName`, `companyName`, `concernedPersonName`) and of the request, longest first. They match through case, spacing, punctuation, Latin diacritics, harakat, tatweel, Arabic letter variants (do-chashmi he included), Cyrillic and Greek look-alikes, and a leading honorific in the record.
- **Detected, not masked** (`platform/p1/residualPII.ts`, a different method on the masked text). At rank 3 and above any finding blocks the call `not_minimised`; below it, the counts are stored as `residualCounts`. The detector looks for:
  - identifier-length digit runs: numbers without a mobile prefix and other ID numbers, but not amounts (one group of at most eleven digits), case and document numbers, land-record numbers, section lists or dates. Thirteen digits, ten single-digit boxes, a card or account number (14 to 19 digits in one group or in fours) and a ten- or eleven-digit run starting 3 keep no exemption;
  - labelled identifiers, each label with its own minimum over its whole value (every digit group up to the next letter): phone 7 digits, CNIC 5, NTN 7, licence 5, a passport token of 7 characters, an address-like email value or a spelled one (`email x at y dot z`);
  - addresses: `r/o`, `resident of`, `ساکن`, `رہائشی` before a place (a general area, Pakistan or a province only when it is the whole place: `r/o Punjab Colony`, `r/o District Kasur`, `ساکن شہر قلوو` count; not the adjective "residential"); plural `residents of`, `سکنائے`, `ساکنان` before a locality word (village, Kot, Pind, Tehsil ...) and a named place; `lives`, `residing`, `stays`, `abode`, `settled`, `residence` with at, in, near or opposite and a number (not a year) or a proper noun within ten words; `hails from`, `originally from`, `belongs to` before a named or numbered place; `C/o` before a name or an address; `Address of accused:` and other address labels for a party role; `قلوو پورہ کا رہنے والا`, `کا باشندہ` after a place; `رہائش پذیر`, `سکونت پذیر`, `مقیم` with a place next to them (`قلوو ٹاؤن میں رہائش پذیر`, `بمقام قلوو پورہ سکونت پذیر`; not `یہاں مقیم`, `بیرون ملک مقیم`, `والد کے گھر میں`); `محلہ`, `موضع` and similar before a name (not `اہل محلہ`); an address label at a field start, or anywhere with a digit or an address word in its value (never "not known", "same as above" or `حسب عنوان`); an explicit `House No.` always; street, plot, flat and shop numbers that are not measures or ranges;
  - parentage and marriage clauses: `s/o`, `son of`, `wife of`, `ولد`, `زوجہ`, `بیوہ`, and the labels `Father's name`, `Parentage`, `ولدیت`, in a sentence or a table (`| Tariq | s/o | Kamran Qalvo |`). After an English cue the check reads eight words: a lower-case finite verb or auxiliary or a sentence end ends it, every other lower-case word is skipped, titles, ranks, offices, roles, organisation and nationality words are skipped, and the first other capitalised word is a name (`son of the then SHO Kamran`, `son of a sitting MNA Kamran`, `son of none other than Kamran` count; `son of a Government servant`, `son of the deceased appeared` pass; `son of a Lahore High Court judge` counts, an accepted false positive; round 5, R5-2). Urdu role nouns, ordinals and occupations are walked past (`زوجہ ملزم کامران`, `ولد نیک قلوو` count); an Urdu stop word ends the check (`دختر نیک اختر`, `زوجہ اول اور زوجہ دوم` pass). At rank 3 and above a missed name is worse than a blocked call, so where a rule trades one for the other it counts (R4-0).
  - Every cue regex is built from word lists the bound test runs at 100,000 characters, so the check stays linear.
- **Not caught at all:**
  - names nobody recorded, written in free prose (there is no auto-NER), and recorded names written only in part or reversed;
  - semantic identifying facts ("the only female sessions judge in the district", age, caste, date of birth);
  - addresses and relationships written without a cue;
  - identifiers spelled out in words (`zero three zero zero ...`, `house number twelve`), obfuscated without a label (`[at]`, `[dot]`) or with look-alike letters (`O3OO` for `0300`; the residual check counts `O300-1234567`);
  - `ولد کا کامران` (a stop word before the name) and `بن` ("son of" in Arabic, the Urdu verb "become");
  - a CNIC or licence label with four digits (`CNIC No. 3520`);
  - vehicle registration and chassis numbers.

  The classification label is still the gate: a privileged text labelled `internal` is masked and counted, not blocked.

## Routes

On the existing HTTP `api` under `/api/platform/brain/` (E-37: no onCall).

| Route | Method | Who | Notes |
| --- | --- | --- | --- |
| `committeeBrain` | POST | partner, associate, clerk on the matter (`ai.call`) | rate kind `p1` (10 per minute per user); body 1 to 100,000 characters; `documentIds` refused (`documents_not_supported`); classification is the strictest of the matter's label, the caller's label and the `internal` floor; writes one `committee_outputs` row |
| `getAiUsage` | GET | partner (`ai.usage.read`) | `?month=YYYY-MM`, default the current PKT month; reads the month total, not the logs; shows both kill switches (the platform's `setBy` is always `"platform"`) |
| `setBudgetAlerts` | POST | partner (`ai.budget.set`) | `{ monthlyBudgetUsd, pkrPerUsd? }`; the thresholds are fixed |

| `setPlatformAiKillSwitch` | POST | platform admin (`platformAdmin` claim), firmless | same body; the operator's switch across every firm. Its `reason` is shown to every firm's partners in `getAiUsage`, so it must never name a firm or a client |

Tracing is on only when `OPIK_BASE_URL` is a usable `http(s)` URL (no credentials, no query or fragment; plain `http` only when the host is loopback (`localhost`, 127.0.0.0/8, `::1`), a private IPv4 literal (10/8, 172.16/12, 192.168/16) or a name ending in `.internal` or `.local`), `OPIK_SELF_HOSTED_CONFIRMED` is `"true"`, and the host is not `comet.com` or a subdomain of it. The checks run in that order and report `unset`, `invalid_url`, `unconfirmed`, then `third_party_host`. The export refuses redirects: a redirect is a `failed` export and nothing is sent to its target.

Nothing in `functions/src` binds the key as a function secret yet. Until the deployment supplies `AI_GATEWAY_API_KEY` to the `api` function, `committeeBrain` answers with a `blocked` row (`no_credentials`) and no provider is called.

## Cost, budget and alerts

- **Model and price.** `committee` goes to `anthropic/claude-opus-5.5` through provider id `ai-gateway`. Prices are integer nano-USD per token (input 4,000, output 20,000), with their source and the date fetched (2026-10-11) in `costTable.ts`. Each priced model also carries its request overhead (`inputOverheadTokens`, 1,024 for Opus) and whether that figure has been measured against the provider (`inputOverheadVerified`, false until G-1). The routing and price tables are frozen. A model with no entry, no price or no overhead is refused `model_unpriced` before anything is reserved or sent (fail closed, Copilot finding on PR #40). Every call sends `max_tokens: 4096`.
- **Cost.** In micro-USD, `ceil((inputTokens x inputPrice + outputTokens x outputPrice) / 1000)`. When the response carries no usage, each side is estimated as `ceil(UTF-8 bytes / 3)` tokens and the row says `tokensEstimated: true`: the input from the masked body that was sent, the output from the raw response, because masking shortens it and the provider billed the raw length. The raw text is used for that count only; the masked text is the only one returned, stored, traced or logged. A failed call the provider may have billed is charged too (step 9), and moves the month's spend and token totals by the same rule as an ok call, so it can cross a threshold and counts toward `budget_exhausted`.
- **Currency.** Micro-USD integers are canonical. When the firm has set `pkrPerUsd`, the row stores the rate and `costPkr` to 2 decimal places. There is no default rate.
- **Budget (audit F07).** Per firm per PKT calendar month (`YYYY-MM`, Asia/Karachi, UTC+5). With no budget set every call is refused `budget_not_set`. The budget is a limit on spend plus holds: a call is sent only after its reservation commits, and a reservation commits only if spent + reserved + its worst case is at most the budget. Once the remainder is smaller than a call's worst case (86,128 micro-USD for a 28-byte prompt; 486,016 for a 100,000-byte ASCII one), that call is refused `budget_exhausted` until the partner raises the budget, a hold is released, or the month turns.
- **The bound, precisely (re-audit R1-D1, R2-D3; Copilot finding on PR #40).** A call's worst case is `costMicroUsd(model, bodyTokenCeiling(maskedBody) + overhead, 4096)`, where:
  - `bodyTokenCeiling` is the largest UTF-8 length of the masked body as sent and of its NFC, NFD, NFKC and NFKD forms. A byte-level tokenizer bills at most one token per byte of what it splits, and a tokenizer that normalises first may split the normal form: NFKC turns U+FDFA, 3 bytes, into 33. Taking the largest of the five is conservative; that no provider bills more for the body is [REQUIRES VERIFICATION] at G-1 (O-57).
  - `overhead` is the larger of the model's `inputOverheadTokens` in the cost table (`REQUEST_OVERHEAD_TOKENS`, 1,024: deliberately generous, since the request sends one user message and no system prompt or tools, but what a provider adds unseen is not documented; the exact figure is [REQUIRES VERIFICATION] at G-1) and the overhead learned for the model from a breach (below), the learned one counted only up to the clamp: `LEARNED_OVERHEAD_MAX_FACTOR` (4) times the table's figure, 4,096 tokens for Opus (re-audit R3-D1).
  - The provider honours `max_tokens`, so output tokens never exceed 4,096.

  Spent stays within budget unless a provider bills more input than bytes + overhead; any such breach is recorded, raises an event, and raises the overhead for later calls of that model. The raise is clamped (re-audit R3-D1): the learned overhead is platform-wide, so it never counts for more than 4 times the table's figure, which bounds what one provider report can add to every other firm's reservations to 3,072 input tokens (12,288 micro-USD at the Opus input price) per call. A breach that shows more than the clamp is an anomaly: it teaches only the clamp, and it is recorded and raised as described below. Within the bound this holds for one call or for many in flight together. The charge estimate used when no usage is reported (`estimateTokens`, bytes / 3, P3-62) is lower than the bound and is not used for the reservation.

  A provider that bills more than the bound breaks the condition, not the books:
  - its charge is still recorded in full, because it is owed;
  - the excess is recorded on the reservation (`exceededMicroUsd`, and `exceededInputTokens` when the input side passed the reservation's `reservedInputTokens`);
  - the same transaction writes the event `ai.reservation.exceeded` (`{ monthKey, reservedMicroUsd, actualMicroUsd, excessMicroUsd }`);
  - when the input side passed, the same transaction raises the model's learned overhead in `platform/p1Overhead` (server-only) to the input tokens billed less the body's ceiling, counted only up to the clamp and keeping the largest seen; every later reservation for the model adds the larger of that (again at most the clamp, whatever is stored) and the table's figure. Every raise is logged `p1.overhead_learned` at ERROR, so an operator sees each one;
  - when the overhead a breach shows is above the clamp, it is an anomaly (re-audit R3-D1): in the same transaction the reservation takes `usageAnomaly: true` and the event `ai.usage.anomaly` is written (id `{usageLogId}_usage_anomaly`, payload `{ monthKey, model, inputTokens, bodyTokens, overheadTokens, learnedTokens, clampTokens }`), and after commit `logger.error("p1.overhead_anomaly", ...)` is logged. A report that implausible (25,000,000 prompt tokens for a 28-byte body, or `Number.MAX_SAFE_INTEGER`) needs a person to look at it; it can no longer price other firms out. The cost table carries no context window per model, so there is no window check;
  - `logger.error("p1.reservation_exceeded", ...)` feeds Cloud Monitoring.

  In that case, and only then, spent can pass the budget, by the excess.
- **Concurrency (audit F07).** A firm holds at most `ai_config/{firmId}.maxConcurrentCalls` live reservations, an integer from 1 to 64, default 4 (`DEFAULT_MAX_CONCURRENT_CALLS`). A further call is refused `concurrency_exhausted`. No route sets it; it is server-set config. Within one instance a firm's reservation and commit transactions run one at a time through a per-firm queue, because transactions that overlap on the month total only abort each other. Across instances the transactions contend, and each one's re-read keeps the budget whatever the interleaving.
- **Time budget (Codex P1 on PR #40).** The whole committeeBrain request fits the 120 s `api` timeout, checked at import by `assertOperationTimeBudget`: the call's phases after its first reads (`CALL_WORST_CASE_MS`, 99 s: the reservation 5 s plus one attempt in flight 3 s, the attempt record 2 s, the transport 60 s, the attempt outcome 2 s, the trace 2 s, the commit 20 s plus one attempt in flight 5 s), plus the handler's own work (`COMMITTEE_HANDLER_OVERHEAD_MS`, 16 s: eight store or Auth round trips before the call at 1 s each, then the `committee_outputs` write with its 3 s deadline and one 2 s attempt in flight, then the Idempotency-Key completion, 3 s), must be at most the timeout less a 5 s margin (`REQUEST_TIMEOUT_MARGIN_MS`). 99 + 16 = 115 = 120 - 5. To fit, the commit's share fell from 30 + 10 s to 20 + 5 s and the reservation's attempt slack from 5 s to 3 s; the transport keeps its 60 s. The pre-call allowance is enforced (re-audit R3-D2, `PRE_CALL_ALLOWANCE_MS`, 8 s): measured on the real clock from when the router received the request (`session.startedAtMs`), and checked by `callP1` after its first reads and before step 8b. Past it, nothing is reserved, sent or written, `callP1` throws `P1PreCallDeadlineError` (`retryable`), and committeeBrain answers 503 `precall_deadline`, which releases the Idempotency-Key so the same request may be retried. A read that hangs is still not cut off, but it costs nothing, and no paid work starts that could outlive the request's timeout. The output write's retries are bounded: each try is one SDK transaction attempt (`maxAttempts: 1`), at most three tries, and no wait or try starts once it would end past `OUTPUT_WRITE_DEADLINE_MS` (3 s). The reservation's lease is the function timeout plus 60 s (180 s), so no live call can still settle a reservation the reconciler acts on.
- **Alerts.** At 70 and 90 percent. The transaction that takes the month total across a threshold creates `ai_budget_alerts/{firmId}_{monthKey}_{70|90}` with `tx.create`, so each fires once per firm per month, even for parallel calls. The same transaction stages the audit row `ai.budget.threshold` (actor `system`) and the event `ai.budget.threshold_crossed`; after commit `logger.warn("p1.budget_threshold", ...)` feeds Cloud Monitoring. Raising the budget does not re-arm a threshold already crossed that month. Delivery to people is P4 (O-54).
- **Failed commit (audit F08).** If the transaction fails after a successful provider call, the result is still returned (the spend has happened), with `accounting: "pending"`, and `logger.error("p1.usage_log_failed", record)` logs the record. The spend is not lost from the books: the reservation keeps holding its worst case with its provider attempt. Once its lease lapses, the firm is refused `accounting_indeterminate` until the reconciler settles it. `accounting` is `settled` whenever the call's usage row and month total are committed. The commit paces its own retries: one SDK attempt each (`maxAttempts: 1`, so the SDK never waits, and never applies its 60 s reset after RESOURCE_EXHAUSTED), with jittered waits from 100 ms doubling to 2 s that never run past the deadline; no attempt starts 20 s after the commit starts (`COMMIT_DEADLINE_MS`, code `commit_deadline`). The 20 s window and one 5 s attempt in flight (`COMMIT_ATTEMPT_SLACK_MS`) are the commit's share of the time budget above; an import-time check enforces it. Before any failure is logged the usage row is read: a commit whose answer was lost is done, nothing is logged as failed, and the thresholds it crossed are read back from its alert docs for the `p1.budget_threshold` warning.

## Kill switch

Two scopes, each `{ disableAll, disabledModels, reason, setBy, setAt }`: the firm's in `ai_config/{firmId}.killSwitch`, the platform's in `platform/p1.killSwitch`. They govern every paid call: since audit F18 the Next.js committee route forwards here and the Next.js and eve runtime has no provider path of its own (see the top of this file). The platform switch's `reason` is shown to every firm's partners in `getAiUsage` (its `setBy` is shown as `"platform"`), so it must never name a firm or a client. Only `disableAll === true` and an exact model id in `disabledModels` block. A request replaces the whole state; `disableAll: false` with no models re-enables. The reason is required (1 to 500 characters) and both writes are audited. P1 reads both on every call with no cache, so a switch takes effect on the next call; calls already in flight complete. Block reasons `kill_switch_platform` and `kill_switch_firm`.

The publication (audit F09) is one transaction: the route's allow row, the output row and the request's stored answer, so the answer commits with the output. It first reads the operation's fence:
- The request must still hold its claim; otherwise it answers 409 `idempotency_claim_lost`.
- The marker must be this call's dispatch. A blocked call, which never dispatched, creates the marker here.
- An attempt that finds its answer already stored was an earlier attempt whose commit landed: that is a success.

With no receipt (a crash between the provider's answer and step 9b), the key answers 409 `idempotency_effect_committed` and makes no second call; the reconciler still charges the attempt.

## Lease reconciler (audit F07, F08)

`p1ReservationReconciler` (`reconciler.ts`) runs every minute in `asia-south1`. It follows the job sweeper's pattern: a pinned 45 s timeout, a 30 s wall-clock budget checked before each page and each reservation, and no retry count, because the next minute's run is its retry. It asks for lapsed records directly, so live ones never take their place however many there are or however their ids sort (re-audit R1-D2, R2-D2):
- **Pass C, the sweep, first.** A slice of 200 records still `reserved`, in document-id order from a cursor kept in `platform/p1ReconcileCursor`, wrapping to the start after the last slice. It acts only on records whose `leaseUntil` no index can find: missing, or neither a Timestamp nor a number. Those count as lapsed (the gateway always writes a Timestamp, so no live call owns such a record). Every open record is read within ceil(open / 200) runs.
- **Pass B.** Records whose lease is a number of milliseconds at or before the clock (a malformed record), oldest first.
- **Pass A.** Records whose lease is a Timestamp at or before the clock, oldest first, 100 a page and at most 5 pages a run.
- **A failed record never stops the run.** Each record is tried at most once a run, and the pass moves past it. A pass whose own query or cursor fails is logged `p1.reconcile_pass_failed` (`pass`, `code`) and the run goes on to the next pass.

Option chosen for R2-D2, and why: an indexed query for lapsed leases (Passes A and B) rather than a bigger scan or a per-firm scan. A scan in document-id order reads live records as well, so any fixed page budget can be filled by live ones; the indexed query returns only records that can be acted on, oldest first, so 500 live records cost nothing and a backlog drains in lease order. The sweep covers what the index cannot (a missing or oddly typed lease) at a bounded cost per run, and running it first means a backlog in Pass A cannot starve it.

Each lapsed reservation is handled in its own transaction that re-reads it:

- **No `providerAttempt`.** Nothing was sent. The reservation is released: its hold leaves `reservedMicroUsd` and it takes `state: "released"`, `actualMicroUsd: 0`. No usage row is written.
- **A `providerAttempt`.** The reservation is settled through the same staging as a call's commit. The charge is the one the attempt recorded after the provider answered, when it did (`reconciledFrom: "recorded"`). Otherwise it is the reserved worst case: the input ceiling and the 4,096-token ceiling, with `tokensEstimated: true` (`reconciledFrom: "worst_case"`). The usage row is the call's own id, so a late commit of a live call can never add a second row or charge. A charge above the hold takes the excess path described under the bound.
- **Malformed records.** Fields a settlement can do without are defaulted: a missing `traceId` is recorded as null, a missing actor as `system`, and an unreadable classification as the strictest label (`privileged-restricted`). A record whose firm, month (`YYYY-MM`) or hold (`reservedMicroUsd`, a non-negative integer) cannot be read fails, because settling it would mean guessing what to take off which month total.
- **Output state (Codex P2 on PR #40).** In the same transaction as a settlement or a release, the call's `committee_outputs` rows (found by `usageLogId`, this firm's only) take `accounting: "settled"`, and so does the answer stored for the request's Idempotency-Key (the reservation's `idempotencyDoc`, only when its stored answer carries this call's trace id and still says `pending`). Both writes are idempotent. A same-key replay then answers `accounting: "settled"`.
- **Transient failures are not counted (re-audit R2-D1).** A failure that a later run may not meet (contention on the firm's month total, ABORTED, UNAVAILABLE, DEADLINE_EXCEEDED, RESOURCE_EXHAUSTED, CANCELLED, UNKNOWN, INTERNAL, UNAUTHENTICATED, an expired transaction) is logged `p1.reconcile_failed` with its code and `transient: true`, and retried on the next run. It never counts toward quarantine, so a valid record is never quarantined because its firm was busy.
- **Quarantine.** Only a fault of the record itself counts: `reservation_malformed`, or any other failure that is not retryable (an invalid write, an existing usage row). Each such run is counted on the record (`reconcileFailures`, `lastReconcileError`) and logged `p1.reconcile_failed` with `transient: false`. At the third (`RECONCILE_MAX_FAILURES`) the record is quarantined: `state: "reconcile_failed"`, `quarantinedAt`, and `logger.error("p1.reconcile_quarantined", { firmId, usageLogId, failures, code })`. It keeps its hold. Its firm is refused `accounting_indeterminate` until an operator settles it: fail closed, because the firm's accounting really is unknown.

### Runbook: settling a quarantined reservation

There is no route for this. It is an operator action with the Admin SDK or the Firestore console, on `ai_reservations/{usageLogId}`, recorded in the incident log.

1. **Find it.** The `p1.reconcile_quarantined` log line names the firm and the id. `lastReconcileError` gives the code: `reservation_malformed` means a firm, month or hold that cannot be read.
2. **Use this step: repair and requeue.** It is the supported path, because the reconciler then writes every record a settlement needs, exactly as the code does.
   - Correct the unreadable field from the evidence: the `committee_outputs` row with this `usageLogId`, the month total, and the Gateway's records for `providerAttempt.responseId` or `requestId`. A field the reconciler needs is `firmId`, `monthKey` (`YYYY-MM`) or `reservedMicroUsd` (a non-negative integer, the hold the month's `reservedMicroUsd` still carries for this record).
   - Set `state` back to `"reserved"` and `reconcileFailures` to 0, and if `leaseUntil` is missing or malformed, set it to a Timestamp in the past.
   - The next minute's run settles it through the normal path (Pass A or the sweep): the usage row, the month total with its token totals and `calls.reconciled`, any threshold alert, the audit row, the event `ai.call.reconciled`, and the output and stored-answer refresh. Step 4 confirms it.
3. **Last resort, only if step 2 cannot work: settle it by hand in one transaction.** Every write below is required; leaving one out leaves the books wrong in a way nothing later corrects. Let `charge` be the micro-USD the Gateway's records show (or the reservation's `reservedMicroUsd` if they show none), `in` and `out` the token counts behind it (or `reservedInputTokens` and `reservedOutputTokens`), and `hold` the reservation's `reservedMicroUsd`.
   - If the provider was called (`providerAttempt` is present):
     - create `ai_usage_logs/{usageLogId}`: `firmId`, `actorId` (or `system`), `matterId`, `jobId`, `taskType`, `provider: "ai-gateway"`, `model`, `classification`, `outcome: "reconciled"`, `blockReason: null`, `inputTokens: in`, `outputTokens: out`, `tokensEstimated` (true unless the Gateway's records gave both counts), `costMicroUsd: charge`, `fxPkrPerUsd` and `costPkr` (from the firm's `pkrPerUsd`, or null), `monthKey`, `trace: { id: <traceId or null>, status: "unknown" }`, `reconciledFrom: "manual"`, `createdAt`;
     - on `ai_usage_months/{firmId}_{monthKey}`, increment `spentMicroUsd` by `charge`, `inputTokens` by `in`, `outputTokens` by `out` and `calls.reconciled` by 1, and decrement `reservedMicroUsd` by `hold`; set `updatedAt`;
     - set the reservation to `state: "settled"`, `actualMicroUsd: charge`, `settledAt`, `settledBy: "operator"`, and `exceededMicroUsd: charge - hold` when `charge` is above `hold`;
     - create `events/{usageLogId}_reconciled`: `name: "ai.call.reconciled"`, `firmId`, `payload: { traceId, task, model, classification, costMicroUsd: charge }`, `classification`, `occurredAt`, `idempotencyKey: "{usageLogId}:reconciled"`;
     - when `charge` is above `hold`, also create `events/{usageLogId}_reservation_exceeded` (`name: "ai.reservation.exceeded"`, `payload: { monthKey, reservedMicroUsd: hold, actualMicroUsd: charge, excessMicroUsd: charge - hold }`, `classification: "internal"`);
     - when the month's spend crosses 70 or 90 percent of the budget and `ai_budget_alerts/{firmId}_{monthKey}_{70|90}` does not exist, create it, with its `ai.budget.threshold` audit row and its `ai.budget.threshold_crossed` event, as `stage` in gateway.ts does;
     - write an `audit_log` row `ai.gateway.reconciled`: actor the operator's uid, target `ai_usage_logs/{usageLogId}`, the reservation's classification, decision `allow`, reason `manual`.
   - If the provider was never called (no `providerAttempt`): decrement the month's `reservedMicroUsd` by `hold`, and set the reservation to `state: "released"`, `actualMicroUsd: 0`, `settledAt`, `settledBy: "operator"`. No usage row, event or charge.
   - Either way, set `accounting: "settled"` on the `committee_outputs` rows with this `usageLogId`, and on `idempotency_keys/{idempotencyDoc}` set `response.body.accounting` to `"settled"` when its stored answer carries this call's `traceId`.
4. **Confirm.** The firm's next call must no longer be refused `accounting_indeterminate`, `getAiUsage` must count the call under `calls.reconciled` (when the provider was called), and the month's `reservedMicroUsd` must have dropped by `hold`.

### Runbook: resetting a learned request overhead (re-audit R3-D1)

A learned overhead raises every firm's reservations for its model, up to the clamp (4 x the cost table's `inputOverheadTokens`, 4,096 tokens for Opus). An operator resets it when the breach that taught it is judged wrong: a `p1.overhead_anomaly` or `p1.overhead_learned` log line, or an `ai.usage.anomaly` event, that the Gateway's records for the attempt's `responseId` or `requestId` do not bear out.

- **Who.** A platform operator with Admin SDK or Firestore console access to production, never a firm user. `platform/p1Overhead` is server-only: `firestore.rules` denies every client read and write through the catch-all (`tests/firestore.rules.p1-phase3d.test.ts` proves no role of any firm, with or without `platformAdmin`, can read, write or delete it). There is no route for this.
- **How.** Delete the model's entry, `models.<key>` in `platform/p1Overhead`, where `<key>` is the model id with every character outside letters, digits, `_` and `-` replaced by `_` (`anthropic/claude-opus-5.5` is `anthropic_claude-opus-5_5`). With the Admin SDK: `update({ ["models." + key]: FieldValue.delete() })`. Deleting the whole doc resets every model.
- **Effect.** The next reservation for the model reads the table's figure again (1,024 for Opus). A later breach may raise it again, up to the clamp, and is logged at ERROR as before.
- **Record.** Note the reset, the model, the value removed and the evidence in the incident log.

The Gateway gives this code no per-request receipt, so no charge is matched against the provider's own bill here. The attempt keeps the provider's `responseId` and the Gateway's `requestId` so this can later be done per request. That remains O-57: reconcile `costMicroUsd` against the Gateway's records at G-1.

## Trace (Opik)

One trace per decision, posted to `{OPIK_BASE_URL}/v1/private/traces/batch`. The trace id is a UUIDv7 and is the usage row's `trace.id`. Ranks 0 to 3 carry the masked outbound body and the masked response; rank 4 and blocked calls carry metadata only (E-49). Export has a 2-second timeout and is fail-open: a failed export never fails the call, the row records `trace.status` (`exported`, `failed` or `disabled`) and the failure is logged as `p1.trace_export_failed`.
